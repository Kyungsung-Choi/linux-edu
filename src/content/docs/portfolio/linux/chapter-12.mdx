마지막 주입니다. 이번 주에는 **새로 배우는 것이 거의 없습니다.**

최종 프로젝트는 Chapter 12에 처음 시작하는 과제가 아니라, **Chapter 1부터 쌓아온 산출물을 하나로 조립하는 작업**입니다. 스냅샷, SetUID 기준선, 서비스 목록, SSH 키, 방화벽 정책, 백업 스크립트 — 이미 다 만들어 두셨습니다.

<Note type="why" title="이 챕터를 마치면">
- 요구사항 목록을 받아 보안이 갖춰진 서버를 처음부터 구축할 수 있다
- 각 설정에 대해 **왜 그렇게 했는지** 문서로 설명할 수 있다
- 다른 사람의 서버를 감사해 취약점을 지적할 수 있다
- 문제가 생겼을 때 추측이 아니라 로그로 원인을 찾는 순서를 안다
- 이 과정 다음에 무엇을 배울지 스스로 계획할 수 있다
</Note>

## 12.2 최종 프로젝트

<Lab id="Final" title="보안 강화된 웹 서비스 서버 구축" time="2주 (Chapter 10부터 병행 권장)">
**깨끗한 Ubuntu Server 24.04 VM에서 처음부터 시작하세요.** 지금까지 쓰던 VM은 이미 많은 것이 설정돼 있어 학습 효과가 떨어집니다.

### 시나리오

작은 회사의 사내 웹 서비스를 운영할 서버 한 대를 구축합니다. 서비스는 사내망에서만 접근하고, 관리는 SSH로 합니다. 개인정보를 다루므로 접속 기록을 남겨야 합니다.

### 필수 요구사항 (10개)

**1. 계정과 권한 체계**
- 관리자 계정 1개(`sudo` 사용), 운영자 계정 1개(제한된 sudo), 서비스 전용 계정
- root 직접 로그인 불가
- 운영자는 웹 서버 재시작만 가능, 다른 sudo 권한 없음
- 패스워드 정책 적용, 계정 만료 정책 설정

**2. SSH 하드닝**
- 공개키 전용 접속 (패스워드 인증 비활성)
- Chapter 7 하드닝 7항목 전부 적용
- fail2ban 동작

**3. 방화벽**
- 기본 차단 + 명시적 허용
- SSH는 관리망 대역에서만
- 각 규칙에 주석으로 사유 기록

**4. 웹 서버**
- Nginx, HTTPS 강제 (HTTP는 301 리다이렉트)
- 보안 헤더 5종 적용
- `server_tokens off`
- 점 파일 접근 차단

**5. 데이터베이스**
- `127.0.0.1`에만 바인드
- 애플리케이션 전용 계정, 최소 권한 (DROP·GRANT 없음)
- 접속 정보는 `640` 권한 파일로 분리

**6. 백업**
- DB와 설정 파일을 자동 백업
- systemd 타이머로 매일 실행
- 7일 이상 된 백업 자동 삭제
- **복원 절차를 실제로 검증한 기록**

**7. 로그**
- 로그 로테이션 설정
- `auditd`로 계정·설정 파일 변경 감시
- 보존 기간 정책

**8. 무결성 기준선**
- AIDE 기준선 생성
- SetUID 목록, enabled 서비스 목록 저장
- 주기적 검사 자동화

**9. 시스템 하드닝**
- 커널 파라미터 적용
- 불필요한 서비스 비활성화
- AppArmor enforce 상태 확인
- `umask` 조정

**10. 감사와 문서**
- Lynis 감사 실행, Hardening index 기록
- 지적 항목에 대한 조치 또는 미적용 사유

### 산출물

**① 구축된 서버** — 검증 가능한 상태

**② 운영 문서** (필수, 아래 항목 포함)

| 섹션 | 내용 |
|---|---|
| 시스템 구성도 | 어떤 서비스가 어떤 포트로, 어떤 계정으로 도는지 |
| 계정 목록 | 각 계정의 용도와 권한 범위 |
| 방화벽 정책표 | 규칙별 사유 |
| 설정 근거 | **각 보안 설정이 어떤 위협을 막는지** |
| 백업·복원 절차 | 복원 검증 결과 포함 |
| 미적용 항목 | 적용하지 않은 것과 그 사유 |
| 장애 대응 절차 | 서비스가 죽었을 때 확인 순서 |

**③ 검증 기록** — "되어야 하는 것"과 "되면 안 되는 것"을 각각 확인한 결과

**④ Lynis 리포트** — 초기와 최종
</Lab>

<Note type="danger" title="이 프로젝트에서 가장 많이 감점되는 것">
**설정은 다 했는데 검증 기록이 없는 경우**입니다.

12주 내내 반복한 원칙입니다 — 허용을 확인하는 것보다 **차단을 확인하는 것**이 중요합니다. 최소한 이 정도는 시험해야 합니다.

| 되어야 하는 것 | 되면 안 되는 것 |
|---|---|
| 관리자 계정 공개키 접속 | 패스워드로 접속 |
| 운영자의 `systemctl restart nginx` | 운영자의 다른 sudo 명령 |
| HTTPS 접속 | HTTP가 그대로 뜨는 것 |
| 앱 계정의 SELECT/INSERT | 앱 계정의 DROP DATABASE |
| 허용 대역에서 SSH | 다른 대역에서 SSH |
| 백업에서 복원 | 웹 루트의 `.env` 접근 |
</Note>

## 12.3 상호 리뷰 — 남의 서버를 감사하기

발표 후 조를 바꿔 **서로의 서버를 점검**합니다. 실무의 보안 감사를 축소한 것입니다.

<Note type="tip" title="감사자가 확인할 순서">
접근 정보를 받았다면 이 순서로 봅니다.

```
1. sudo ss -tulpn                    ← 무엇이 열려 있나
2. sudo ufw status verbose           ← 방화벽 정책이 그것과 맞나
3. grep -E "PermitRootLogin|PasswordAuthentication" /etc/ssh/sshd_config
4. awk -F: '$3==0 {print $1}' /etc/passwd     ← UID 0 계정
5. sudo find / -perm -4000 -type f 2>/dev/null | diff - 기준선
6. sudo find /var/www -perm -002 -type f      ← 누구나 쓰기 가능
7. curl -I https://서버/.env                  ← 403 이어야
8. curl -I https://서버                       ← 보안 헤더 확인
9. sudo cat /etc/sudoers.d/*                  ← sudo 범위
10. sudo lynis audit system
```

**1번과 2번이 어긋나면** 그것만으로 지적 사항입니다. 열려 있는데 방화벽 정책에 없거나, 정책에는 있는데 서비스가 없다면 관리가 안 되고 있다는 뜻입니다.
</Note>

<Note type="warn" title="리뷰할 때의 태도">
지적은 **사람이 아니라 설정에** 합니다. 그리고 세 가지를 함께 적으세요.

1. **무엇이** 문제인가 (사실)
2. **왜** 문제인가 (어떤 위협)
3. **어떻게** 고치는가 (구체적 방법)

"방화벽이 엉망이다"는 리뷰가 아닙니다. **"3306이 `0.0.0.0`에 열려 있어 사내망 어디서든 DB에 직접 접근 가능하다. `bind-address`를 `127.0.0.1`로 바꾸고 ufw에서도 차단하는 것을 권한다"**가 리뷰입니다.

이건 실무에서 그대로 쓰는 형식입니다. 취약점 보고서, 코드 리뷰, 장애 보고서 모두 같은 구조를 씁니다.
</Note>

## 12.4 문제 해결 방법론

이 과정에서 반복해 온 순서를 정리합니다. **막혔을 때 이 순서로 가세요.**

| 단계 | 하는 일 | 도구 |
|---|---|---|
| **1. 증상 확정** | 무엇이 안 되는지 정확히. "안 돼요"가 아니라 "이 명령이 이 오류를 낸다" | 오류 메시지 전문 |
| **2. 범위 좁히기** | 어느 계층인가 — 네트워크? 권한? 설정? 서비스? | Chapter 7의 6단계 진단 |
| **3. 로그 확인** | **추측하기 전에 로그를 본다** | `journalctl -u`, `/var/log/*` |
| **4. 재현** | 최소 조건으로 다시 만들어본다 | |
| **5. 가설과 검증** | 하나씩 바꾸며 확인. **한 번에 하나만** | |
| **6. 문서화** | 원인과 조치를 남긴다 | |

<Note type="tip" title="3번을 건너뛰는 것이 가장 흔한 실수">
서비스가 안 뜨면 사람들은 설정을 이것저것 바꿔봅니다. 그런데 대부분의 경우 **로그에 원인이 그대로 적혀 있습니다.**

```
$ systemctl status nginx
$ journalctl -u nginx -n 50 --no-pager
$ journalctl -u nginx -p err --since "10 min ago"
```

"포트가 이미 사용 중", "설정 파일 27번째 줄 문법 오류", "권한 없음" — 이런 메시지가 나옵니다. 읽으면 5초, 추측하면 한 시간입니다.

**그리고 한 번에 하나만 바꾸세요.** 세 가지를 동시에 고쳐서 해결되면 무엇이 원인이었는지 영원히 모릅니다.
</Note>

<Note type="tip" title="공식 문서를 읽는 습관">
Chapter 1에서 `man`의 역사를 이야기했습니다. 검색으로 찾은 블로그 글은 버전이 다르거나 틀릴 수 있습니다.

우선순위는 이렇습니다.

1. `man 명령어` — 그 시스템에 설치된 정확한 버전의 설명서
2. **공식 문서** — Ubuntu Server Guide, Nginx Docs, PostgreSQL Docs
3. Arch Wiki — 배포판은 달라도 리눅스 일반 지식으로 최고 수준
4. 블로그·Q&A — **날짜와 버전을 확인**하고 참고

`ifconfig`나 `apt-key add`가 나오는 문서를 보면 오래된 것입니다(Chapter 6·7). 다른 내용도 낡았을 가능성이 높습니다.
</Note>

자격증은 **아는 것을 증명하는 수단**이지 실력 그 자체가 아닙니다. 특히 리눅스 분야에서는 "무엇을 만들어 봤는가"가 훨씬 강한 증거입니다.

최종 프로젝트의 **운영 문서를 잘 다듬어 두세요.** 요구사항을 어떻게 해석했고, 각 설정을 왜 그렇게 했고, 무엇을 검증했는지가 담긴 문서는 웬만한 자격증보다 설득력 있습니다.

면접에서 "리눅스 할 줄 아세요?"라는 질문에 자격증 이름을 대는 것과, **"이런 요구사항으로 서버를 구축했고 이렇게 검증했습니다"**라고 문서를 보여주는 것은 다릅니다.
</Note>

</Note>

### 계속 배우는 방법

<Note type="tip" title="망가뜨릴 수 있는 서버 한 대를 계속 두세요">
Chapter 1에서 스냅샷을 강조한 이유가 이것입니다. **실력은 무서워하지 않고 시도한 횟수에 비례합니다.**

- VM이든 클라우드 최소 인스턴스든 **자기 서버 한 대**를 유지하세요
- 개인 프로젝트를 실제로 배포해 보세요. 도메인을 사고 HTTPS를 붙이는 것만으로도 배웁니다
- 로그를 정기적으로 들여다보세요. 인터넷에 노출된 서버의 `auth.log`는 훌륭한 교재입니다
- 무언가 망가지면 **고치기 전에 왜 망가졌는지** 먼저 알아내세요

12주 과정이 끝나도 리눅스를 다 아는 것은 아닙니다. 다만 이제 **모르는 것을 스스로 찾아낼 수 있는 상태**가 되었을 겁니다. 그것이 이 과정의 진짜 목표였습니다.
</Note>

## 12.6 과정 회고

<Note type="why" title="Chapter 1의 그 문장을 다시">
> 이번 주의 목표는 리눅스를 잘 다루는 것이 아닙니다. 검은 화면에 흰 글자만 있는 터미널 앞에서 **당황하지 않는 상태**가 되는 것입니다.

12주가 지났습니다. 이제 그 검은 화면은 여러분에게 **정보가 가득한 작업 공간**일 겁니다.

그리고 배운 것들 대부분에 이유가 있었습니다. 명령어가 두 글자인 것은 텔레타이프가 초당 열 글자를 인쇄했기 때문이고, `/usr`이 그 이름인 것은 1.5MB 디스크가 꽉 찼기 때문이고, SSH가 있는 것은 1995년 헬싱키에서 누군가 패스워드를 훔쳐봤기 때문입니다.

**이유를 아는 사람은 새로운 것을 만나도 추론할 수 있습니다.** 이 과정이 명령어 목록이 아니라 이야기로 짜여 있었던 이유입니다.
</Note>

### 개인 학습 계획 세우기

마지막 과제입니다. 다음 세 가지를 정리해 제출하세요.

1. **가장 어려웠던 챕터와 이유** — 그 부분을 어떻게 보완할 계획인지
2. **가장 유용했다고 느낀 것** — 실무에서 바로 쓸 수 있을 것 같은 것
3. **앞으로 3개월 계획** — 무엇을, 어떻게, 무엇으로 확인할지

<Note type="tip" title="3번을 구체적으로 쓰세요">
"리눅스를 더 공부한다"는 계획이 아닙니다.

- **무엇을** — "쿠버네티스 기초"
- **어떻게** — "매주 토요일 2시간, 공식 튜토리얼 + 로컬 클러스터 실습"
- **무엇으로 확인** — "3개월 뒤 개인 프로젝트를 클러스터에 배포하고 문서화"

이 형태로 쓰면 3개월 뒤 달성 여부를 스스로 판단할 수 있습니다. 못 지켰다면 계획이 과했던 것이니 조정하면 됩니다.
</Note>
