지금까지는 **디스크에 놓인 것**을 다뤘습니다. 이번 주는 **메모리에서 돌아가는 것**입니다.

서버 운영의 실체가 여기 있습니다. 서비스가 죽었을 때 왜 죽었는지 알아내고, 다시 살리고, 부팅할 때 자동으로 뜨게 만드는 일 — 그게 Chapter 5입니다.

<Note type="why" title="이 챕터를 마치면">
- 프로세스가 어떻게 태어나고 죽는지, PID와 부모자식 관계를 설명할 수 있다
- 시그널로 프로세스를 정중히 종료하거나 강제로 죽일 수 있고, 둘의 차이를 안다
- 전원을 켜고 로그인 화면이 뜨기까지의 부팅 과정을 순서대로 말할 수 있다
- `systemctl`로 서비스를 시작·중지·확인하고 부팅 시 자동 실행을 설정할 수 있다
- 직접 만든 스크립트를 서비스와 타이머로 등록해 주기적으로 실행시킬 수 있다
- 서비스에 전용 계정을 주는 것이 왜 보안인지 설명할 수 있다
</Note>

## 5.1 프로세스의 생애

**프로그램**은 디스크에 있는 파일이고, **프로세스**는 그것이 메모리에 올라와 실제로 돌아가는 상태입니다. `/bin/bash` 파일은 하나지만, 터미널을 세 개 열면 bash 프로세스는 세 개입니다.

<Term code={`
$ ps
    PID TTY          TIME CMD
   3421 pts/0    00:00:00 bash
   3502 pts/0    00:00:00 ps
`} />

| 용어 | 뜻 |
|---|---|
| **PID** | 프로세스 번호. 시스템이 프로세스를 식별하는 유일한 값 |
| **PPID** | 부모 프로세스의 PID |
| **UID** | 이 프로세스를 실행한 사용자. **Chapter 4의 권한이 여기서 적용된다** |

### 모든 프로세스에는 부모가 있다

리눅스에서 새 프로세스는 **기존 프로세스가 자기를 복제해서** 만들어집니다. 부모가 복제(fork)하고, 그 복제본이 다른 프로그램으로 갈아입는(exec) 방식입니다.

<Term code={`
$ pstree -p | head -12
systemd(1)─┬─cron(812)
           ├─nginx(1204)─┬─nginx(1205)
           │             └─nginx(1206)
           ├─sshd(1041)───sshd(3410)───bash(3421)───pstree(3520)
           └─systemd-journal(298)
`} />

**모든 것의 뿌리가 PID 1인 `systemd`**입니다. 그리고 여러분이 지금 명령을 치는 `bash(3421)`의 조상을 거슬러 올라가면 `sshd`를 거쳐 `systemd`에 닿습니다.

<Note type="tip" title="이 구조가 주는 실무적 의미">
Chapter 3에서 "SSH 접속이 끊기면 작업도 죽는다"고 했습니다. 이제 이유가 보입니다. 여러분의 명령은 `bash`의 자식이고, `bash`는 `sshd`의 자식입니다. **접속이 끊겨 `sshd`가 죽으면 그 아래 자식들에게 종료 신호가 내려갑니다.**

`nohup`이 하는 일은 그 신호를 무시하게 만드는 것입니다. 부모가 죽어 고아가 된 프로세스는 PID 1이 입양해서 계속 돌아갑니다.
</Note>

<Hist year="1969" title="왜 '복제'라는 이상한 방식인가">
새 프로그램을 실행할 때 처음부터 프로세스를 만드는 대신 **부모를 통째로 복제한 뒤 내용물만 갈아치우는** 것은 낯선 설계입니다. 왜 이렇게 했을까요?

초기 UNIX는 메모리가 극도로 부족했고, 시스템 콜을 단순하게 유지하는 것이 최우선이었습니다. "복제하라(fork)"와 "이 프로그램으로 바꿔라(exec)" 두 개로 나누면 각각이 아주 단순해집니다. 그리고 이 분리 덕분에 **복제한 직후 갈아입기 전 그 짧은 순간에** 자식의 환경을 조정할 수 있게 되었습니다.

Chapter 3의 리다이렉션이 정확히 그 틈에서 일어납니다. 셸은 자식을 복제하고, 갈아입기 전에 그 자식의 출력 통로를 파일로 바꿔치기한 다음, 프로그램을 실행합니다. **프로그램 자신은 자기 출력이 어디로 가는지 전혀 모릅니다.** 파이프도 같은 원리입니다.

우아함이 아니라 절박함에서 나온 설계가, 결과적으로 UNIX의 가장 강력한 특징이 되었습니다.
</Hist>

<Mini title="프로세스 계보 따라가기">
1. `echo $$` 로 지금 셸의 PID를 확인하세요.
2. `ps -f` 로 그 셸의 PPID(부모)를 확인하고, `ps -f -p 그PPID`로 부모가 무엇인지 보세요.
3. `pstree -p | head -20` 으로 전체 트리를 보고, **PID 1이 무엇인지** 확인하세요.
4. 새 터미널을 열고 `echo $$`를 실행해 PID가 다른지 확인하세요.

<Answer>
<Term code={`
$ echo $$
3421

$ ps -f -p 3421
UID    PID   PPID  C STIME TTY      TIME     CMD
student 3421  3410  0 11:02 pts/0   00:00:00 -bash

$ ps -f -p 3410
UID    PID   PPID  C STIME TTY      TIME     CMD
student 3410  1041  0 11:02 ?       00:00:00 sshd: student@pts/0
`} />

`bash(3421)` ← `sshd(3410)` ← `sshd(1041)` ← `systemd(1)`. 접속 하나가 이런 사슬로 이어져 있고, **위쪽 고리가 끊어지면 아래가 전부 딸려 갑니다.**
</Answer>
</Mini>

## 5.3 시그널 — 프로세스에 말 걸기

프로세스를 종료하는 명령 이름이 `kill`이지만, 실제로 하는 일은 **시그널을 보내는 것**입니다. 종료는 그중 하나일 뿐입니다.

| 번호 | 이름 | 뜻 | 무시 가능? |
|---|---|---|---|
| `1` | SIGHUP | 터미널 연결 끊김. **설정 다시 읽기**로도 쓰임 | 가능 |
| `2` | SIGINT | <kbd>Ctrl</kbd>+<kbd>C</kbd> | 가능 |
| `9` | SIGKILL | **즉시 강제 종료** | **불가능** |
| `15` | SIGTERM | 정중한 종료 요청 (**기본값**) | 가능 |
| `18/19` | SIGCONT/STOP | 재개 / 일시 정지 | STOP은 불가 |

<Term code={`
$ kill 3421              # 기본 SIGTERM(15) — 정리할 시간을 준다
$ kill -9 3421           # SIGKILL — 즉시 죽인다
$ kill -HUP 1204         # 설정 다시 읽기 (nginx 등)

$ pkill -f "python app.py"   # 이름/명령줄로 찾아서
$ killall nginx              # 같은 이름 전부
`} />

<Note type="danger" title="kill -9 를 먼저 쓰지 마세요">
`SIGTERM`(기본값)은 프로세스에게 **"정리하고 나가라"**고 부탁합니다. 프로그램은 이 신호를 받으면 열린 파일을 닫고, 쓰던 데이터를 디스크에 밀어넣고, 임시 파일을 지운 뒤 종료합니다.

`SIGKILL`(-9)은 커널이 프로세스를 **즉시 지워버립니다.** 프로그램은 신호를 받지도 못하므로 정리할 기회가 없습니다. 결과는 이렇습니다.

- 데이터베이스라면 **아직 디스크에 안 쓴 데이터가 사라집니다**
- 락 파일이나 PID 파일이 남아 다음 시작이 실패합니다
- 임시 파일이 쌓입니다

순서는 항상 **`kill` → 몇 초 기다림 → 그래도 안 죽으면 `kill -9`** 입니다. `-9`를 습관처럼 쓰는 것은 서버를 매번 전원 코드 뽑아 끄는 것과 같습니다.

참고로 `D` 상태(디스크 입출력 대기)인 프로세스는 **`-9`로도 죽지 않습니다.** 커널이 입출력을 끝낼 때까지 신호를 전달할 수 없기 때문입니다. 이 경우 저장소 쪽을 봐야 합니다.
</Note>

<Hist year="1970s" title="좀비와 고아 — 프로세스에도 가족 문제가 있다">
프로세스가 종료되면 곧바로 사라지지 않습니다. **종료 코드를 부모가 확인해 갈 때까지** 목록에 남습니다. 부모가 "네가 성공했는지 실패했는지" 물어볼 기회를 주기 위해서입니다.

그런데 부모가 게을러서 확인하지 않으면, 죽었는데 목록에서 안 사라지는 상태가 됩니다. 이것이 **좀비 프로세스**입니다. 메모리는 이미 회수됐고 목록의 한 줄만 남은 것이라 대개 해롭지 않지만, 부모 프로그램에 버그가 있어 수천 개가 쌓이면 프로세스 번호가 고갈됩니다.

반대 상황도 있습니다. 부모가 자식보다 먼저 죽으면 자식은 **고아**가 됩니다. 이때 PID 1이 그 자식을 **입양**해서 종료 코드를 대신 회수해 줍니다.

이름이 유난히 인간적입니다. 좀비, 고아, 입양, 부모와 자식. 초기 UNIX 개발자들의 작명 감각이 그대로 남았고, 덕분에 개념이 잘 기억됩니다. Chapter 3의 `less`나 `GNU`처럼 **농담과 비유가 시스템에 화석으로 남아 있는** 또 하나의 예입니다.
</Hist>

## 5.4 부팅 — 전원을 켜고 로그인까지

<Term code={`
# 부팅 과정 요약
전원 → BIOS/UEFI → 부트로더(GRUB) → 커널 → initramfs → systemd(PID 1) → 각 서비스 → 로그인
`} />

| 단계 | 하는 일 | 문제가 생기면 |
|---|---|---|
| **BIOS/UEFI** | 하드웨어 점검, 부팅 장치 선택 | 부팅 순서·디스크 인식 문제 |
| **GRUB** | 커널을 골라 메모리에 올림 | 커널 선택 화면, 복구 모드 진입 지점 |
| **커널** | 하드웨어 초기화, 루트 파일시스템 마운트 | `dmesg`에서 확인 |
| **initramfs** | 루트를 마운트하기 위한 임시 파일시스템 | 디스크·LVM 드라이버 누락 |
| **systemd** | 서비스를 의존성 순서대로 시작 | `systemctl` 로 확인 |

<Term code={`
# 부팅에 얼마나 걸렸나
$ systemd-analyze

   6.204s snapd.service

<Note type="tip" title="복구 모드는 여기서 들어갑니다">
설정을 잘못 건드려 부팅이 안 될 때, 부팅 중 <kbd>Shift</kbd>(또는 <kbd>Esc</kbd>)를 눌러 **GRUB 메뉴**로 들어갑니다. 거기서 이전 커널을 고르거나 복구 모드로 진입해 고칠 수 있습니다.

Chapter 1에서 "12주 동안 시스템을 두세 번은 못 쓰게 만든다"고 했죠. 그때 쓰는 것이 스냅샷이고, 스냅샷이 없는 실서버에서 쓰는 것이 이 GRUB 메뉴입니다. Chapter 10에서 **GRUB에 패스워드를 거는 이유**도 다룹니다 — 물리 접근이 가능한 사람은 이 메뉴로 root 권한을 얻을 수 있기 때문입니다.
</Note>

## 5.5 systemd — 서비스 관리자

<Compare>
  <Win>서비스 관리자(services.msc)에서 서비스를 시작·중지하고 시작 유형을 정합니다. GUI 목록이 중심입니다.</Win>
  <Lin>`systemctl` 명령 하나로 같은 일을 합니다. 서비스 정의가 **텍스트 파일**이라 버전 관리하고 서버 여러 대에 복사할 수 있습니다.</Lin>
</Compare>

<Hist year="2010s" title="systemd 는 왜 논쟁적이었나">
systemd 이전에는 **SysV init**이 서비스를 관리했습니다. 서비스마다 셸 스크립트를 하나씩 두고 순서대로 실행하는 방식이었는데, 두 가지 문제가 있었습니다. 스크립트를 **하나씩 차례로** 실행하니 부팅이 느렸고, 스크립트마다 품질이 제각각이었습니다.

systemd는 의존성을 선언하게 하고 **가능한 것은 병렬로** 시작해 부팅을 크게 단축했습니다. 대신 서비스 관리뿐 아니라 로그·네트워크·장치까지 흡수하면서 커졌고, **"하나만 잘하라"는 UNIX 철학에 어긋난다**는 강한 반발을 샀습니다. 배포판이 갈라설 만큼 큰 논쟁이었습니다.

결과적으로 주요 배포판 대부분이 systemd를 채택했습니다. 여러분이 이 논쟁의 어느 편이든, **실무에서 만나는 리눅스 서버는 systemd로 돌아갑니다.** 다만 이 배경을 알아두면 오래된 문서에서 `service`나 `/etc/init.d/` 같은 옛 방식이 나올 때 당황하지 않습니다.
</Hist>

### 기본 조작

<Term code={`
$ sudo systemctl start nginx        # 시작
$ sudo systemctl stop nginx         # 중지
$ sudo systemctl restart nginx      # 재시작
$ sudo systemctl reload nginx       # 설정만 다시 읽기 (무중단)
$ systemctl status nginx            # 상태 확인 — 가장 자주 쓴다

$ sudo systemctl enable nginx       # 부팅 시 자동 시작
$ sudo systemctl disable nginx      # 자동 시작 해제
$ sudo systemctl enable --now nginx # 활성화 + 즉시 시작

$ systemctl list-units --type=service --state=running
$ systemctl --failed                # 실패한 서비스만
`} />

<Note type="warn" title="start 와 enable 은 다릅니다">
- `start` — **지금** 시작. 재부팅하면 안 뜬다
- `enable` — **부팅할 때** 시작하도록 등록. 지금은 안 뜬다

서버를 구성하고 `start`만 한 채 잊으면, **다음 재부팅에서 서비스가 사라집니다.** 실무에서 꽤 자주 겪는 사고이고, 대개 몇 달 뒤 예기치 않은 재부팅 때 발견됩니다. 둘 다 필요하면 `enable --now`를 쓰세요.
</Note>

## 5.6 내 손으로 서비스 만들기

여기가 이번 주의 실전입니다. 스크립트를 하나 만들어 systemd 서비스로 등록해 봅니다.

### ① 스크립트

<Term code={`
$ sudo vi /usr/local/bin/disk-check.sh
`} />

```bash
#!/bin/bash
# 디스크 사용률이 임계치를 넘으면 로그에 남긴다
THRESHOLD=80
USAGE=$(df / | awk 'NR==2 {gsub("%",""); print $5}')

if [ "$USAGE" -ge "$THRESHOLD" ]; then
  echo "경고: 루트 파티션 사용률 ${USAGE}% (임계치 ${THRESHOLD}%)"
  exit 1
else
  echo "정상: 루트 파티션 사용률 ${USAGE}%"
fi
```

<Term code={`
$ sudo chmod 755 /usr/local/bin/disk-check.sh
$ /usr/local/bin/disk-check.sh
정상: 루트 파티션 사용률 50%
`} />

`chmod 755`가 Chapter 4의 그 명령입니다. 실행 권한이 없으면 서비스로 등록해도 동작하지 않습니다.

### ② 전용 계정 만들기

<Term code={`
$ sudo useradd --system --no-create-home --shell /usr/sbin/nologin diskcheck
`} />

<Note type="tip" title="왜 전용 계정인가 — 이번 주의 보안 포인트">
이 스크립트를 root로 돌려도 동작은 합니다. 그런데 **왜 굳이 계정을 따로 만들까요?**

스크립트에 취약점이 있거나, 나중에 누군가 이 스크립트를 수정할 수 있게 되면, **그 코드가 실행되는 권한이 곧 피해 범위**가 됩니다. root로 돌면 시스템 전체이고, `diskcheck` 계정으로 돌면 그 계정이 접근할 수 있는 것뿐입니다.

`--system`은 UID를 1000 미만으로 주고, `--shell /usr/sbin/nologin`은 이 계정으로 **로그인 자체를 막습니다.** Chapter 3에서 `/etc/passwd`를 훑을 때 봤던 `nologin` 계정들이 바로 이런 것들이었습니다.

Chapter 4의 최소 권한 원칙이 여기서 구체적인 명령이 됩니다.
</Note>

### ③ 서비스 유닛 파일

<Term code={`
$ sudo vi /etc/systemd/system/disk-check.service
`} />

```ini
[Unit]
Description=디스크 사용률 점검
After=network.target

[Service]
Type=oneshot
User=diskcheck
Group=diskcheck
ExecStart=/usr/local/bin/disk-check.sh

# 보안 강화 — 이 서비스가 만질 수 있는 범위를 좁힌다
NoNewPrivileges=true
PrivateTmp=true
ProtectSystem=strict
ProtectHome=true

[Install]
WantedBy=multi-user.target
```

| 항목 | 뜻 |
|---|---|
| `Type=oneshot` | 한 번 실행하고 끝나는 작업 (계속 도는 서비스는 `simple`) |
| `User` / `Group` | **어떤 권한으로 돌릴지** |
| `NoNewPrivileges` | 실행 중 권한 상승 금지 — SetUID 악용 차단 |
| `PrivateTmp` | 이 서비스만의 `/tmp` 를 준다 |
| `ProtectSystem=strict` | `/usr`, `/etc` 등을 읽기 전용으로 |
| `ProtectHome` | 사용자 홈 디렉터리 접근 차단 |
| `WantedBy` | 어느 단계에서 시작할지 |

### ④ 타이머로 주기 실행

<Term code={`
$ sudo vi /etc/systemd/system/disk-check.timer
`} />

```ini
[Unit]
Description=디스크 점검을 5분마다 실행

[Timer]
OnBootSec=2min
OnUnitActiveSec=5min
Persistent=true

[Install]
WantedBy=timers.target
```

### ⑤ 등록하고 확인

<Term code={`
$ sudo systemctl daemon-reload           # 유닛 파일을 고쳤으면 반드시
$ sudo systemctl enable --now disk-check.timer

$ systemctl list-timers disk-check.timer
NEXT                        LEFT     LAST  UNIT                ACTIVATES
Wed 2026-09-03 12:05:00 KST 3min 12s  -    disk-check.timer    disk-check.service

$ sudo systemctl start disk-check.service   # 즉시 한 번 실행해 보기
$ journalctl -u disk-check.service -n 5
Sep 03 12:00:03 ubuntu-lab disk-check.sh[4102]: 정상: 루트 파티션 사용률 50%
`} />

<Note type="warn" title="daemon-reload 를 잊지 마세요">
유닛 파일을 만들거나 고친 뒤 `daemon-reload`를 하지 않으면 **systemd는 옛 내용을 계속 씁니다.** "분명 고쳤는데 반영이 안 된다"는 문제의 대부분이 이것입니다.
</Note>

<Note type="tip" title="cron 은 어떻게 됐나">
전통적으로 주기 실행은 `cron`이 담당했고 지금도 널리 쓰입니다.

```
$ crontab -e
*/5 * * * * /usr/local/bin/disk-check.sh    # 5분마다
0 3 * * * /usr/local/bin/backup.sh          # 매일 03:00
```

다섯 자리는 순서대로 **분·시·일·월·요일**입니다. cron이 더 간단하지만, systemd 타이머는 **로그가 journal에 통합되고, 서버가 꺼져 있어 놓친 실행을 `Persistent=true`로 따라잡으며, 위에서 본 보안 옵션을 그대로 쓸 수 있습니다.** 새로 만드는 것은 타이머를, 기존 시스템은 cron을 읽을 줄 알면 됩니다.
</Note>

<Mini title="내 서비스 등록하고 로그 확인하기">
1. 위의 `disk-check.sh`를 만들고 직접 실행해 동작을 확인하세요.
2. 전용 계정 `diskcheck`를 만들고 `id diskcheck`로 UID가 1000 미만인지 확인하세요.

4. `journalctl -u disk-check.service`로 출력이 로그에 남았는지 확인하세요.
5. `sudo -u diskcheck ls /home` 을 실행해 보세요. 접근이 막히나요?

<Answer>

## 🔒 보안 포인트 · 돌아가는 것을 줄이고 좁히기

| 원칙 | 실행 방법 |
|---|---|
| **안 쓰는 서비스는 끈다** | `systemctl list-units --type=service --state=running` 으로 훑고, 모르는 것은 조사 후 `disable --now` |
| **서비스마다 전용 계정** | `useradd --system --shell /usr/sbin/nologin` |
| **유닛에 보안 옵션** | `NoNewPrivileges`, `PrivateTmp`, `ProtectSystem=strict`, `ProtectHome` |
| **root로 도는 프로세스 감시** | `ps aux | awk '$1=="root"'` 로 목록을 보고 root일 이유가 있는지 따진다 |
| **명령줄 인자에 비밀 금지** | `ps`는 누구나 본다 |
| **cron 작업의 권한 확인** | `sudo crontab -l`, `/etc/cron.d/` — 침입자가 지속성 확보에 쓰는 단골 장소 |

<Note type="warn" title="지금 확인해 볼 것">
공격자가 침입에 성공하면 **재부팅해도 살아남을 방법**을 심어둡니다. 가장 흔한 자리가 서비스와 cron입니다.

```
$ systemctl list-unit-files --state=enabled | grep -v "^systemd-"
$ sudo ls -la /etc/cron.d/ /etc/cron.daily/
$ for u in $(cut -d: -f1 /etc/passwd); do sudo crontab -l -u $u 2>/dev/null | grep -v "^#" && echo "  ↑ $u"; done
```

지금 이 목록을 저장해 두면 **기준선**이 됩니다. Chapter 4의 SetUID 목록과 같은 용도이고, Chapter 11에서 둘 다 비교합니다.
</Note>

1. **프로세스 조사** — 지금 돌고 있는 서비스 중 **root 권한으로 도는 것**을 모두 찾아 목록으로 만드세요. 각각에 대해 root여야 하는 이유를 한 줄씩 추정해 적으세요. (모르면 "조사 필요"라고 적어도 됩니다)
2. **시그널 실험** — `sleep 300`을 백그라운드로 띄우고, `SIGTERM`과 `SIGKILL`로 각각 종료해 **셸이 출력하는 메시지가 어떻게 다른지** 기록하세요. 왜 다른지 설명합니다.
3. **점검 스크립트 작성** — 다음 세 가지를 확인해 출력하는 스크립트를 `/usr/local/bin/health-check.sh`로 만드세요.
   - 루트 파티션 사용률 (80% 넘으면 경고)
   - 메모리 사용률
   - 지정한 서비스(예: `ssh`)가 살아 있는지 (`systemctl is-active`)
4. **전용 계정** — `healthcheck` 시스템 계정을 만드세요. 로그인은 불가능해야 합니다.
5. **서비스 등록** — 유닛 파일을 작성하되, 본문에 나온 **보안 옵션 네 가지를 모두 포함**하세요. `daemon-reload` 후 실행해 `journalctl`에 출력이 남는지 확인합니다.
6. **타이머 등록** — 10분마다 실행되게 하고, `systemctl list-timers`로 다음 실행 시각을 확인하세요.
7. **보안 옵션 검증** — 유닛에서 `ProtectHome=true`를 **일부러 뺀 버전**과 넣은 버전을 각각 만들어, 스크립트에 `ls /home/student` 한 줄을 추가한 뒤 결과가 어떻게 다른지 확인하세요.
8. **기준선 저장** — 현재 enabled 상태인 서비스 목록과 cron 작업 목록을 `~/baseline-w5.txt`에 저장하세요. **Chapter 11에서 씁니다.**

**제출물** — 1번 목록과 추정, 2번 메시지 비교, 스크립트와 유닛 파일 전문, 6번 타이머 출력, 7번 비교 결과.
</Lab>

<Note type="tip" title="채점 기준">
7번이 이 과제의 핵심입니다. **보안 옵션을 넣으라니까 넣은 것**과 **그 옵션이 실제로 무엇을 막는지 눈으로 확인한 것**은 다릅니다. `ProtectHome=true`일 때 `ls /home/student`가 빈 결과를 내는 것을 직접 보면, 그 한 줄이 무엇을 하는지 평생 기억합니다.

1번은 정답이 없습니다. "잘 모르겠다"고 솔직히 적는 것이 아는 척하는 것보다 낫습니다. 다만 **모르는 서비스가 root로 돌고 있다는 사실을 인지하는 것** 자체가 이 문항의 목적입니다.
</Note>

## 부록 A · Chapter 5 명령어

### 프로세스 조회

| 명령 | 하는 일 | 자주 쓰는 형태 |
|---|---|---|
| `ps` | 프로세스 목록 | `ps aux` · `ps -ef` · `ps -f -p PID` |
| `ps --sort` | 정렬 | `ps aux --sort=-%mem \| head` |
| `pstree` | 트리 구조 | `pstree -p` |
| `pgrep` | 이름으로 PID 찾기 | `pgrep -a nginx` |
| `top` / `htop` | 실시간 | `top` → `M` 메모리순 · `P` CPU순 · `q` 종료 |
| `echo $$` | 현재 셸의 PID | |

### 프로세스 제어

| 명령 | 하는 일 |
|---|---|
| `kill PID` | SIGTERM (정중한 종료) |
| `kill -9 PID` | SIGKILL (**최후 수단**) |
| `kill -HUP PID` | 설정 다시 읽기 |
| `pkill -f "패턴"` | 명령줄로 찾아 종료 |
| `killall 이름` | 같은 이름 전부 |
| `nice -n 10 명령` | 낮은 우선순위로 시작 |
| `renice -n 5 -p PID` | 우선순위 변경 |

### systemd

| 명령 | 하는 일 |
|---|---|
| `systemctl status 서비스` | 상태 + 최근 로그 |
| `systemctl start/stop/restart` | 시작/중지/재시작 |
| `systemctl reload` | 설정만 다시 읽기 (무중단) |
| `systemctl enable --now` | 부팅 자동 시작 + 즉시 시작 |
| `systemctl disable --now` | 자동 시작 해제 + 즉시 중지 |
| `systemctl --failed` | 실패한 서비스만 |
| `systemctl list-units --type=service --state=running` | 돌고 있는 서비스 |
| `systemctl list-unit-files --state=enabled` | 자동 시작 등록된 것 |
| `systemctl cat 서비스` | 유닛 파일 내용 |
| `systemctl daemon-reload` | **유닛 파일 수정 후 필수** |
| `systemctl list-timers` | 타이머 목록과 다음 실행 시각 |
| `journalctl -u 서비스` | 그 서비스의 로그 (Chapter 6에서 자세히) |

### 부팅 분석

| 명령 | 하는 일 |
|---|---|
| `systemd-analyze` | 부팅 소요 시간 |
| `systemd-analyze blame` | 서비스별 소요 시간 |
| `dmesg` | 커널 메시지 |
| `uptime` | 가동 시간과 부하 |

### 유닛 파일 뼈대

```ini
[Unit]
Description=설명
After=network.target

[Service]
Type=simple           # 계속 도는 서비스 / oneshot = 한 번 실행
User=전용계정
ExecStart=/절대/경로/실행파일
Restart=on-failure    # 죽으면 자동 재시작
NoNewPrivileges=true
PrivateTmp=true
ProtectSystem=strict
ProtectHome=true

[Install]
WantedBy=multi-user.target
```

## 부록 C · 이번 주 용어의 유래

| 이름 | 유래 |
|---|---|
| **fork** | 갈래가 나뉜다는 뜻. 프로세스가 자기를 복제해 둘로 갈라진다 |
| **exec** | execute. 복제한 껍데기에 다른 프로그램을 갈아입힌다 |
| **PID 1** | 모든 프로세스의 조상. 부모를 잃은 프로세스를 입양한다 |
| **daemon** | 배경에서 조용히 일하는 그리스 신화의 정령. 악마(demon)가 아니다. BSD 마스코트가 악마 모습인 것은 이 이름을 가지고 논 농담이다 |
| **kill** | 이름과 달리 실제로는 시그널을 보내는 명령. 종료는 그중 하나일 뿐이다 |
| **SIGHUP** | hang up. 전화선이 끊겼다는 뜻으로, 모뎀 시절 단말기 연결이 끊길 때 보내던 신호였다. 지금은 "설정 다시 읽기"로 재활용된다 |
| **nice** | 착하다. 값이 클수록 남에게 CPU를 양보한다 |
| **좀비 프로세스** | 죽었는데 부모가 아직 결과를 회수하지 않아 목록에 남은 상태 |
| **systemd** | system daemon. 끝의 d가 데몬을 뜻하므로 "시스템디"가 아니라 "시스템 디"에 가깝다 |
| **init** | initialization. systemd 이전의 PID 1이었고, 지금도 `/sbin/init`은 systemd를 가리키는 링크로 남아 있다 |
