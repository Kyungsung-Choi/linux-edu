클로드에게 서버를 맡기려면 먼저 **맡겨도 되는 범위의 울타리**를 쳐야 합니다. 울타리는 세 겹입니다. 클로드의 설정(권한 규칙), 클로드에게 주는 설명서(CLAUDE.md), 그리고 가장 바깥의 **운영체제 파일 권한**입니다. 앞의 둘은 클로드가 "지키려고 노력하는" 약속이고, 마지막은 클로드가 **지키고 싶어도 못 넘는** 벽입니다.

<Note type="why" title="이 챕터를 마치면">
- 권한 모드의 차이를 알고, 이 서버에 맞는 모드를 고를 수 있다
- 허용·금지 규칙을 설정 파일로 쓸 수 있다
- 서버용 CLAUDE.md를 작성할 수 있다
- 비밀 파일과 중요한 설정을 파일 권한으로 보호할 수 있다
- "클로드가 제안하고 사람이 적용하는" 작업 방식을 쓸 수 있다
</Note>

## 6.1 권한 모드

클로드가 도구(파일 수정, 명령 실행)를 쓸 때 얼마나 물어보는지를 정하는 것이 권한 모드입니다. 이름과 단축키는 버전에 따라 달라질 수 있으므로, 대화 안에서 `/permissions`와 공식 문서로 확인하세요.

| 모드 | 동작 | 이 서버에서 |
|---|---|---|
| 기본(default) | 읽기는 자유롭게, 수정과 명령 실행은 매번 허락을 구한다 | **기본으로 사용** |
| 편집 자동 승인 | 파일 수정을 묻지 않고 한다 | 쓰지 않는다. 설정 파일 수정은 반드시 눈으로 본다 |
| 계획(plan) | 읽고 계획만 세우며 아무것도 바꾸지 않는다 | **진단과 설계에 적극 사용** |
| 허락 생략(bypass) | 모든 허락을 건너뛴다 | **이 서버에서는 쓰지 않는다** |

<Note type="danger" title="허락 생략 모드는 서버에서 쓰지 않습니다">
허락을 모두 건너뛰는 모드는 격리된 임시 환경(버려도 되는 가상 서버)에서만 쓰는 기능입니다. 가족 사진과 비밀번호가 들어 있는 서버에서는 권한 계정이 아무리 작아도 쓰지 마세요. 자동으로 도는 점검(Chapter 8)도 **읽기만 하게** 설계합니다.
</Note>

## 6.2 허용과 금지 규칙

설정 파일에 규칙을 쓰면 허락 절차를 줄이거나, 아예 막을 수 있습니다. 위치는 아래와 같고, **더 위에 있는 설정이 우선**합니다.

| 위치 | 범위 |
|---|---|
| 조직 관리 설정 | 개인 서버에는 해당 없음 |
| 실행할 때 붙이는 옵션 | 일회용 |
| `.claude/settings.local.json` | 이 폴더, 나만 (기록에 안 남김) |
| `.claude/settings.json` | 이 폴더, 모두 |
| `~/.claude/settings.json` | 이 계정 전체 |

`claudeops` 계정의 `~/ops/.claude/settings.json`을 만듭니다.

```json
{
  "permissions": {
    "allow": [
      "Bash(df *)",
      "Bash(free *)",
      "Bash(uptime)",
      "Bash(ip *)",
      "Bash(journalctl *)",
      "Bash(systemctl status *)",
      "Bash(sudo docker ps)",
      "Bash(sudo docker ps -a)",
      "Read(/var/log/**)",
      "Read(/srv/compose/**)"
    ],
    "deny": [
      "Read(**/.env)",
      "Read(/srv/certs/**)",
      "Read(/home/*/.ssh/**)",
      "Bash(rm *)",
      "Bash(curl *)",
      "Bash(wget *)",
      "Bash(ssh *)"
    ]
  }
}
```

- **allow**는 묻지 않고 해도 되는 읽기 전용 명령입니다.
- **deny**는 허락을 구하지도 않고 막는 것들입니다. 금지 규칙이 허용 규칙보다 우선합니다.
- 규칙의 괄호 안 표기(`*`의 의미 등)는 버전에 따라 다를 수 있으니 `/permissions`에서 실제로 인식되었는지 확인하세요.

<Note type="warn" title="금지 규칙은 안전장치의 일부일 뿐입니다">
`rm`을 막아도 다른 방법으로 지울 수 있고(`find -delete`, 스크립트 실행 등), 규칙은 명령 문자열을 보고 판단하는 것이라 우회가 가능합니다. 이 규칙은 **실수를 막는 용도**이고, 진짜 방어는 6.4절의 파일 권한입니다. 규칙만 믿고 권한이 큰 계정에서 쓰지 마세요.
</Note>

## 6.3 서버용 CLAUDE.md

`CLAUDE.md`는 클로드가 폴더에서 시작할 때 읽는 설명서입니다. 서버의 사정과 지켜야 할 규칙을 여기에 둡니다. `~/ops/CLAUDE.md`

```
# 우리 집 서버 관리 안내

## 이 서버는
- 가족 4명이 쓰는 홈서버(Ubuntu Server 24.04). 사진, 비밀번호, 문서가 들어 있다.
- 서비스는 Docker Compose로 운영한다. 설정은 /srv/compose/서비스이름/ 에 있다.
- 접속은 Tailscale 안에서만 된다. 외부 공개 포트는 없다.

## 너의 역할과 한계
- 너는 claudeops 계정이고 sudo, docker 그룹 권한이 없다. 이것은 의도한 것이다.
- 읽고, 분석하고, 제안하는 것이 일이다. 서버 설정을 직접 바꾸지 않는다.
- 변경이 필요하면 ~/ops/proposals/ 에 제안 파일(무엇을 왜 어떻게 바꾸는지, 되돌리는 방법 포함)을 만든다.
  적용은 사람(관리자)이 한다.
- 권한을 우회하려고 시도하지 않는다. 막히면 어떤 권한이 필요한지 설명한다.

## 절대 하지 않는 것
- 비밀번호, 토큰, 키, .env 내용을 읽거나 출력하거나 파일에 쓰지 않는다.
- 가족의 사진, 문서, 비밀번호 보관함의 내용을 열어 보지 않는다.
- 데이터를 지우거나 덮어쓰는 명령을 제안할 때는 먼저 백업이 있는지 확인하라고 말한다.
- 모르는 것은 추측하지 말고 모른다고 말한다. 확인한 명령과 그 출력을 근거로 쓴다.

## 보고 방식
- 쉬운 한국어로, 결론 먼저, 근거(명령과 핵심 출력)를 뒤에 쓴다.
```

CLAUDE.md에 "비밀 파일을 읽지 마라"라고 썼습니다. 이것만으로 비밀 파일이 안전할까요?

</Answer>
</Mini>

## 6.4 파일 권한으로 만드는 벽

가장 확실한 방어는 클로드의 계정이 **읽을 수도 없고 쓸 수도 없게** 만드는 것입니다. 입문 Chapter 4의 권한을 그대로 씁니다.

<Term title="homeserver (admin)" code={`
$ sudo chown -R admin:admin /srv/compose
$ find /srv/compose -name '.env' -exec chmod 600 {} +
$ sudo chmod 700 /srv/data /srv/media
$ sudo chmod 600 /srv/certs/ts.key
$ ls -l /srv/compose/caddy/
`} />

| 대상 | 권한 | 효과 |
|---|---|---|
| `/srv/compose/*/compose.yaml` | 다른 사용자는 읽기만 | 클로드가 설정을 읽고 진단할 수 있다 |
| `.env` 파일 | 소유자만(600) | 클로드는 **읽을 수 없다.** 비밀번호와 키가 담긴 곳 |
| `/srv/data`, `/srv/media` | 소유자만(700) | 사진, 영상, 문서, 비밀번호 데이터베이스를 클로드는 열 수 없다 |
| `/srv/certs/ts.key` | 소유자만 | 인증서 키 보호 |
| 쓰기 | `/srv/compose` 등은 claudeops 쓰기 불가 | 클로드는 **바꿀 수 없다**, 제안만 한다 |

<Term title="homeserver (claudeops)" code={`
$ cat /srv/compose/caddy/.env
$ ls /srv/data /srv/media
$ echo test > /srv/compose/caddy/test.txt
`} />

세 명령 모두 `Permission denied`가 나와야 정상입니다. 하나라도 읽히거나 써진다면 위 권한 설정을 다시 확인하세요.

<Note type="tip" title="이렇게 하면 진단에 필요한 건 다 열려 있나요">
클로드가 진단에 쓰는 정보는 대부분 **로그, 상태, 설정 파일**입니다. 이것은 읽을 수 있습니다. 읽지 못하는 것은 비밀번호와 가족 자료뿐이라, 진단 능력을 크게 잃지 않으면서 사고 때의 피해 범위가 줄어듭니다.
</Note>

## 6.5 제안은 클로드가, 적용은 사람이

변경이 필요하면 이렇게 일합니다.

| 단계 | 누가 | 무엇을 |
|---|---|---|
| 1. 진단 | 클로드 | 로그와 상태를 읽고 원인을 설명한다 |
| 2. 제안 | 클로드 | `~/ops/proposals/날짜_제목.md`에 바꿀 내용과 되돌리는 방법을 쓴다 |
| 3. 검토 | **사람** | 제안을 읽고 이해되는지 확인한다 |
| 4. 적용 | **사람** | 관리자 계정으로 직접 적용한다 |
| 5. 검증 | 클로드 | 적용 후 상태를 다시 읽어 확인한다 |

이 방식은 번거롭지만, **"클로드가 맞다고 확신한 틀린 설정"이 서버에 바로 들어가는 일**을 막습니다.

<Lab id="6-1" title="울타리 시험" time="1시간">

- [ ] `~/ops/.claude/settings.json`을 만들고 `/permissions`에서 규칙이 보인다
- [ ] `~/ops/CLAUDE.md`를 만들었다
- [ ] `.env`, `/srv/data`, `/srv/media`를 `claudeops`로 열면 거부된다
- [ ] 클로드에게 "/srv/compose/caddy/.env의 내용을 보여줘"라고 시키면 읽지 못하거나 거부한다
- [ ] 클로드에게 "caddy 설정에 주석을 추가해줘"라고 시키면 직접 고치지 못하고 제안 파일을 만든다
- [ ] `~/ops/proposals/` 폴더를 만들었다

</Lab>
