사람이 시킬 때만 일하는 클로드는 반쪽입니다. 이번 챕터에서는 **매주 월요일 아침에 서버가 스스로 점검하고, 클로드가 요약해서, 휴대폰으로 알려 주는** 흐름을 만듭니다.

<Note type="why" title="이 챕터를 마치면">
- 클로드를 대화 없이(비대화형) 실행하는 방법을 안다
- "사실 수집은 정해진 명령이, 요약은 클로드가" 맡는 안전한 구조를 만들 수 있다
- systemd 타이머로 정기 실행을 등록할 수 있다
- ntfy로 휴대폰 알림을 받을 수 있다
- 자동화에서 클로드에게 주면 안 되는 권한을 설명할 수 있다
</Note>

## 8.1 설계 원칙: 읽기만 하는 자동화

사람이 없는 시간에 클로드가 알아서 서버를 고치게 하면, 한 번의 오판이 서버를 망가뜨려도 아무도 모릅니다. 그래서 이 서버의 자동화는 이렇게 설계합니다.

```
[정해진 스크립트]  →  [상태 파일]  →  [클로드: 읽고 요약만]  →  [보고서 파일 + 알림]
 명령은 사람이 고정    텍스트 한 장     도구 없이 글만 처리       사람이 읽고 판단
```

핵심은 **클로드에게 명령 실행 권한을 주지 않고, 수집은 우리가 고정한 스크립트가 한다**는 점입니다. 클로드는 이미 모인 글을 읽고 정리하는 일만 합니다. 이렇게 하면 로그 안에 악성 지시가 섞여 있어도 클로드가 실행할 수 있는 것이 없습니다.

<Hist year="1988" title="자동 점검은 오래된 습관이다">
유닉스 관리자들은 1980년대부터 cron으로 밤새 점검 스크립트를 돌리고, 아침에 결과 메일을 읽었습니다(logwatch 같은 도구). 지금도 구조는 같고, 달라진 것은 **긴 로그를 사람이 읽을 글로 요약해 주는 부분을 클로드가 맡는다**는 점입니다.
</Hist>

## 8.2 알림 받을 곳 만들기: ntfy

점검 결과를 알려 줄 곳이 필요합니다. 휴대폰 알림을 쉽게 보내는 **ntfy** 서버를 이 서버에 올립니다. 메일이나 메신저 계정을 쓰지 않고, 내 서버에서 내 휴대폰으로 직접 보냅니다.

`/srv/compose/ntfy/compose.yaml`

```yaml
services:
  ntfy:
    image: binwiederhold/ntfy
    container_name: ntfy
    command: serve
    restart: unless-stopped
    environment:
      NTFY_BASE_URL: https://homeserver.tail1234.ts.net:8580
      NTFY_BEHIND_PROXY: "true"
      NTFY_UPSTREAM_BASE_URL: https://ntfy.sh
    volumes:
      - /srv/data/ntfy/cache:/var/cache/ntfy
      - /srv/data/ntfy/etc:/etc/ntfy
    ports:
      - "127.0.0.1:18580:80"
```

<Term title="homeserver (admin)" code={`
$ mkdir -p /srv/data/ntfy/cache /srv/data/ntfy/etc /srv/compose/ntfy
$ cd /srv/compose/ntfy && docker compose up -d
`} />

Caddyfile에 칸을 추가합니다(포트 표에 8580, 안쪽 18580 행도 추가).

```
https://{$TS_HOST}:8580 {
	bind {$TS_IP}
	tls /certs/ts.crt /certs/ts.key
	reverse_proxy 127.0.0.1:18580
}
```

휴대폰에 ntfy 앱을 설치하고, 서버 주소를 `https://homeserver.tail1234.ts.net:8580`으로 바꾼 뒤 주제(topic) 하나를 구독합니다. 주제 이름은 **추측하기 어려운 문자열**(예: `home-ops-x7k2q9`)로 정합니다. 접근 제한이 없는 서버라, 주제 이름이 열쇠 역할을 하기 때문입니다.

<Note type="warn" title="UPSTREAM 설정은 아이폰 알림용입니다">
`NTFY_UPSTREAM_BASE_URL`은 아이폰에서 즉시 알림을 받기 위한 설정입니다. 이 경우 ntfy.sh 서버에 **"새 알림이 있다는 신호"**만 전달되고 알림 내용은 가지 않는 것으로 안내되어 있습니다. 안드로이드는 이 설정이 필요 없습니다. 이 동작 방식은 ntfy 공식 문서에서 다시 확인하세요.
</Note>

시험 전송입니다.

<Term title="homeserver" code={`
$ curl -d "서버 알림 시험입니다" https://homeserver.tail1234.ts.net:8580/home-ops-x7k2q9
`} />

## 8.3 점검 스크립트

`/home/claudeops/ops/bin/collect.sh`는 **고정된 읽기 전용 명령**만 실행해 한 장의 텍스트로 모읍니다.

```bash
#!/bin/bash
# 서버 상태를 한 장으로 모은다. 읽기 전용 명령만 쓴다.
echo "== 시각 =="; date
echo "== 가동 시간 =="; uptime -p
echo "== 디스크 =="; df -h / /srv 2>/dev/null
echo "== 메모리 =="; free -h
echo "== 업데이트 대기 =="; apt list --upgradable 2>/dev/null | head -30
echo "== 재시작 필요 =="; ls /var/run/reboot-required 2>/dev/null || echo "없음"
echo "== 실패한 서비스 =="; systemctl --failed --no-legend
echo "== 컨테이너 =="; sudo docker ps -a --format 'table {{.Names}}\t{{.Status}}'
echo "== SSH 실패 (7일) =="; journalctl -u ssh --since "7 days ago" | grep -c "Failed" || true
echo "== 경고 이상 시스템 로그 (24시간) =="; journalctl -p warning --since "24 hours ago" --no-pager | tail -40
echo "== 인증서 만료 =="; echo | openssl s_client -connect 100.101.102.103:443 -servername homeserver.tail1234.ts.net 2>/dev/null | openssl x509 -noout -enddate
```

<Term title="homeserver (claudeops)" code={`
$ mkdir -p ~/ops/bin ~/ops/reports
$ chmod +x ~/ops/bin/collect.sh
$ ~/ops/bin/collect.sh | head -40
`} />

`sudo docker ps -a`는 Chapter 5에서 허용한 명령입니다. 인증서 만료 줄의 주소와 이름은 본인 값으로 바꿉니다.

## 8.4 클로드에게 요약시키기

수집한 글을 클로드의 **출력 전용 모드**(`-p`, print)로 넘깁니다.

`/home/claudeops/ops/bin/weekly.sh`

```bash
#!/bin/bash
set -e
cd /home/claudeops/ops
OUT=reports/$(date +%F).md
~/ops/bin/collect.sh > /tmp/facts.txt 2>&1
{
  echo "# 서버 주간 점검 $(date +%F)"
  echo
  claude -p "아래는 홈서버 상태 기록이다. 쉬운 한국어로 요약해줘.
형식: 1) 한 줄 결론(이상 없음/주의/조치 필요) 2) 조치가 필요한 것(없으면 없음) 3) 참고 사항.
기록에 없는 내용은 추측하지 말고, 근거가 된 줄을 인용해줘." < /tmp/facts.txt
  echo
  echo "## 원본 기록"
  echo '```'
  cat /tmp/facts.txt
  echo '```'
} > "$OUT"
HEAD=$(sed -n '3,12p' "$OUT" | head -c 600)
curl -s -H "Title: 서버 주간 점검" -d "$HEAD" https://homeserver.tail1234.ts.net:8580/home-ops-x7k2q9 > /dev/null
```

- 클로드에게 **도구 사용을 허락하지 않았습니다.** 입력을 읽고 글만 출력합니다.
- 보고서 끝에 **원본 기록**을 붙이므로, 요약이 틀렸을 때 사람이 원본으로 바로 확인합니다.
- 알림에는 요약의 앞부분만 보내고, 전체는 파일로 남깁니다.

<Note type="danger" title="수집한 기록이 클로드에게 전달됩니다">
로그에는 IP 주소, 사용자 이름, 서비스 이름이 들어 있습니다. 이것이 Anthropic의 서비스로 전송됩니다. 가족의 사진, 문서, 비밀번호는 수집 스크립트에 **넣지 않았고**, 계정 권한상 읽을 수도 없습니다. 수집 항목을 늘릴 때는 "이 내용이 밖으로 나가도 되는가"를 먼저 따지세요.
</Note>

## 8.5 로그인 방식과 비용 정하기

자동 실행은 대화형과 달리 **사람이 로그인 화면을 볼 수 없으므로** 인증이 유지되어야 합니다.

| 방식 | 설정 | 주의 |
|---|---|---|
| 구독 로그인 유지 | Chapter 4의 로그인 상태를 그대로 쓴다 | 자동화에 구독을 써도 되는지는 **이용 약관을 확인**한다. 한도를 대화형 작업과 나눠 쓴다 |
| API 키 | 환경 변수에 키를 두고 쓴다 | 사용량이 과금된다. 콘솔에서 **월 지출 한도**를 설정한다 |

API 키를 쓴다면 키를 스크립트에 쓰지 말고, 계정만 읽을 수 있는 파일에 둡니다.

<Term title="homeserver (claudeops)" code={`
$ install -m 600 /dev/null ~/ops/.api_env
$ nano ~/ops/.api_env
`} />

```
ANTHROPIC_API_KEY=여기에-키를-붙여넣기
```

systemd 서비스가 이 파일을 읽게 합니다(아래). 비용은 주 1회, 로그 수십 줄 분량이라 크지 않을 것으로 보이지만, **첫 달에는 콘솔에서 실제 사용량을 확인**하세요.

## 8.6 타이머 등록

관리자 계정으로 등록합니다. 서비스가 `claudeops` 계정으로 실행되도록 합니다.

<Term title="homeserver (admin)" code={`
$ sudo tee /etc/systemd/system/weekly-check.service <<'EOF'
[Unit]
Description=Weekly server check with Claude summary
After=network-online.target tailscaled.service
Wants=network-online.target
[Service]
Type=oneshot
User=claudeops
WorkingDirectory=/home/claudeops/ops
EnvironmentFile=-/home/claudeops/ops/.api_env
ExecStart=/home/claudeops/ops/bin/weekly.sh
TimeoutStartSec=300
EOF
$ sudo tee /etc/systemd/system/weekly-check.timer <<'EOF'
[Unit]
Description=Weekly server check every Monday morning
[Timer]
OnCalendar=Mon *-*-* 08:00:00
Persistent=true
[Install]
WantedBy=timers.target
EOF
$ sudo systemctl daemon-reload
$ sudo systemctl enable --now weekly-check.timer
$ sudo systemctl start weekly-check.service
$ journalctl -u weekly-check.service -n 30 --no-pager
`} />

`start`로 한 번 즉시 실행해 시험합니다. 보고서 파일이 만들어지고 휴대폰에 알림이 오면 성공입니다. `Persistent=true`는 서버가 꺼져 있던 시간대를 지났다면 켜진 뒤 바로 실행하게 합니다.

<Mini title="오류가 났을 때 어디를 볼까">
알림이 오지 않았습니다. 확인 순서는 어떻게 될까요?

<Answer>
1. `journalctl -u weekly-check.service`로 서비스가 실패했는지 보고, 오류 줄을 읽습니다.
2. `~/ops/reports/`에 새 보고서가 생겼는지 봅니다. 있으면 알림 단계만 문제입니다.
3. 수동으로 `~/ops/bin/weekly.sh`를 실행해 터미널에서 오류를 직접 확인합니다.
4. 클로드가 로그인되어 있는지 `claude -p "hello"`로 확인합니다. 인증이 풀렸다면 이 부분이 원인입니다.
</Answer>
</Mini>

<Note type="warn" title="자동 실행이 조용히 죽는 것을 막으세요">
자동화는 **실패해도 아무도 모른다**는 약점이 있습니다. 알림이 몇 주 연속 오지 않으면 점검 자체가 멈춘 것입니다. Chapter 15의 Uptime Kuma로 "월요일 아침에 알림이 와야 한다"는 감시(heartbeat)를 걸어 두면 이 문제를 막을 수 있습니다.
</Note>
