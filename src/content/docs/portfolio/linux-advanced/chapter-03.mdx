서비스를 올릴 때마다 방식이 다르면 석 달 뒤에는 아무도 기억하지 못합니다. 이번 챕터에서 **모든 서비스를 똑같은 방식으로 올리는 틀**을 만들어 둡니다. 이후 챕터는 이 틀에 한 칸씩 채우는 일입니다.

<Note type="why" title="이 챕터를 마치면">
- Docker Engine과 Compose를 공식 방법으로 설치할 수 있다
- 서비스마다 같은 폴더 구조와 같은 포트 규칙을 쓸 수 있다
- 서비스에 HTTPS를 붙이되, **tailnet 안에서만 열리게** 만들 수 있다
- 가족이 처음 열어 볼 안내 페이지를 만들 수 있다
- 서비스 업데이트와 재부팅 뒤 자동 시작을 설명할 수 있다
</Note>

## 3.1 Docker 설치

입문 Chapter 9에서 컨테이너를 배웠습니다. 서버에는 Ubuntu 기본 저장소의 `docker.io`가 아니라 **Docker 공식 저장소**의 Docker Engine을 씁니다. 기본 저장소 판은 버전이 오래되고 Compose 플러그인이 빠져 있는 경우가 많습니다.

공식 순서는 (1) 저장소와 서명키를 등록하고 (2) 패키지를 설치하는 것입니다. 명령은 Docker 공식 문서 「Install Docker Engine on Ubuntu」의 **apt 저장소로 설치** 항목을 그대로 따르세요. 문서가 갱신되므로 이 책에 명령을 옮겨 적지 않습니다. 설치되는 패키지는 아래 5개입니다.

| 패키지 | 역할 |
|---|---|
| `docker-ce` | Docker 엔진 |
| `docker-ce-cli` | `docker` 명령 |
| `containerd.io` | 컨테이너 실행기 |
| `docker-buildx-plugin` | 이미지 빌드 도구 |
| `docker-compose-plugin` | `docker compose` 명령 |

설치 뒤 확인합니다.

<Term title="homeserver" code={`
$ sudo docker run --rm hello-world
$ docker compose version
`} />

<Note type="danger" title="docker 그룹은 사실상 root입니다">
`docker` 그룹에 사용자를 넣으면 sudo 없이 docker를 쓸 수 있어 편하지만, 그 사용자는 컨테이너로 호스트의 모든 파일을 읽고 쓸 수 있으므로 **root와 같다**고 생각해야 합니다. 이 과정에서는 관리자 본인 계정만 docker 그룹에 넣고, 가족 계정과 Chapter 5의 클로드 작업 계정은 넣지 않습니다.

<Term code={`
$ sudo usermod -aG docker $USER
`} />

적용하려면 로그아웃했다가 다시 접속합니다.
</Note>

## 3.2 폴더와 이름 규칙

서비스가 10개가 되어도 한눈에 보이도록 규칙을 정합니다.

| 위치 | 용도 |
|---|---|
| `/srv/compose/서비스이름/compose.yaml` | 서비스 설정 (이 폴더 전체를 백업 대상으로) |
| `/srv/data/서비스이름/` | 서비스가 쓰는 자료 (설정, 데이터베이스) |
| `/srv/media/` | 사진·영상 같은 큰 자료. 나중에 별도 디스크를 붙일 자리 |
| `/srv/certs/` | HTTPS 인증서 |
| `/srv/backups/` | 백업 보관 (Chapter 17) |

<Term title="homeserver" code={`
$ sudo mkdir -p /srv/compose /srv/data /srv/media /srv/certs /srv/backups
$ sudo chown $USER:$USER /srv/compose /srv/data /srv/media
`} />

서비스를 올리는 모습은 항상 같습니다.

<Term title="homeserver" code={`
$ cd /srv/compose/서비스이름
$ docker compose up -d
$ docker compose ps
$ docker compose logs --tail 50
`} />

## 3.3 포트 배치표

각 서비스는 자기 화면 포트를 갖고, **서버 안(127.0.0.1)에만 열리게** 합니다. 바깥 문은 Caddy 하나만 갖습니다.

| 서비스 | 가족이 여는 주소의 포트 (HTTPS) | 서비스가 서버 안에서 쓰는 포트 | 챕터 |
|---|---|---|---|
| 가족 안내 페이지 | 443 | Caddy가 직접 제공 | 3 |
| Immich | 2283 | 127.0.0.1:12283 | 10 |
| Jellyfin | 8096 | 127.0.0.1:18096 | 11 |
| Vaultwarden | 8222 | 127.0.0.1:18222 | 12 |
| AdGuard Home 관리 화면 | 3000 | 127.0.0.1:13000 | 13 |
| Home Assistant | 8123 | 127.0.0.1:18123 | 14 |
| Uptime Kuma | 3001 | 127.0.0.1:13001 | 15 |
| Gitea | 3002 | 127.0.0.1:13002 | 15 |
| Paperless-ngx | 8000 | 127.0.0.1:18000 | 16 |

규칙은 하나입니다. **바깥 포트 N, 안쪽 포트 1N**(앞에 1을 붙임). 포트 번호가 겹치면 서비스가 시작하지 않으므로, 서버 노트에 이 표를 그대로 붙여 두세요. Chapter 2의 접근 규칙에 적은 포트 목록이 이 표의 왼쪽 열과 같습니다.

<Hist year="2015" title="왜 서비스 앞에 문지기를 따로 두나">
서비스마다 자기가 직접 HTTPS와 로그인을 처리하게 하면, 서비스가 10개일 때 인증서 설정도 10번, 보안 점검도 10번입니다. 그래서 서버 업계는 서비스 앞에 **리버스 프록시**라는 문지기를 하나 세우고, 문지기가 인증서와 접속을 맡고 안쪽 서비스에는 전달만 하는 구조를 표준으로 삼았습니다. 이 과정의 문지기는 설정이 짧은 Caddy입니다.
</Hist>

## 3.4 tailnet 안에서만 쓰는 HTTPS

### 왜 HTTPS가 필요한가

집 안에서 쓰는 서비스라도 HTTPS가 필요한 경우가 있습니다. 대표적으로 **Vaultwarden은 HTTPS가 아니면 웹 화면과 앱이 동작하지 않습니다.** 브라우저가 암호 기능을 HTTPS에서만 열어 주기 때문입니다. 사진 앱과 스마트홈 앱도 HTTPS 주소를 선호합니다.

Tailscale은 tailnet 이름(`호스트이름.tailnet이름.ts.net`)에 대한 **정식 HTTPS 인증서**를 무료로 발급해 줍니다. 이 인증서를 Caddy에게 주면, 가족 기기에 따로 인증서를 설치하지 않아도 자물쇠가 정상으로 뜹니다.

### 사전 설정

1. Tailscale 관리 콘솔의 DNS 화면에서 **MagicDNS**와 **HTTPS Certificates**를 켭니다.
2. 서버에서 자기 전체 이름을 확인합니다.

<Term title="homeserver" code={`
$ tailscale status --json | grep -m1 DNSName
        "DNSName": "homeserver.tail1234.ts.net.",
`} />

이 책에서는 `homeserver.tail1234.ts.net`을 예시 이름으로 씁니다. **본인의 이름으로 바꿔 쓰세요.**

<Note type="warn" title="인증서에 서버 이름이 공개됩니다">
정식 인증서는 인증서 투명성 기록이라는 공개 목록에 올라갑니다. 즉 `homeserver.tail1234.ts.net`이라는 **이름이 인터넷에 공개 기록**으로 남습니다. 서비스 내용이나 접속 권한이 공개되는 것은 아니지만, 서버 이름에 가족 이름이나 주소 같은 개인정보를 넣지 마세요.
</Note>

### 인증서 받기

<Term title="homeserver" code={`
$ sudo tailscale cert --cert-file /srv/certs/ts.crt --key-file /srv/certs/ts.key homeserver.tail1234.ts.net
$ sudo chmod 600 /srv/certs/ts.key
$ ls -l /srv/certs
`} />

### Caddy 올리기

`/srv/compose/caddy/` 폴더를 만들고 파일 2개를 둡니다.

`/srv/compose/caddy/compose.yaml`

```yaml
services:
  caddy:
    image: caddy:2
    container_name: caddy
    restart: unless-stopped
    network_mode: host
    env_file: .env
    volumes:
      - ./Caddyfile:/etc/caddy/Caddyfile:ro
      - /srv/certs:/certs:ro
      - /srv/compose/caddy/site:/srv/site:ro
      - caddy_data:/data
volumes:
  caddy_data:
```

`/srv/compose/caddy/.env`

```
TS_HOST=homeserver.tail1234.ts.net
TS_IP=100.101.102.103
```

`TS_IP`는 `tailscale ip -4`가 알려 준 서버의 tailnet 주소입니다.

`/srv/compose/caddy/Caddyfile`

```
{
	auto_https off
}

# 가족 안내 페이지
https://{$TS_HOST} {
	bind {$TS_IP}
	tls /certs/ts.crt /certs/ts.key
	root * /srv/site
	file_server
}
```

핵심은 두 줄입니다.

- `bind {$TS_IP}`: Caddy는 **tailnet 주소로만** 문을 엽니다. 공유기 쪽(집 안 LAN)이나 인터넷에서는 이 문이 보이지 않습니다.
- `auto_https off`: Caddy가 스스로 인증서를 받으려 하지 않게 하고, 우리가 준 Tailscale 인증서만 씁니다.

서비스를 추가할 때는 이 파일에 칸을 하나씩 더합니다(아래는 Chapter 10에서 쓸 예시입니다).

```
https://{$TS_HOST}:2283 {
	bind {$TS_IP}
	tls /certs/ts.crt /certs/ts.key
	reverse_proxy 127.0.0.1:12283
}
```

### 가족 안내 페이지 만들기

<Term title="homeserver" code={`
$ mkdir -p /srv/compose/caddy/site
$ cat > /srv/compose/caddy/site/index.html <<'EOF'
<!doctype html>
<meta charset="utf-8">
<meta name="viewport" content="width=device-width,initial-scale=1">
<title>우리 집 서버</title>
<h1>우리 집 서버</h1>
<p>Tailscale 앱이 켜져 있어야 열립니다.</p>
<ul>
  <li>준비 중입니다. 서비스가 추가되면 여기에 링크가 생깁니다.</li>
</ul>
EOF
$ cd /srv/compose/caddy && docker compose up -d
`} />

가족 기기에서 `https://homeserver.tail1234.ts.net`을 열어 안내 페이지가 자물쇠와 함께 보이는지 확인합니다. 서비스가 하나씩 늘 때마다 이 페이지에 링크를 추가합니다.

## 3.5 인증서 갱신과 재부팅

Tailscale 인증서는 약 90일마다 만료됩니다. 갱신을 자동화합니다.

`/usr/local/bin/ts-cert-renew.sh`

```bash
#!/bin/sh
set -e
tailscale cert --cert-file /srv/certs/ts.crt --key-file /srv/certs/ts.key homeserver.tail1234.ts.net
chmod 600 /srv/certs/ts.key
docker exec caddy caddy reload --config /etc/caddy/Caddyfile
```

<Term title="homeserver" code={`
$ sudo chmod +x /usr/local/bin/ts-cert-renew.sh
$ sudo tee /etc/systemd/system/ts-cert-renew.service <<'EOF'
[Unit]
Description=Renew Tailscale certificate
[Service]
Type=oneshot
ExecStart=/usr/local/bin/ts-cert-renew.sh
EOF
$ sudo tee /etc/systemd/system/ts-cert-renew.timer <<'EOF'
[Unit]
Description=Weekly Tailscale certificate renewal
[Timer]
OnCalendar=weekly
Persistent=true
[Install]
WantedBy=timers.target
EOF
$ sudo systemctl daemon-reload
$ sudo systemctl enable --now ts-cert-renew.timer
$ systemctl list-timers ts-cert-renew.timer
`} />

`tailscale cert`는 인증서가 아직 충분히 남았으면 새로 받지 않으므로, 주 1회 실행해도 문제없습니다. 입문 Chapter 5에서 배운 systemd 타이머를 그대로 쓴 것입니다.

재부팅 뒤 Docker가 Caddy보다 먼저 일어나고 Tailscale이 늦으면, Caddy가 tailnet 주소에 문을 열지 못합니다. Docker가 Tailscale 뒤에 시작하게 순서를 정해 둡니다.

<Term title="homeserver" code={`
$ sudo systemctl edit docker.service
`} />

열린 편집기에 아래 두 줄을 넣고 저장합니다.

```
[Unit]
After=tailscaled.service
```

`restart: unless-stopped`로 컨테이너가 재부팅 뒤 자동으로 돌아옵니다.

## 3.6 업데이트하는 법

서비스는 이미지 새 버전이 나오면 갈아 끼웁니다.

<Term title="homeserver" code={`
$ cd /srv/compose/서비스이름
$ docker compose pull
$ docker compose up -d
$ docker image prune -f
`} />

| 서비스 종류 | 업데이트 습관 |
|---|---|
| 비밀번호(Vaultwarden), 사진(Immich) | **업데이트 전에 백업.** 릴리스 노트의 주의 사항을 먼저 읽는다 |
| 나머지 | 한 달에 한 번 몰아서 |

<Note type="warn" title="자동으로 업데이트하는 도구는 쓰지 않습니다">
Watchtower 같은 자동 업데이트 도구는 편하지만, 사진 앱이나 데이터베이스가 **주의 사항을 읽지 않은 채 업데이트되어** 망가지는 사례가 있습니다. 서버가 가족 사진을 담고 있다면 업데이트는 사람이 하는 일로 두세요. 이 업데이트 점검을 Chapter 8에서 클로드가 알려 주게 만듭니다.
</Note>

<Mini title="포트 번호 정하기">
Immich는 바깥(가족이 여는 주소)에서 2283, 서버 안에서 12283을 씁니다. Gitea를 올릴 때 가족이 여는 주소의 포트가 3002라면, 서버 안 포트와 Caddyfile의 `reverse_proxy` 줄은 어떻게 쓰면 될까요?

<Answer>
서버 안 포트는 `13002`이고, Caddyfile의 칸은 `https://{$TS_HOST}:3002 { bind {$TS_IP}  tls ...  reverse_proxy 127.0.0.1:13002 }`입니다. Gitea의 compose에서는 `ports: "127.0.0.1:13002:3000"`처럼 **127.0.0.1을 붙여** 서버 밖으로 열리지 않게 합니다. 가족 접근 규칙(Chapter 2)에 3002를 더하는 것도 잊지 마세요.
</Answer>
</Mini>

<Lab id="3-1" title="운영 틀 완성" time="1시간 30분">

- [ ] `docker run --rm hello-world`와 `docker compose version`이 된다
- [ ] `/srv` 아래 폴더를 규칙대로 만들었다
- [ ] Tailscale 인증서를 받았고 Caddy가 안내 페이지를 HTTPS로 보여 준다
- [ ] 휴대폰(LTE)에서 안내 페이지 주소에 자물쇠가 떠서 열린다
- [ ] 같은 와이파이에서 서버의 집 안 주소(예: 192.168.0.50:443)로는 **열리지 않는다**(tailnet 주소로만 문이 열렸다는 증거)
- [ ] 인증서 갱신 타이머가 등록되어 있다(`systemctl list-timers`)
- [ ] 서버를 재부팅한 뒤에도 안내 페이지가 열린다
- [ ] 포트 배치표를 서버 노트에 붙였다

</Lab>
