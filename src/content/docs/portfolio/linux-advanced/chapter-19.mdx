최종 프로젝트는 새로운 것을 배우는 시간이 아닙니다. Chapter 1~18에서 만든 것을 **하나의 가족 서비스로 조립하고, 가족이 실제로 쓰게 하고, 사고 시나리오로 시험하는 것**입니다. 서버를 만든 사람이 아니라 **가족이 믿고 쓸 수 있는가**가 합격 기준입니다.

<Note type="why" title="이 챕터를 마치면">
- 서버의 구성, 운영 방법, 복구 방법을 한 묶음의 문서로 정리할 수 있다
- 가족에게 서버를 소개하고 쓰는 방법을 안내할 수 있다
- 시나리오로 서버의 약점을 찾아 고칠 수 있다
- 서버를 오래 운영하기 위한 달력과 습관을 갖는다
</Note>

## 19.1 완성 기준

| 영역 | 기준 |
|---|---|
| 기반 | Ubuntu Server 24.04, 공유기에서 주소 예약, 유선 연결, 정전 뒤 자동 시작 |
| 접속 | Tailscale만 사용. 공유기에 열린 포트 없음. SSH 키 로그인 |
| 가족 접근 | 가족 계정 초대, ACL로 서비스 포트만 허용 (SSH 불가) |
| 운영 틀 | Docker Compose, Caddy HTTPS, 포트 배치표, `/srv` 폴더 규칙 |
| 서비스 | **3개 이상** (권장: 사진, 비밀번호, 광고 차단 또는 문서) |
| 클로드 | `claudeops` 전용 계정, 파일 권한 벽, CLAUDE.md, 권한 규칙 |
| 자동 점검 | 주간 보고서와 휴대폰 알림, 생존 신호 감시 |
| 감시 | Uptime Kuma에 모든 서비스 등록, 알림 연결 |
| 백업 | 3-2-1(서버 밖 사본 포함), 자동 실행, 감시 연결, **복구 훈련 완료** |
| 보안 | 자동 보안 업데이트, ufw, 열린 포트 점검, 분실 대응 순서표 |
| 문서 | 서버 노트, 복구 절차표(종이), 가족용 안내 1장 |

## 19.3 서버 노트 완성

Chapter 1의 서버 노트를 다음 항목으로 완성합니다. **비밀번호는 쓰지 않습니다.**

| 항목 | 내용 |
|---|---|

| 서비스 목록 | 이름, 폴더, 접속 주소, 업데이트 방법, 마지막 업데이트 날짜 |

| 열쇠 목록 | restic 암호의 위치, Tailscale 계정, 클라우드 키 (**종이, 서버 밖**) |
| 가족 목록 | 누가 어떤 기기로 어떤 서비스를 쓰는지 |
| 변경 기록 | Git과 CHANGELOG의 위치 |
| 알려진 한계 | "서버가 통째로 멈추면 알림이 없다" 등 |

<Note type="tip" title="서버를 나 말고도 알아야 합니다">
내가 갑자기 서버를 돌볼 수 없게 되면 어떻게 될까요? **가족 한 명**에게 서버 노트(종이)와 복구 절차표가 어디 있는지, 서버가 멈췄을 때 최소한 무엇을 해야 하는지(코드를 뽑지 말고 연락하기) 알려 두세요. 서버를 가족의 생활 기반으로 삼는다는 것은 이런 책임까지 포함합니다.
</Note>

## 19.4 인수 점검 시나리오

만든 사람이 "잘 된다"고 말하는 것으로는 부족합니다. **시나리오로 시험**합니다.

### 시나리오 1: 가족이 쓴다

- 가족 1명에게 안내 페이지만 주고 **설명 없이** 사진 앱 설치와 로그인까지 해 보게 합니다. 막히는 곳이 안내문의 약점입니다.
- 집 밖(LTE)에서 사진이 올라가는지 확인합니다.

### 시나리오 2: 재부팅

- 새벽에 `sudo reboot`을 합니다. 5분 안에 모든 서비스가 초록색으로 돌아오는지 Uptime Kuma로 봅니다. 돌아오지 않는 것이 있으면 그 서비스의 `restart` 설정과 부팅 순서를 확인합니다.

### 시나리오 3: 백업 복구

- Chapter 17의 훈련 1과 2를 **새 마음으로 다시** 합니다. 문서만 보고 가능한지 확인하세요.

### 시나리오 4: 기기 분실

- Chapter 18의 분실 순서를 따라 가족 1명의 오래된 기기를 제거하고, 서비스 접속이 막히는지 확인합니다(허락을 받고).

### 시나리오 5: 디스크 가득

- 서버에서 큰 임시 파일을 만들어 디스크 사용률 90%를 흉내 냅니다(`fallocate`로 만들고 바로 지움). Uptime Kuma나 주간 보고서가 이를 알리는지 봅니다. 알리지 못한다면 감시 항목을 추가하세요.

### 시나리오 6: 클로드 점검

- 클로드에게 "지금 서버에서 위험해 보이는 것을 읽기만 해서 알려줘"라고 시킵니다. 답을 직접 확인하고, 틀린 점과 놓친 점을 기록합니다.

<Mini title="점검에서 발견한 약점을 어떻게 다룰까">
시나리오 2에서 Home Assistant가 재부팅 뒤에 올라오지 않았습니다. 이후 어떻게 하면 좋을까요?

<Answer>
(1) 로그로 원인을 찾습니다(`docker compose logs`). (2) 고치고 **같은 시나리오를 다시** 시험합니다. 한 번 고친 것을 시험하지 않으면 고쳐졌는지 모릅니다. (3) 원인과 해결을 Git 커밋 메시지와 서버 노트의 "알려진 문제"에 남깁니다. 문제를 찾은 것은 실패가 아니라 점검의 성과입니다.
</Answer>
</Mini>

## 19.5 운영 달력

서버를 오래 쓰려면 일정이 필요합니다.

| 주기 | 할 일 |
|---|---|
| 매주 | 월요일 아침의 점검 보고서를 읽는다(알림이 오지 않으면 점검 시스템이 멈춘 것) |
| 매월 | 서비스 릴리스 노트를 읽고 백업 후 업데이트, 사용량 확인(클로드 비용) |
| 분기 | Chapter 18의 분기별 점검과 복구 훈련 |
| 매년 | 디스크와 서버 수명 점검, 클로드와 서비스의 요금·약관 재확인, 가족에게 사용 현황 묻기 |
