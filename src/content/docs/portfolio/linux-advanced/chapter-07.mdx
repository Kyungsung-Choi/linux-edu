울타리를 쳤으니 이제 일을 시킵니다. 클로드를 잘 쓰는 사람은 **질문을 잘하는 사람**이 아니라 **답을 검증하는 사람**입니다. 이번 챕터는 일을 시키는 법과 검증하는 법을 함께 연습합니다.

<Note type="why" title="이 챕터를 마치면">
- 서버 문제를 "진단 → 제안 → 적용 → 검증" 순서로 클로드와 풀 수 있다
- 질문에 상황 정보를 넣어 정확한 답을 이끌어 낼 수 있다
- 클로드의 답이 사실인지 근거 명령으로 확인할 수 있다
- 서버 작업 기록을 남기게 할 수 있다
</Note>

## 7.1 좋은 질문의 모양

서버 문제를 물을 때는 네 가지를 함께 줍니다.

| 요소 | 예 |
|---|---|
| 증상 | "어제 밤부터 사진 앱이 느리다" |
| 언제부터 | "화요일 새벽에 서버를 업데이트한 뒤" |
| 이미 해 본 것 | "재부팅은 해 봤다" |
| 원하는 결과 | "원인 후보를 확률 순으로, 확인할 명령과 함께" |

```
어제 새벽 업데이트 뒤부터 사진 앱(Immich)이 느려졌어.
재부팅은 해 봤어. 로그와 상태를 읽고 원인 후보를 3개까지 가능성 높은 순으로 알려줘.
각 후보마다 근거가 된 명령과 출력, 확인하는 방법을 붙여줘. 아직 아무것도 바꾸지 마.
```

마지막 줄이 중요합니다. **"아직 바꾸지 마"** 가 진단 단계를 지킵니다. 계획(plan) 모드에서 시작하면 더 확실합니다.

## 7.2 실습 시나리오 1: 로그에서 이상한 접속 찾기

```
지난 7일 동안 SSH 로그인 실패와 성공 기록을 정리해줘.
사용자 이름별로 몇 번인지, 처음 보는 IP가 있는지, 시간대 특징이 있는지 알려줘.
```

클로드는 `journalctl -u ssh`나 `/var/log/auth.log`를 읽을 것입니다. 이 서버는 Tailscale 안에서만 열려 있으므로 **밖에서 시도한 흔적은 거의 없어야 정상**입니다. 낯선 IP가 많이 보이면 공유기나 서버 설정이 열려 있다는 신호입니다.

<Mini title="사실 확인하기">
클로드가 "지난 7일 동안 로그인 실패는 총 23회"라고 답했습니다. 이 숫자가 맞는지 어떻게 확인할까요?

<Answer>
클로드가 쓴 명령과 출력을 보여 달라고 하고, 직접 같은 명령을 실행해 숫자를 세 봅니다.

<Term code={`
$ journalctl -u ssh --since "7 days ago" | grep -c "Failed password"
`} />

클로드의 숫자와 다르면, 어느 명령의 어느 줄을 세었는지 물어봅니다. 숫자를 자신 있게 말하는 것과 맞는 것은 별개입니다. **큰 결정(차단, 삭제, 설정 변경)에 쓰는 숫자는 한 번은 직접 센다**는 규칙을 두세요.
</Answer>
</Mini>

## 7.3 실습 시나리오 2: 디스크가 왜 찼나

```
디스크 사용량을 확인하고 가장 많이 차지하는 폴더 5개를 알려줘.
그중 지워도 안전한 것과 확인이 필요한 것을 나눠서 설명해줘. 지우는 명령은 제안만 해.
```

클로드가 `du`로 찾아내는 흔한 후보는 아래와 같습니다.

| 후보 | 안전성 | 확인법 |
|---|---|---|
| Docker 오래된 이미지 | 보통 안전 | `docker image ls`로 사용 중인지 확인 |
| 로그 파일(`/var/log`, `journal`) | 일부 정리 가능 | `journalctl --disk-usage` |
| `/srv/data/immich` 등 서비스 자료 | **지우면 안 됨** | 서비스 자료는 서비스의 도구로만 정리 |

<Note type="danger" title="서비스 자료는 파일로 지우지 않습니다">
사진, 데이터베이스, 문서 폴더를 `rm`으로 지우면 서비스는 파일이 없어져도 목록은 그대로라 앱이 망가집니다. 이런 자료는 **그 서비스의 화면이나 도구로** 지웁니다. 클로드가 이 폴더를 지우라고 제안하면 거절하세요.
</Note>

## 7.4 실습 시나리오 3: 설정을 고치고 싶을 때

```
Caddyfile에 Gitea용 칸을 추가하고 싶어. 가족이 여는 포트는 3002, 서버 안 포트는 13002야.
Chapter 3의 규칙을 따라서 바꿀 내용을 ~/ops/proposals/ 에 제안 파일로 만들어줘.
적용 방법, 확인 방법, 되돌리는 방법을 모두 써줘.
```

관리자 계정으로 제안 파일을 읽고, 바꿀 줄이 이해되는지 확인한 뒤 직접 적용합니다.

<Term title="homeserver (admin)" code={`
$ cat /home/claudeops/ops/proposals/*gitea*.md
$ cd /srv/compose/caddy
$ cp Caddyfile Caddyfile.bak.$(date +%F)
$ nano Caddyfile
$ docker exec caddy caddy validate --config /etc/caddy/Caddyfile
$ docker exec caddy caddy reload --config /etc/caddy/Caddyfile
`} />

**바꾸기 전에 복사(백업)하고, 문법을 검사하고, 적용합니다.** 이 순서를 클로드의 제안서에 넣도록 요구하는 것이 CLAUDE.md의 역할입니다.

## 7.5 클로드가 틀리는 방식

| 틀리는 모양 | 대응 |
|---|---|
| **없는 명령이나 옵션을 지어낸다** | 그 명령의 `--help`나 `man` 결과를 확인한다 |
| **예전 버전 문법을 쓴다** | 서비스 공식 문서의 해당 버전 페이지와 대조한다 |
| **한 번 본 로그로 단정한다** | "다른 가능성은 없는가, 이 결론을 뒤집을 증거는 무엇인가"를 묻는다 |
| **위험한 명령을 가볍게 제안한다** | 영향 범위와 되돌리는 방법을 먼저 요구한다 |
| **확인하지 않은 것을 확인했다고 말한다** | "방금 어떤 명령을 실제로 실행했는지 목록으로 보여줘"라고 요구한다 |

<Note type="tip" title="두 번째 의견 구하기">
중요한 변경은 새 대화를 열어 같은 제안서를 보여 주고 "이 변경의 위험을 지적해줘"라고 물어보세요. 같은 모델이라도 처음 대화의 맥락이 없는 상태에서는 다른 문제를 짚어 줍니다.
</Note>

## 7.6 작업 기록 남기기

서버가 3개월 뒤 이상해졌을 때 "그때 뭘 바꿨지"를 찾으려면 기록이 필요합니다. 적용한 변경은 `~/ops/CHANGELOG.md`에 한 줄씩 남기게 합니다.

```
작업이 끝날 때마다 ~/ops/CHANGELOG.md 에 날짜, 무엇을 왜 바꿨는지, 되돌리는 방법을 한 줄로 추가할 내용을 알려줘.
```

클로드는 이 파일에 쓸 수 없으므로 내용을 출력하고, 사람이 복사해 붙입니다. 번거롭지만 **사람이 승인한 변경만 기록되는** 장점이 있습니다.
