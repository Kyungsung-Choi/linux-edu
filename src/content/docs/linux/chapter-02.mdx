Chapter 1에서 "모든 것은 파일이다"를 배웠습니다. 그렇다면 그 파일들은 **어디에** 있을까요? 이번 주는 리눅스의 지도를 읽는 법입니다. 윈도우 사용자가 가장 먼저 길을 잃는 곳이기도 합니다 — `C:\`가 없기 때문입니다.

<Note type="why" title="이 챕터를 마치면">
- 드라이브 문자 없이 하나의 트리로 통합된 구조를 설명할 수 있다
- `/etc`, `/var`, `/usr` 같은 디렉터리가 **무엇을 담고 왜 그런 이름인지** 안다
- `ls -l`이 뱉는 한 줄을 일곱 조각으로 나눠 읽을 수 있다
- 파일을 안전하게 복사·이동·삭제하고, 와일드카드로 여러 개를 한 번에 다룰 수 있다
- 하드링크와 심볼릭 링크의 차이를 설명할 수 있다
- vi에서 빠져나올 수 있다
</Note>

## 2.1 드라이브 문자가 없는 세계

윈도우에서 USB를 꽂으면 `E:` 드라이브가 생깁니다. 리눅스에서는 아무 문자도 생기지 않습니다. 대신 **트리의 어딘가에 그 USB가 붙습니다.**

<Compare>
  <Win>저장장치마다 독립된 트리가 하나씩 생깁니다. `C:\`, `D:\`, `E:\` 는 서로 남남이고, 프로그램은 자기 파일이 어느 드라이브에 있는지 알아야 합니다.</Win>
  <Lin>트리는 `/` 하나뿐입니다. 새 저장장치는 그 트리의 **한 지점에 접붙여집니다**. 붙는 지점을 마운트 포인트라고 하고, 프로그램은 그게 어느 장치인지 몰라도 됩니다.</Lin>
</Compare>

<Hist year="1970s" title="C 드라이브는 왜 C부터 시작하나">
윈도우의 조상인 MS-DOS는 CP/M이라는 옛 운영체제의 관례를 물려받았습니다. 당시 컴퓨터에는 하드디스크가 없었고 **플로피 디스크 드라이브가 한두 개** 달려 있었습니다. 그 둘이 `A:`와 `B:`였습니다.

나중에 하드디스크가 등장하자 남은 다음 글자인 `C:`를 줬습니다. 플로피가 사라진 지 20년이 넘었는데도 시스템 드라이브가 여전히 `C:`인 이유가 이것입니다. **1970년대 플로피 두 대의 자리가 아직 비어 있는 셈입니다.**

UNIX는 다른 길을 택했습니다. 장치가 늘어날 때마다 이름 공간을 새로 만드는 대신, **하나의 트리에 계속 접붙이기로** 한 것입니다. 그래서 리눅스에는 드라이브 문자라는 개념 자체가 없습니다.
</Hist>

</Note>

## 2.2 FHS — 리눅스의 지도

디렉터리 배치는 **FHS(Filesystem Hierarchy Standard)**라는 표준을 따릅니다. 배포판이 달라도 `/etc`에 설정이 있는 이유가 이것입니다.

| 경로 | 담는 것 | 이름의 유래 |
|---|---|---|
| `/` | 뿌리 | root |
| `/etc` | 시스템 설정 파일 | **et cetera** (기타) |
| `/var` | 크기가 변하는 데이터 — 로그, 메일, DB | **var**iable |
| `/usr` | 설치된 프로그램과 라이브러리 | 아래 역사 참조 |
| `/home` | 사용자 개인 디렉터리 | home |
| `/root` | root 계정의 홈 (`/`와 다름) | root |
| `/tmp` | 임시 파일 (재부팅 시 삭제) | temporary |
| `/opt` | 배포판 패키지가 아닌 별도 설치 | optional |
| `/dev` | 장치 파일 | device |
| `/proc` | 커널이 즉석에서 만드는 프로세스 정보 | process |
| `/sys` | 커널·하드웨어 정보 | system |
| `/boot` | 부팅에 필요한 커널과 부트로더 | boot |
| `/srv` | 이 서버가 제공하는 데이터 | service |

<Hist year="1970s" title="/usr 은 user 의 약자가 아니다 — 이제는">
초기 UNIX가 돌던 PDP-11에는 RK05 디스크가 두 장 있었고, **한 장이 1.5MB**였습니다. 처음에 `/usr`은 말 그대로 **사용자들의 홈 디렉터리**였습니다.

그런데 시스템이 커지면서 첫 번째 디스크가 꽉 찼습니다. 개발자들은 급한 대로 프로그램 일부를 두 번째 디스크, 즉 `/usr` 아래로 옮겼습니다. `/bin`이 넘치니 `/usr/bin`을 만들고, `/lib`이 넘치니 `/usr/lib`을 만든 것입니다. **설계가 아니라 응급 조치였습니다.**

이 임시방편이 표준으로 굳었고, 나중에 사람들은 `/usr`을 "Unix System Resources"의 약자라고 재해석하기 시작했습니다. 사용자 홈은 `/home`으로 따로 나갔고요. **50년 전 1.5MB 디스크가 꽉 찬 사건이 오늘날 모든 리눅스의 디렉터리 구조에 남아 있습니다.**

참고로 최근 Ubuntu는 `/bin`을 `/usr/bin`으로 향하는 심볼릭 링크로 만들어 이 분열을 되돌렸습니다. 50년 만의 정리입니다.
</Hist>

<Hist year="1970s" title="/etc 는 '기타 폴더'였다">
`/etc`는 라틴어 **et cetera**, 즉 "기타 등등"입니다. 처음에는 `/bin`(실행 파일)에도 `/dev`(장치)에도 안 들어가는 **분류 불가능한 것들을 던져 넣는 잡동사니 폴더**였습니다.

그런데 그 잡동사니 중 설정 파일의 비중이 점점 커졌고, 결국 "설정 폴더"가 되었습니다. 이름은 그대로 남아서, 지금도 여러분의 서버에는 **"기타"라는 이름의 폴더에 시스템의 모든 설정이 들어 있습니다.**
</Hist>

### 윈도우 대응 지도

<Compare>
  <Win>
    `C:\Program Files` — 프로그램
    `C:\Windows\System32` — 시스템 파일
    `C:\Users\이름\AppData` — 앱 설정
    `C:\Users\이름` — 내 문서
    `C:\Windows\Temp` — 임시 파일
  </Win>
  <Lin>
    `/usr/bin`, `/opt` — 프로그램
    `/usr/lib`, `/etc` — 시스템 파일과 설정
    `~/.config` — 앱 설정 (점 파일)
    `/home/이름` — 내 문서
    `/tmp` — 임시 파일
  </Lin>
</Compare>

<Note type="warn" title="윈도우와 결정적으로 다른 점">
윈도우는 프로그램 하나가 **자기 폴더 하나에** 실행파일·설정·데이터를 다 넣습니다. 리눅스는 **용도별로 흩어놓습니다.** Nginx를 설치하면 실행파일은 `/usr/sbin`, 설정은 `/etc/nginx`, 로그는 `/var/log/nginx`, 웹 문서는 `/var/www`로 갑니다.

처음엔 불편해 보이지만 이유가 있습니다. 설정만 백업하려면 `/etc`만 챙기면 되고, 로그 디스크만 따로 붙이려면 `/var`만 마운트하면 됩니다. **용도가 같은 것끼리 모아두면 통째로 다룰 수 있습니다.**
</Note>

<Mini title="지도 위를 걸어보기">

3. `ls -l /bin` 의 **첫 줄**을 보세요. 방금 배운 `/usr` 통합의 흔적이 보입니다.

`/bin`이 폴더가 아니라 `usr/bin`을 가리키는 **심볼릭 링크**입니다(맨 앞 글자 `l`). 1970년대에 디스크가 꽉 차서 갈라졌던 것을 2020년대에 다시 합친 흔적입니다. 링크는 2.7절에서 자세히 다룹니다.
</Answer>
</Mini>

## 2.3 경로 읽고 쓰기

| 표기 | 뜻 |
|---|---|
| `/` | 루트 (경로 맨 앞) 또는 구분자 |
| `.` | 지금 이 디렉터리 |
| `..` | 한 단계 위 |
| `~` | 내 홈 디렉터리 |
| `-` | 직전에 있던 디렉터리 |

**절대경로**는 `/`에서 시작해 전체를 적습니다. **상대경로**는 지금 위치를 기준으로 적습니다.

<Term code={`
$ pwd
/home/student

# 절대경로 — 어디서 실행하든 같은 곳
$ ls /var/log/syslog

# 상대경로 — 지금 위치 기준
$ cd ../..
$ pwd
/

$ cd -          # 직전 위치로 되돌아가기
/home/student
`} />

<Note type="tip" title="슬래시 방향이 반대인 이유">
윈도우는 `\`, 리눅스는 `/`를 씁니다. 사실 **UNIX가 먼저 `/`를 썼고**, MS-DOS가 나중에 디렉터리를 지원할 때는 이미 `/`를 명령어 옵션 기호로 쓰고 있어서(`dir /w` 처럼) 어쩔 수 없이 `\`를 골랐습니다. 여기서도 옛 결정이 40년을 갑니다.
</Note>

<Note type="tip" title="여기서 이미 보안이 보인다">
`auth.log`와 `syslog`의 권한은 `-rw-r-----`입니다. 소유자는 읽고 쓰고, `adm` 그룹은 읽기만, **나머지 사람은 아무것도 못 합니다.** 로그에는 누가 언제 로그인했는지가 담기므로 아무나 보면 안 되기 때문입니다.

반면 `dpkg.log`는 `-rw-r--r--`로 누구나 읽을 수 있습니다. 어떤 패키지를 설치했는지는 비밀이 아니니까요. **권한은 그 파일이 무엇을 담는지에 대한 판단의 결과입니다.** Chapter 4에서 이 판단을 직접 하게 됩니다.
</Note>

<Mini title="한 줄 읽기 연습">
1. `ls -lh /etc/shadow` 를 실행해 보세요. 권한이 어떻게 되어 있나요? 왜 그럴까요?
2. `ls -ld /tmp` 를 실행하세요. 맨 뒤 권한 자리에 `t`가 보입니다. (Chapter 4에서 다룹니다)
3. `ls -l /dev/null` 의 **맨 앞 글자**를 확인하세요. 일반 파일이 아닙니다.

<Answer>
<Term code={`
$ ls -lh /etc/shadow
-rw-r----- 1 root shadow 1.3K Sep  1 09:10 /etc/shadow

$ ls -ld /tmp
drwxrwxrwt 10 root root 4.0K Sep  3 10:30 /tmp

$ ls -l /dev/null
crw-rw-rw- 1 root root 1, 3 Sep  3 09:08 /dev/null
`} />

`/etc/shadow`는 **패스워드 해시가 든 파일**이라 root와 shadow 그룹 외에는 읽을 수조차 없습니다.
`/tmp`의 맨 끝 `t`는 스티키 비트로, 누구나 쓸 수 있되 **자기 파일만 지울 수 있게** 하는 장치입니다.
`/dev/null`의 맨 앞 `c`는 일반 파일이 아니라 **문자 장치**라는 뜻입니다. 크기 자리에 `1, 3`이라는 장치 번호가 들어가 있는 것도 그래서입니다.
</Answer>
</Mini>

## 2.5 파일 조작 — 그리고 휴지통이 없다는 것

| 명령 | 하는 일 | 윈도우 |
|---|---|---|
| `mkdir` | 디렉터리 만들기 | 새 폴더 |
| `touch` | 빈 파일 만들기 / 시각 갱신 | — |
| `cp` | 복사 | `copy` |
| `mv` | 이동 **또는 이름 변경** | `move` / 이름 바꾸기 |
| `rm` | 삭제 | `del` |
| `rmdir` | 빈 디렉터리 삭제 | — |

<Term code={`
$ mkdir -p project/src/lib      # -p : 중간 경로까지 한 번에
$ touch project/src/main.py
$ cp project/src/main.py project/src/main.py.bak
$ mv project/src/main.py.bak project/backup.py    # 이동과 이름변경이 같은 명령
$ ls -R project
project:
backup.py  src

project/src:
lib  main.py
`} />

<Note type="danger" title="rm 에는 휴지통이 없습니다">
`rm`으로 지운 파일은 **어디로도 가지 않습니다.** 확인 질문도 없고, 복구 도구를 동원해야 하는 상황이 됩니다.

특히 `rm -rf`는 디렉터리를 통째로, 되묻지 않고, 오류도 무시하며 지웁니다. 실무 사고의 단골이며 다음 두 가지가 대표적입니다.

- `rm -rf /경로 *` — 경로 뒤에 **공백이 잘못 들어가** 현재 디렉터리 전체가 함께 지워짐
- `rm -rf $DIR/*` — 변수 `$DIR`가 비어 있어 실질적으로 `rm -rf /*`가 됨
</Note>

<Hist year="1970s" title="왜 휴지통을 안 만들었나">
Chapter 1에서 본 텔레타이프 환경을 떠올려 보세요. 확인 질문을 하려면 **종이에 질문을 인쇄하고, 사용자가 답을 타이핑하고, 그걸 다시 읽어야** 했습니다. 초당 열 글자 속도로요. 자주 쓰는 명령마다 그러면 작업이 불가능했습니다.

그래서 UNIX는 **"사용자는 자기가 무엇을 하는지 안다"**는 전제를 택했습니다. 묻지 않고 실행합니다. 이 전제가 리눅스를 자동화에 강하게 만들었습니다 — 스크립트가 확인 질문에 막히지 않으니까요. 동시에 이 전제가 위험의 원천이기도 합니다.

**강력함과 위험함이 같은 설계에서 나옵니다.** 둘을 분리할 수는 없고, 대신 습관으로 막습니다.
</Hist>

<Note type="tip" title="사고를 막는 습관 세 가지">
1. **지우기 전에 `ls`로 먼저 확인.** 지울 대상을 `rm` 대신 `ls`에 넣어 실행해 보고, 목록이 의도와 같으면 그때 `rm`으로 바꿉니다.
2. **`rm -i`를 별칭으로.** `alias rm='rm -i'`를 `~/.bashrc`에 넣으면 매번 확인을 받습니다. (Chapter 3에서 설정)
3. **지우는 대신 옮기기.** 확신이 없으면 `mkdir ~/trash`를 만들어 `mv`로 옮겨두고, 며칠 뒤 지웁니다.
</Note>

### 와일드카드 — 여러 개를 한 번에

셸이 명령을 실행하기 **전에** 패턴을 실제 파일 이름 목록으로 바꿔줍니다. 이것을 글로빙(globbing)이라고 합니다.

| 패턴 | 뜻 | 예 |
|---|---|---|
| `*` | 아무 글자 0개 이상 | `*.log` → 모든 로그 파일 |
| `?` | 아무 글자 정확히 1개 | `day?.txt` → day1.txt, day2.txt |
| `[abc]` | 괄호 안 글자 중 하나 | `log[123].txt` |
| `[0-9]` | 범위 | `report[0-9].csv` |
| `{a,b}` | 목록 중 하나 | `file.{txt,md}` |

<Term code={`
# 확인 먼저 — ls 로 대상을 눈으로 본다
$ ls *.bak
old.bak  temp.bak  backup.bak

# 목록이 의도와 같으면 그때 지운다
$ rm *.bak
`} />

<Mini title="안전하게 정리하기">
1. 연습용 디렉터리를 만드세요. `mkdir -p ~/lab2 && cd ~/lab2`
2. 파일 다섯 개를 한 번에 만드세요. `touch note{1,2,3}.txt data1.csv data2.csv`
3. **`ls`로 먼저 확인**한 뒤 `.txt` 파일만 지우세요.
4. `data`로 시작하는 파일만 `backup/` 디렉터리로 옮기세요.

<Answer>
<Term code={`
$ mkdir -p ~/lab2 && cd ~/lab2
$ touch note{1,2,3}.txt data1.csv data2.csv
$ ls
data1.csv  data2.csv  note1.txt  note2.txt  note3.txt

# 반드시 ls 로 먼저 확인
$ ls *.txt
note1.txt  note2.txt  note3.txt
$ rm *.txt

$ mkdir backup && mv data*.csv backup/
$ ls backup
data1.csv  data2.csv
`} />

`touch note{1,2,3}.txt` 한 줄이 파일 세 개를 만든 것에 주목하세요. 중괄호 확장은 셸이 해주는 일이라 **모든 명령에서 똑같이 쓸 수 있습니다.**
</Answer>
</Mini>

## 2.6 찾기 — find

<Term code={`
# 이름으로 찾기 (대소문자 무시는 -iname)
$ find /etc -name "*.conf"

# 최근 24시간 안에 수정된 파일

<Note type="tip" title="2>/dev/null 은 무슨 뜻인가">
`find /`를 일반 사용자로 실행하면 권한 없는 디렉터리마다 오류 메시지가 쏟아집니다. `2>/dev/null`은 **그 오류 메시지를 "아무것도 없는 곳"으로 버리라**는 뜻입니다.

`/dev/null`은 Chapter 1에서 배운 "모든 것은 파일이다"의 극단적인 예입니다. **무엇을 써도 사라지고, 읽으면 항상 비어 있는 장치 파일**입니다. 원리와 문법은 Chapter 3 리다이렉션에서 제대로 다룹니다. 지금은 "오류를 숨기는 관용구" 정도로 알아두세요.
</Note>

## 2.7 링크 — 같은 파일에 이름 두 개 붙이기

<Compare>
  <Win>**바로가기(.lnk)**는 그 자체가 하나의 파일입니다. 탐색기가 해석해서 대상을 열어주지만, 다른 프로그램에게는 그냥 알 수 없는 파일입니다.</Win>
  <Lin>링크는 **파일시스템 수준의 기능**입니다. 모든 프로그램이 링크를 진짜 파일처럼 취급하므로, 특별한 지원이 필요 없습니다.</Lin>
</Compare>

### 먼저 inode 를 알아야 합니다

리눅스에서 파일의 **실체**는 이름이 아니라 **inode**라는 번호가 붙은 데이터 덩어리입니다. 이름은 그 inode를 가리키는 꼬리표일 뿐입니다.

<Term code={`
$ ls -li ~/lab2/backup/data1.csv
1573241 -rw-r--r-- 1 student student 0 Sep  3 10:40 data1.csv
`} />

맨 앞 `1573241`이 inode 번호입니다. **이 번호가 파일의 진짜 정체입니다.**

| | 하드링크 | 심볼릭 링크 |
|---|---|---|
| 만들기 | `ln 원본 링크` | `ln -s 원본 링크` |
| 가리키는 것 | **inode** (실체) | **경로** (문자열) |
| 원본을 지우면 | 멀쩡함 | **깨짐** |
| 다른 파티션으로 | 불가 | 가능 |
| 디렉터리에 | 불가 | 가능 |
| `ls -l` 표시 | 일반 파일과 동일 | `l` + `-> 대상` |

<Term code={`
$ cd ~/lab2 && echo "원본 내용" > original.txt

$ ln original.txt hard.txt        # 하드링크
$ ln -s original.txt soft.txt     # 심볼릭 링크

$ ls -li
1573250 -rw-r--r-- 2 student student 13 Sep  3 10:45 hard.txt
1573250 -rw-r--r-- 2 student student 13 Sep  3 10:45 original.txt
1573251 lrwxrwxrwx 1 student student 12 Sep  3 10:45 soft.txt -> original.txt

# 원본을 지우면?
$ rm original.txt
$ cat hard.txt
원본 내용
$ cat soft.txt
cat: soft.txt: No such file or directory
`} />

`original.txt`와 `hard.txt`는 **inode 번호가 같습니다(1573250).** 같은 실체에 붙은 두 개의 이름일 뿐이라 원본을 지워도 데이터는 남습니다. 그리고 링크 수가 `2`인 것도 보이죠 — 2.4절에서 봤던 그 숫자입니다.

반면 `soft.txt`는 **`original.txt`라는 문자열**을 들고 있을 뿐이라 원본이 사라지면 허공을 가리킵니다.

<Hist year="1970s" title="왜 이름과 실체를 분리했나">
파일 이름이 곧 파일이라면, 여러 사람이 같은 데이터를 공유하려면 복사본을 만들어야 합니다. 1.5MB 디스크를 쓰던 시절에 이건 감당할 수 없는 낭비였습니다.

그래서 UNIX는 **데이터(inode)와 이름(디렉터리 항목)을 분리**했습니다. 디렉터리는 사실 "이름 → inode 번호" 표에 지나지 않습니다. 이 설계 덕분에 이름 여러 개가 데이터 하나를 공유할 수 있고, `mv`가 사실상 표에서 이름만 바꾸는 즉시 작업인 이유이며(그래서 큰 파일을 같은 파티션 안에서 옮기면 눈 깜짝할 새 끝납니다), 삭제 명령이 `delete`가 아니라 **`unlink`**라 불리는 이유입니다. 지우는 게 아니라 **이름을 떼는** 것이고, 마지막 이름이 떨어져 나갔을 때 비로소 데이터가 회수됩니다.
</Hist>

<Note type="tip" title="실무에서 심볼릭 링크는 이렇게 쓴다">
버전이 올라가는 프로그램을 `/opt/myapp-1.2.0`처럼 버전별로 설치해 두고, `/opt/myapp`을 현재 버전으로 향하는 심볼릭 링크로 만듭니다. 업그레이드할 때는 **링크만 새 버전으로 바꾸면 되고, 문제가 생기면 링크만 되돌리면 됩니다.** Chapter 8 웹 서버 배포에서 이 패턴을 씁니다.
</Note>

### vi — 안 쓰고 싶어도 만나게 되는 것

nano가 편한데 왜 vi를 배울까요? **vi는 어떤 리눅스에도 반드시 있기 때문입니다.** 최소 설치 서버, 복구 모드, 도커 컨테이너 안에는 nano가 없는 경우가 많습니다. 그리고 `visudo`나 `crontab -e` 같은 명령은 기본 편집기로 vi를 띄웁니다.

<Hist year="1976" title="vi 에 모드가 있는 이유">
빌 조이가 vi를 만들 때 쓰던 단말기는 **ADM-3A**였고, 두 가지 제약이 있었습니다.

첫째, **화살표 키가 없었습니다.** 커서 이동에 쓸 수 있는 건 일반 글자 키뿐이었고, 오른손 검지부터 차례로 놓이는 `h j k l`이 선택되었습니다(그 키캡에는 실제로 화살표가 인쇄되어 있었습니다). 이것이 오늘날까지 vi가 hjkl로 움직이는 이유입니다.

둘째, **접속 속도가 300 baud, 초당 30자 남짓**이었습니다. 화면 전체를 다시 그리는 데 몇 초가 걸렸기 때문에, 최대한 적은 글자로 많은 일을 시켜야 했습니다. 그래서 **"글자를 입력하는 모드"와 "명령을 내리는 모드"를 분리**했습니다. 명령 모드에서는 `dd`(두 글자)로 한 줄을 지울 수 있습니다 — 메뉴도, 조합키도 필요 없습니다.

지금 기준으로는 이상해 보이지만, **화살표 키도 없고 초당 30자로 통신하던 환경에서는 이것이 가장 합리적인 설계였습니다.**
</Hist>

**최소 생존 세트** — 이것만 알면 서버에서 설정을 고칠 수 있습니다.

| 상황 | 키 |
|---|---|
| 입력 시작 | `i` (커서 위치) 또는 `o` (아래에 새 줄) |
| 입력 끝 → 명령 모드 | <kbd>Esc</kbd> |
| 저장하고 나가기 | `:wq` 또는 `ZZ` |
| **저장하지 않고 나가기** | `:q!` |
| 한 줄 삭제 | `dd` |
| 되돌리기 / 다시 | `u` / `Ctrl+r` |
| 검색 | `/찾을말` → `n`으로 다음 |

<Note type="danger" title="vi 에서 길을 잃었을 때">
화면이 이상해지고 아무 키도 안 먹는 것 같다면 순서대로 하세요.

1. <kbd>Esc</kbd>를 두어 번 누른다 — 어느 모드에 있든 명령 모드로 돌아옵니다
2. `:q!` 를 치고 <kbd>Enter</kbd> — **저장하지 않고** 나갑니다

`:q!`는 지금까지의 편집을 전부 버립니다. 설정 파일을 잘못 건드렸을 때 **가장 안전한 탈출구**이기도 합니다. 이 두 단계를 지금 손에 익혀두세요.
</Note>

<Mini title="vi 로 파일 하나 고쳐보기">
1. `vi ~/lab2/vitest.txt` 로 새 파일을 엽니다.
2. `i`를 눌러 입력 모드로 들어가 아무 문장이나 두 줄 쓰세요.
3. <kbd>Esc</kbd> → `:wq` 로 저장하고 나옵니다.
4. 다시 `vi`로 열어 `dd`로 한 줄을 지운 뒤, 이번엔 **저장하지 않고** `:q!`로 나오세요.
5. `cat`으로 확인하면 두 줄이 그대로 있어야 합니다.

<Answer>
<Term code={`
$ cat ~/lab2/vitest.txt
첫 번째 줄입니다.
두 번째 줄입니다.
`} />

`dd`로 지웠는데도 파일에 두 줄이 그대로라면 성공입니다. **vi의 편집은 메모리에서만 일어나고, `:w`로 저장하기 전까지 디스크의 파일은 손대지 않습니다.** 그래서 `:q!`가 안전한 탈출구가 되는 것입니다. 실수했을 때 저장하지 않고 나가면 아무 일도 일어나지 않습니다.
</Answer>
</Mini>

2. **파일 생성** — `logs`에 `app1.log`부터 `app5.log`까지 다섯 개, `config`에 `db.conf`, `web.conf` 두 개를 만드세요. 역시 반복 입력 없이 만듭니다.
3. **`ls -l` 해부** — `config/db.conf`에 대해 `ls -l`을 실행하고, 출력의 **일곱 조각을 각각 무엇인지 적으세요.** (타입+권한 / 링크 수 / 소유자 / 그룹 / 크기 / 시각 / 이름)
4. **안전한 정리** — `logs`의 파일 중 이름이 홀수인 것(`app1`, `app3`, `app5`)만 `archive`로 옮기세요. **옮기기 전에 `ls`로 대상을 확인한 과정도 함께 제출**합니다.
5. **링크 실험** — `config/db.conf`에 하드링크와 심볼릭 링크를 하나씩 만들고 `ls -li`로 확인하세요. 그런 다음 **원본을 지우고** 두 링크에 각각 `cat`을 실행해, 결과가 왜 다른지 inode 개념으로 설명하세요.
6. **vi 실습** — `config/web.conf`를 vi로 열어 `port 8080` 이라는 줄을 추가하고 저장하세요. 그런 다음 다시 열어 그 줄을 `dd`로 지운 뒤 **저장하지 않고** 나오세요. 파일이 그대로인 것을 `cat`으로 확인합니다.
7. **디렉터리 지도 복습** — `/etc`, `/var`, `/usr`, `/tmp` 중 **세 개를 골라**, 각각 무엇을 담는 곳이고 이름이 어디서 왔는지 한 문장씩 적으세요.
</Lab>

<Note type="tip" title="채점 기준">
4번과 5번이 핵심입니다. 4번은 **`rm`이나 `mv` 전에 `ls`로 확인하는 습관**이 몸에 붙었는지를 봅니다. 5번은 결과를 맞히는 것보다 **"하드링크는 inode를, 심볼릭 링크는 경로 문자열을 가리킨다"**는 원리로 설명했는지를 봅니다.
</Note>

## 부록 C · 이번 주 용어의 유래

| 이름 | 유래 |
|---|---|
| **`/usr`** | 원래 사용자 홈이었다. 1.5MB 디스크가 꽉 차 프로그램을 옮긴 응급 조치가 표준이 됐고, 나중에 "Unix System Resources"로 재해석됐다 |
| **`/etc`** | et cetera(기타). 분류 안 되는 것을 넣던 잡동사니 폴더가 설정 폴더가 됐다 |
| **`/var`** | variable. 크기가 계속 변하는 데이터 |
| **`/opt`** | optional. 배포판이 관리하지 않는 선택 설치 |
| **`C:` 드라이브** | `A:`·`B:`는 플로피 드라이브 자리였다. 플로피가 사라진 뒤에도 자리가 비어 있다 |
| **inode** | index node. 파일의 진짜 실체이고, 이름은 여기 붙은 꼬리표다 |
| **unlink** | 삭제의 진짜 이름. 데이터를 지우는 게 아니라 **이름을 떼는** 것이다 |
| **glob** | 초기 UNIX의 경로 확장 프로그램 `glob`(global)에서. 지금은 셸에 내장됐다 |
| **vi** | visual editor. 그 이전 편집기 `ed`는 화면 없이 한 줄씩만 다뤘다 |
| **hjkl** | ADM-3A 단말기에 화살표 키가 없었고, 그 키캡에 화살표가 인쇄돼 있었다 |
| **nano** | 이전 편집기 `pico`(피코)의 자유 소프트웨어판. 피코보다 작은 단위가 나노다 |
