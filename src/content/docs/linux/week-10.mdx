Part 4가 시작됩니다. 지금까지 각 주차 끝에 흩어져 있던 `🔒 보안 포인트`들을 **하나의 체계로 묶습니다.**

이번 주의 목표는 명령어를 더 아는 것이 아닙니다. **"왜 이 설정인지 설명할 수 있는 상태"**가 되는 것입니다. 체크리스트를 따라 하는 사람과, 그 체크리스트를 만들 수 있는 사람의 차이가 여기서 갈립니다.

<Note type="why" title="이 주차를 마치면">
- 우리 서버가 누구에게 어떻게 공격받는지 구조적으로 따질 수 있다
- 공격 표면이라는 개념으로 무엇을 줄여야 할지 판단할 수 있다
- 패스워드 정책과 계정 만료를 설정하고, SSH에 2단계 인증을 붙일 수 있다
- 방화벽을 **기본 차단 + 명시적 허용** 원칙으로 설계할 수 있다
- AppArmor가 권한 모델 위에 무엇을 더하는지 설명할 수 있다
- 기본 설치 서버를 체크리스트에 따라 강화하고 **전후를 근거와 함께 비교**할 수 있다
</Note>

## 10.1 위협 모델링 — 무엇을 막을 것인가

보안을 "좋은 설정을 많이 넣는 것"으로 생각하면 길을 잃습니다. 먼저 **무엇을, 누구로부터, 왜 지키는지**를 정해야 합니다.

네 가지 질문으로 시작합니다.

| 질문 | 우리 실습 서버의 경우 |
|---|---|
| **무엇을 지키나** | 웹 서비스의 가용성, DB의 데이터, 서버 자체의 통제권 |
| **누가 노리나** | 자동화된 봇(대다수), 내부자 실수, 표적 공격자(드묾) |
| **어디로 들어오나** | SSH(22), 웹(80/443), 취약한 애플리케이션, 훔친 자격증명 |
| **뚫리면 무엇을 잃나** | 데이터 유출, 서비스 중단, 암호화폐 채굴에 악용, 다른 서버 공격의 발판 |

<Note type="tip" title="현실적인 위협 순서">
드라마에서 보는 정교한 표적 공격은 실제로는 드뭅니다. 여러분의 서버에서 실제로 일어나는 일은 순서대로 이렇습니다.

1. **자동화된 스캔과 무차별 대입** — 노출되는 즉시, 하루 수천 건. 7주차에서 `auth.log`로 확인했습니다
2. **알려진 취약점의 자동 악용** — 패치 안 된 소프트웨어를 스캐너가 찾아냅니다
3. **잘못된 설정** — 열어둔 DB, `777` 권한, 노출된 `.env`. **사고 원인 1위입니다**
4. **훔친 자격증명** — 다른 곳에서 유출된 비밀번호 재사용
5. 표적 공격 — 마지막

**1~3번이 압도적입니다.** 그래서 하드닝의 대부분은 화려한 기술이 아니라 **기본을 빠짐없이 하는 것**입니다.
</Note>

### 공격 표면 — 줄일수록 안전하다

**공격 표면**은 공격자가 건드릴 수 있는 지점의 총합입니다.

| 표면 | 줄이는 방법 | 배운 주차 |
|---|---|---|
| 열린 포트 | 필요한 것만, 가능하면 `127.0.0.1`에 | 7·8·9주차 |
| 실행 중인 서비스 | 안 쓰는 것은 `disable --now` | 5주차 |
| 설치된 패키지 | 안 쓰는 것은 제거 | 6주차 |
| 로그인 가능한 계정 | `nologin`, 미사용 계정 잠금 | 4주차 |
| 권한이 넓은 파일 | SetUID 최소화, `777` 제거 | 4주차 |
| 소프트웨어 버전 | 최신 유지 | 6·11주차 |

<Hist year="1988" title="모리스 웜 — 인터넷 전체가 멈춘 날">
1988년 11월, 코넬 대학원생 로버트 모리스가 만든 프로그램이 인터넷에 풀렸습니다. 인터넷에 연결된 컴퓨터가 6만 대 남짓이던 시절, **그중 약 10%가 마비**됐습니다.

이 웜이 쓴 방법은 지금 봐도 익숙합니다. 알려진 취약점 악용, 약한 패스워드 추측, 신뢰 관계를 이용한 확산. **35년이 지난 지금도 공격의 기본 문법은 같습니다.**

이 사건이 남긴 것은 두 가지입니다. 첫째, 최초의 컴퓨터 침해 관련 유죄 판결. 둘째, **CERT(침해사고대응팀)의 탄생**입니다. 사고가 터진 뒤에야 대응 조직이 생긴 것이죠.

보안의 역사는 대체로 이런 모양입니다 — 7주차의 SSH도, 4주차의 섀도 패스워드도 사고가 먼저였습니다. **여러분이 이번 주에 넣는 설정 하나하나가 누군가의 사고 뒤에 만들어진 것**입니다.
</Hist>

## 10.2 계정 보안 강화

### 패스워드 정책

<Term code={`
$ sudo apt install libpam-pwquality
$ sudo vi /etc/security/pwquality.conf
`} />

```
minlen = 12          # 최소 길이
dcredit = -1         # 숫자 최소 1개
ucredit = -1         # 대문자 최소 1개
lcredit = -1         # 소문자 최소 1개
ocredit = -1         # 특수문자 최소 1개
maxrepeat = 3        # 같은 문자 3회 초과 반복 금지
usercheck = 1        # 계정 이름 포함 금지
enforce_for_root     # root 에도 적용
```

<Note type="warn" title="복잡도보다 길이가 중요합니다">
전통적인 "대소문자+숫자+특수문자" 규칙은 사람들이 `Password1!` 같은 예측 가능한 패턴을 만들게 합니다. 규칙은 만족하지만 실제로는 약합니다.

현대 지침(NIST 등)은 **길이를 우선**하고, 주기적 강제 변경은 권장하지 않습니다. 자주 바꾸게 하면 `Passw0rd1`, `Passw0rd2`처럼 번호만 올리기 때문입니다.

그래서 실무에서는 이렇게 갑니다.
- **길이를 늘린다** (12자 이상, 가능하면 패스프레이즈)
- **유출된 패스워드 목록과 대조한다**
- **주기적 변경 대신 유출 징후가 있을 때 변경한다**
- **가장 좋은 것은 패스워드를 아예 안 쓰는 것** — 7주차의 SSH 공개키가 그 예입니다
</Note>

<Hist year="2017" title="'90일마다 비밀번호를 바꾸세요'가 철회된 이유">
수십 년 동안 보안 지침의 기본은 **주기적 패스워드 변경**이었습니다. 90일마다 바꾸게 하면 유출된 패스워드의 유효 기간이 줄어든다는 논리였죠.

그런데 실제 데이터가 쌓이자 정반대 결과가 나왔습니다. 사람들은 강제로 바꾸라고 하면 **최소한의 변경**만 합니다. `Winter2024!`가 `Spring2025!`가 되고, `Passw0rd1`이 `Passw0rd2`가 됩니다. 공격자가 이전 패스워드를 알면 다음 것을 맞히는 데 몇 번이면 충분했습니다.

더 나쁜 것은 **기억할 수 없어 적어두게 된다**는 점이었습니다. 모니터에 붙은 포스트잇이 늘었습니다.

2017년 미국 NIST는 지침을 개정하며 **주기적 강제 변경 권고를 삭제**했습니다. 대신 길이를 늘리고, 유출된 패스워드 목록과 대조하고, **침해 징후가 있을 때만 변경**하도록 바꿨습니다. 영국 NCSC도 같은 방향으로 갔습니다.

**보안 지침도 데이터로 검증되고 뒤집힙니다.** "원래 그렇게 하는 것"이라고 배운 것도 근거를 물어봐야 하는 이유이고, 이 과정에서 계속 "왜"를 따진 이유이기도 합니다.
</Hist>

### 계정 만료와 잠금

<Term code={`
$ sudo chage -l student                 # 현재 정책 확인
$ sudo chage -M 90 -W 14 student        # 90일 만료, 14일 전 경고
$ sudo chage -E 2026-12-31 intern       # 계정 만료일 (퇴사·인턴 종료)

$ sudo passwd -l olduser                # 패스워드 잠금
$ sudo usermod -s /usr/sbin/nologin olduser   # 셸도 막기

# 로그인 실패 시 계정 잠금 (faillock)
$ sudo vi /etc/security/faillock.conf
# deny = 5
# unlock_time = 900
`} />

<Note type="tip" title="계정 만료일이 실무에서 중요한 이유">
인턴, 협력업체, 임시 계정은 **만들 때 만료일을 함께 넣는 것**이 원칙입니다. 사람이 기억해서 지우기를 기대하면 반드시 남습니다.

침해사고 조사에서 "3년 전 퇴사자 계정이 살아 있었고 그걸로 들어왔다"는 사례가 흔합니다. `chage -E`는 그 사고를 자동으로 막습니다.
</Note>

<Mini title="계정 정책 적용하고 확인하기">

5. `chage -E`로 만료일이 **어제**인 계정을 만들어 로그인 시도해 보세요.

### SSH 2단계 인증

7주차에서 공개키 인증을 설정했습니다. 여기에 한 겹을 더합니다.

<Term code={`
$ sudo apt install libpam-google-authenticator
$ google-authenticator      # 사용자 본인이 실행. QR 코드가 나온다
`} />

<Term code={`
$ sudo vi /etc/pam.d/sshd
# 맨 아래 추가
# auth required pam_google_authenticator.so

$ sudo vi /etc/ssh/sshd_config
# KbdInteractiveAuthentication yes
# AuthenticationMethods publickey,keyboard-interactive

$ sudo sshd -t && sudo systemctl reload ssh
`} />

<Note type="danger" title="반드시 두 번째 창을 열어둔 채로">
7주차에서 강조한 절차가 여기서도 그대로입니다. **2FA 설정을 잘못하면 아무도 못 들어갑니다.**

1. 현재 SSH 세션을 **닫지 말고** 그대로 둡니다
2. 새 터미널에서 접속을 시도합니다
3. 성공을 확인한 뒤에만 원래 창을 닫습니다

그리고 `google-authenticator`가 출력하는 **비상 코드(scratch code)를 반드시 안전한 곳에 보관**하세요. 휴대폰을 분실하면 그것이 유일한 복구 수단입니다.
</Note>

## 10.3 방화벽 — 기본 차단, 명시적 허용

<Hist year="1998" title="netfilter — 커널 안의 관문">
리눅스 방화벽은 커널의 **netfilter**라는 프레임워크 위에 서 있습니다. 패킷이 네트워크 스택을 지나는 여러 지점에 "갈고리(hook)"를 걸어두고, 그 지점에서 규칙을 검사하는 구조입니다.

사용자가 쓰는 도구는 세대를 거쳤습니다.

- **iptables** (1998~) — 오랫동안 표준이었고 지금도 문서가 가장 많습니다
- **nftables** (2014~) — iptables를 대체. 문법이 정리되고 성능이 개선됐습니다
- **ufw** — "Uncomplicated FireWall". 위 둘의 복잡함을 감춘 우분투의 얼굴

셋은 경쟁 관계가 아니라 **층**입니다. `ufw`로 쓴 규칙은 결국 nftables 규칙으로 번역돼 커널에 들어갑니다. 그래서 `ufw`만 알아도 대부분 되지만, **문제가 생기면 아래층을 볼 줄 알아야** 합니다.
</Hist>

<Term code={`
# 기본 정책 — 들어오는 것은 모두 차단, 나가는 것은 허용
$ sudo ufw default deny incoming
$ sudo ufw default allow outgoing

# 필요한 것만 명시적으로 허용
$ sudo ufw allow 22/tcp comment 'SSH'
$ sudo ufw allow 80/tcp comment 'HTTP'
$ sudo ufw allow 443/tcp comment 'HTTPS'

# 출발지 제한 — 훨씬 강력하다
$ sudo ufw allow from 192.168.56.0/24 to any port 22 proto tcp comment 'SSH from LAN only'
$ sudo ufw allow from 10.0.1.5 to any port 3306 proto tcp comment 'App server only'

# 속도 제한 — 무차별 대입 완화
$ sudo ufw limit 22/tcp

$ sudo ufw enable
$ sudo ufw status verbose numbered
`} />

<Note type="danger" title="ufw enable 전에 SSH 를 먼저 허용하세요">
`ufw default deny incoming` 상태에서 `ufw enable`을 실행하면 **즉시 모든 접속이 끊깁니다.** 원격 서버라면 그 순간 접근 불가입니다.

순서는 반드시 이렇습니다.

```
1. sudo ufw allow 22/tcp        ← 먼저
2. sudo ufw enable              ← 그 다음
3. 새 창에서 접속 확인
```

클라우드 서버에서 이 순서를 뒤집어 인스턴스를 다시 만든 사람이 정말 많습니다. 실습 VM에서 미리 겪어보세요 — 콘솔로 들어가 `ufw disable`을 치면 복구됩니다.
</Note>

### 정책 설계 예시

지금까지 만든 서버(SSH + 웹 + DB + Samba)의 정책은 이렇게 갑니다.

| 서비스 | 포트 | 정책 | 이유 |
|---|---|---|---|
| SSH | 22 | 관리망 대역만 | 인터넷 전체에 열 이유 없음 |
| HTTP | 80 | 전체 허용 | HTTPS로 리다이렉트용 |
| HTTPS | 443 | 전체 허용 | 서비스 본체 |
| MySQL | 3306 | **규칙 없음** | `127.0.0.1`에만 바인드 (8주차) |
| Samba | 445 | 사내 대역만 | **절대 인터넷 금지** (9주차) |

<Note type="tip" title="방화벽만 믿지 마세요 — 계층 방어">
DB를 `127.0.0.1`에 바인드했다면 방화벽 규칙은 필요 없습니다. 그래도 **둘 다 하는 것**이 원칙입니다.

이유는 **한 겹이 실수로 풀릴 수 있기 때문**입니다. 누군가 `bind-address`를 `0.0.0.0`으로 바꿔도 방화벽이 남아 있으면 사고가 안 납니다. 반대도 마찬가지고요.

이것을 **계층 방어(defense in depth)**라고 합니다. 완벽한 한 겹보다 **불완전한 여러 겹**이 현실에서 더 잘 버팁니다.
</Note>

<Mini title="방화벽 설계하고 검증하기">
**VM 콘솔에 접근 가능한 상태에서 진행하세요.**

## 10.4 AppArmor — 권한 위에 한 겹 더

4주차의 권한 모델에는 한계가 있습니다. **웹 서버 프로세스는 `www-data`가 읽을 수 있는 모든 파일을 읽을 수 있습니다.** 웹 서버가 `/etc/passwd`를 읽을 이유는 없는데도 말이죠.

<Compare>
  <Win>무결성 수준과 AppContainer로 앱을 격리합니다. 스토어 앱은 선언한 기능만 쓸 수 있습니다.</Win>
  <Lin>**AppArmor**(우분투)나 **SELinux**(RHEL)가 프로세스별로 "이 프로그램은 이 경로만 이 방식으로 접근 가능"을 강제합니다.</Lin>
</Compare>

| | 임의적 접근 제어 (DAC) | 강제적 접근 제어 (MAC) |
|---|---|---|
| 예 | `rwx` 권한 (4주차) | AppArmor, SELinux |
| 기준 | **누가** 접근하나 | **어떤 프로그램**이 접근하나 |
| 소유자가 바꿀 수 있나 | 예 | **아니오** (관리자만) |
| root는? | 다 가능 | **root도 프로파일에 묶인다** |

<Term code={`
$ sudo aa-status
apparmor module is loaded.
32 profiles are loaded.
28 profiles are in enforce mode.
   /usr/sbin/tcpdump
   /usr/lib/NetworkManager/nm-dhcp-client.action
   ...
4 profiles are in complain mode.

$ sudo apt install apparmor-utils
$ sudo aa-complain /usr/sbin/nginx     # 위반을 기록만 (차단 안 함)
$ sudo aa-enforce /usr/sbin/nginx      # 실제로 차단
$ sudo journalctl -k | grep -i apparmor | tail -5
`} />

<Note type="tip" title="complain 모드로 먼저 관찰하세요">
프로파일을 곧바로 `enforce`로 켜면 **정상 동작까지 막혀 서비스가 죽을 수 있습니다.**

실무 절차는 이렇습니다.

1. **`aa-complain`** — 위반을 로그에 기록만 하고 차단하지 않습니다
2. 며칠 운영하며 로그를 봅니다. 정상 동작인데 걸리는 것이 있으면 프로파일에 추가합니다
3. 충분히 관찰한 뒤 **`aa-enforce`**로 전환합니다

9주차의 컨테이너 보안 옵션과 같은 계열의 도구입니다. **"이 프로그램은 이것만 하면 된다"를 명시적으로 선언**하는 것이죠. 최소 권한 원칙이 프로세스 수준으로 내려온 형태입니다.
</Note>

<Note type="warn" title="AppArmor 를 끄지 마세요">
문제가 생겼을 때 인터넷 안내에 "AppArmor를 비활성화하라"는 조언이 흔합니다. **증상은 사라지지만 방어막 하나를 통째로 걷어내는 것**입니다.

올바른 대응은 `journalctl -k | grep apparmor`로 **무엇이 왜 막혔는지 확인하고, 그 항목만 프로파일에 허용**하는 것입니다. 도구를 끄는 것은 마지막 수단입니다.
</Note>

<Term code={`
$ sudo sysctl --system                   # 적용
$ sysctl net.ipv4.tcp_syncookies         # 확인
net.ipv4.tcp_syncookies = 1
`} />

<Note type="tip" title="fs.protected_symlinks 가 막는 것">
2주차에서 배운 심볼릭 링크가 공격에 쓰일 수 있습니다.

공격자가 `/tmp`(누구나 쓸 수 있는 곳)에 `/etc/shadow`를 가리키는 심볼릭 링크를 만들어 둡니다. 그리고 root 권한으로 도는 어떤 프로그램이 그 이름의 파일에 쓰기를 시도하면, **실제로는 `/etc/shadow`가 덮어써집니다.**

`fs.protected_symlinks = 1`은 **스티키 비트가 걸린 디렉터리에서, 링크 소유자와 접근자가 다르면 따라가지 않게** 합니다. 4주차의 스티키 비트와 2주차의 심볼릭 링크가 여기서 만납니다.

**개별 지식이 아니라 연결된 이해가 필요한 이유**가 이런 데 있습니다.
</Note>

## 10.8 CIS Benchmark 와 자동 점검

체크리스트를 직접 만들 필요는 없습니다. 업계 표준이 있습니다.

| 기준 | 성격 |
|---|---|
| **CIS Benchmark** | 가장 널리 쓰이는 하드닝 가이드. 배포판별 상세 항목 |
| **DISA STIG** | 미 국방부 기준. 더 엄격 |
| **ISMS-P** | 국내 정보보호 인증. 관리적 통제 포함 |

<Note type="tip" title="체크리스트를 그대로 적용하지 마세요">
CIS Benchmark는 수백 개 항목입니다. 전부 적용하면 **서비스가 동작하지 않을 수 있습니다.**

올바른 사용법은 이렇습니다.

1. 우리 환경에 **해당하는 항목만** 고른다
2. 각 항목이 **무엇을 막는지 이해한다**
3. 테스트 환경에서 적용하고 **서비스가 정상인지 확인**한다
4. 적용하지 않기로 한 항목은 **그 이유를 문서로 남긴다**

4번이 특히 중요합니다. 감사에서 "왜 이 항목을 적용하지 않았나"라는 질문에 **"우리 환경에서는 이러이러해서 해당 없음"**이라고 답할 수 있어야 합니다. 이것을 위험 수용(risk acceptance)이라 하고, 보안 업무의 상당 부분이 이 판단과 기록입니다.
</Note>

10. **전후 비교표** — 2번의 "before"와 지금의 "after"를 나란히 놓은 표를 만드세요. **각 변경이 어떤 위협을 줄였는지** 1번의 위협 모델과 연결해 설명합니다.
11. **미적용 항목 기록** — 적용하지 않기로 한 항목이 있다면 **그 이유를 문서로** 남기세요.

**제출물** — 위협 모델, before/after 비교표(10번), 방화벽 규칙 목록과 검증 결과, 커널 파라미터 설명, 미적용 항목과 사유.
</Lab>

<Note type="tip" title="채점 기준">
**10번이 이 과제의 전부입니다.** 설정을 넣은 것은 절반이고, **그 설정이 어떤 위협을 줄였는지 자기 위협 모델과 연결해 설명한 것**이 나머지 절반입니다.

"SSH 패스워드 인증을 껐다"는 사실 기술입니다. "우리 서버는 인터넷에 노출돼 하루 수천 건의 무차별 대입을 받고 있었고(2번 기록), 패스워드 인증을 끄면서 그 경로가 통째로 무력화됐다(5번 검증)"가 답입니다.

11번도 실무에서 중요합니다. **적용하지 않은 것을 기록하는 것**은 게으름이 아니라 판단입니다. 판단한 사람과 몰라서 안 한 사람은 문서로 구분됩니다.
</Note>
