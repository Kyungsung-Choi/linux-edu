Part 2가 시작됩니다. 지금까지는 리눅스를 **쓰는 사람**이었다면, 이제부터는 **관리하는 사람**입니다.

그 첫 관문이 권한입니다. 1주차에서 "UNIX는 태어날 때부터 다중 사용자 시스템이었다"고 했고, 2주차에서 `ls -l`의 아홉 글자를 미뤄뒀습니다. 이번 주에 그 아홉 글자를 끝까지 해부합니다.

<Note type="why" title="이 주차를 마치면">
- 리눅스가 사용자·그룹·나머지 세 계층으로 권한을 나누는 이유를 설명할 수 있다
- `rwx` 아홉 글자와 8진수 `755`를 자유롭게 오갈 수 있다
- `umask`가 새 파일의 기본 권한을 어떻게 정하는지 안다
- SetUID·SetGID·스티키 비트가 무엇이고 **왜 위험한지** 설명할 수 있다
- `sudo`를 안전하게 설정하고, root 직접 로그인을 막을 수 있다
- 부서별 공유 디렉터리를 요구사항대로 설계할 수 있다
</Note>

## 4.1 왜 계정이 나뉘어 있나

<Compare>
  <Win>개인용 PC에서 출발했습니다. 한 사람이 한 대를 쓰는 것이 전제였고, 제대로 된 권한 분리는 Windows NT 계열에 와서야 붙었습니다. 지금도 많은 사용자가 관리자 계정으로 일상 작업을 합니다.</Win>
  <Lin>1969년부터 여러 사람이 한 대를 나눠 쓰는 것이 전제였습니다. **권한 분리가 나중에 붙은 기능이 아니라 설계의 출발점**입니다. 그래서 일상 작업을 root로 하지 않는 것이 관행으로 굳었습니다.</Lin>
</Compare>

<Hist year="1969" title="집 한 채 값 컴퓨터를 수십 명이 나눠 쓰던 시절">
1주차에서 잠깐 언급했던 이야기를 이어갑니다. 당시 컴퓨터는 건물 한 층을 차지했고, 연구원 수십 명이 단말기로 동시에 접속해 썼습니다.

이 환경에서는 두 가지가 반드시 필요했습니다. **남의 파일을 못 보게 막는 것**, 그리고 **한 사람의 실수가 전체를 멈추지 않게 하는 것**입니다. 그래서 UNIX는 파일마다 소유자를 두고, 사용자마다 할 수 있는 일을 제한했습니다.

오늘날 서버 보안의 상당 부분이 이 50년 된 설계 위에 서 있습니다. 클라우드에 올린 웹 서버가 해킹당해도 시스템 전체가 넘어가지 않는 이유는, **웹 서버가 자기 전용 계정으로 돌기 때문**입니다. 그 계정은 다른 파일을 건드릴 권한이 없습니다. 8주차에서 직접 그렇게 구성합니다.
</Hist>

## 4.2 계정 정보는 어디에 있나

1주차의 "모든 것은 파일이다"가 여기서도 통합니다. 계정 정보도 텍스트 파일입니다.

| 파일 | 담는 것 | 누가 읽을 수 있나 |
|---|---|---|
| `/etc/passwd` | 계정 이름, UID, GID, 홈, 로그인 셸 | **누구나** |
| `/etc/shadow` | 패스워드 해시, 만료 정책 | **root만** |
| `/etc/group` | 그룹 이름, GID, 소속 멤버 | 누구나 |
| `/etc/gshadow` | 그룹 패스워드 | root만 |

$ grep student /etc/passwd
student:x:1000:1000:Student,,,:/home/student:/bin/bash

$ sudo grep student /etc/shadow
student:$y$j9T$rXk...생략...:20334:0:99999:7:::
`} />

<Hist year="1988" title="섀도 패스워드 — 읽을 수 있다는 것만으로 위험했다">
초기 UNIX는 패스워드 해시를 `/etc/passwd`에 그대로 넣었습니다. 해시는 되돌릴 수 없으니 공개해도 안전하다고 여겼기 때문입니다.

그런데 컴퓨터가 빨라지면서 전제가 무너졌습니다. 해시를 되돌리는 대신 **흔한 패스워드를 하나씩 해시해서 대조하는** 사전 공격이 현실적인 시간 안에 가능해진 것입니다. 파일을 읽을 수만 있으면 시간을 들여 깰 수 있었습니다.

그래서 해시를 root만 읽는 별도 파일로 옮기고, 원래 자리에는 `x`만 남겼습니다. **"읽을 수 있다"와 "안전하다"는 다르다**는 교훈이고, 지금도 유효합니다. 11주차에서 로그 파일 권한을 다룰 때 같은 원칙을 다시 적용합니다.
</Hist>

## 4.3 계정과 그룹 관리

<Term code={`
# 계정 생성 — 홈 디렉터리와 셸을 명시하는 것이 안전하다
$ sudo useradd -m -s /bin/bash minsu
$ sudo passwd minsu

# 그룹 생성과 소속 추가
$ sudo groupadd devteam
$ sudo usermod -aG devteam minsu     # -a 를 빠뜨리면 기존 그룹이 날아간다

# 확인
$ id minsu
uid=1001(minsu) gid=1001(minsu) groups=1001(minsu),1002(devteam)

# 계정 삭제 (-r 은 홈 디렉터리까지)
$ sudo userdel -r minsu
`} />

<Note type="danger" title="usermod -G 에서 -a 를 빠뜨리면">
`usermod -G devteam minsu`는 minsu의 보조 그룹을 **devteam 하나로 교체**합니다. 원래 속해 있던 그룹이 전부 사라집니다.

`sudo` 그룹에 속한 관리자에게 이 실수를 하면 **그 사람은 즉시 sudo 권한을 잃습니다.** 서버에 root로 직접 로그인할 수 없게 막아둔 상태라면 아무도 관리 작업을 못 하게 됩니다. `-aG`의 `a`(append)는 반드시 붙이세요.
</Note>

<Note type="tip" title="useradd 와 adduser">
우분투에는 두 가지가 있습니다. `useradd`는 모든 리눅스에 있는 저수준 명령이라 옵션을 일일이 줘야 하고, `adduser`는 데비안 계열 전용 대화형 스크립트로 홈 디렉터리·그룹·패스워드를 알아서 챙겨줍니다.

**학습할 때는 `useradd`**를 쓰세요. 무엇이 자동으로 되고 있는지 보이기 때문입니다. 실무에서는 편한 쪽을 쓰되, RHEL 계열 서버에는 `adduser`가 `useradd`의 별칭일 뿐이라는 것을 기억해야 합니다.
</Note>

<Mini title="계정 만들고 소속 확인하기">
1. `testuser` 계정을 홈 디렉터리와 bash 셸을 지정해 만드세요.
2. `id testuser`로 UID와 GID를 확인하세요. 1000번대인가요, 그 아래인가요?
3. `grep testuser /etc/passwd`로 일곱 필드를 확인하고, 각각이 무엇인지 짚어 보세요.
4. `testgroup` 그룹을 만들어 `testuser`를 **기존 그룹을 유지한 채** 추가하세요.
5. 실습이 끝나면 `userdel -r`로 정리하세요.

<Answer>
<Term code={`
$ sudo useradd -m -s /bin/bash testuser
$ id testuser
uid=1001(testuser) gid=1001(testuser) groups=1001(testuser)

$ sudo groupadd testgroup
$ sudo usermod -aG testgroup testuser
$ id testuser
uid=1001(testuser) gid=1001(testuser) groups=1001(testuser),1002(testgroup)

$ sudo userdel -r testuser
`} />

UID가 **1001**입니다. 1000번부터가 사람이 쓰는 계정이고, 그 아래는 서비스용입니다. 그리고 계정을 만들자 **같은 이름의 그룹이 자동으로 함께 생긴** 것도 보이죠 — 우분투의 기본 동작으로, 각자의 파일이 기본적으로 자기만의 그룹에 속하게 해 우발적 공유를 막습니다.

4번에서 `-a` 없이 실행했다면 `testuser`의 기존 그룹이 날아갔을 겁니다.
</Answer>

## 4.4 권한 아홉 글자 — 2주차의 숙제

<Term code={`
$ ls -l report.txt
-rw-r--r-- 1 student devteam 1024 Sep  3 10:00 report.txt
`} />

맨 앞 `-`는 파일 종류(2주차), 나머지 아홉 글자가 권한입니다. **세 글자씩 세 덩어리**로 읽습니다.

| 덩어리 | 대상 | 예시의 값 |
|---|---|---|
| 1~3 | **소유자** (user) | `rw-` 읽고 쓰기 |
| 4~6 | **그룹** (group) | `r--` 읽기만 |
| 7~9 | **나머지 전부** (others) | `r--` 읽기만 |

### 판정 순서가 중요합니다

시스템은 세 덩어리를 모두 확인하지 않습니다. **위에서부터 하나만 맞으면 거기서 멈춥니다.**

1. 내가 소유자인가? → 그렇다면 **소유자 권한만** 적용, 끝
2. 아니면, 내가 그룹에 속하나? → 그렇다면 **그룹 권한만** 적용, 끝
3. 둘 다 아니면 → **나머지 권한** 적용

<Note type="warn" title="그래서 이런 일이 생깁니다">
`----rwxrwx` 라는 권한을 상상해 보세요. 소유자는 아무 권한이 없고 그룹과 나머지는 전부 가능합니다.

이때 **소유자 본인은 자기 파일을 읽지 못합니다.** 그룹에도 속해 있는데 말이죠. 소유자 조건에서 이미 판정이 끝났기 때문입니다. "더 넓은 권한이 있으니 되겠지"라고 생각하면 틀립니다. 실무에서 "분명 권한을 줬는데 안 된다"는 문제의 상당수가 이 순서 때문입니다.
</Note>

### 디렉터리에서 rwx 의 뜻은 다릅니다

같은 글자인데 대상이 디렉터리면 의미가 바뀝니다. 여기서 많이 헷갈립니다.

| 권한 | 파일에서 | **디렉터리에서** |
|---|---|---|
| `r` | 내용 읽기 | **목록 보기** (`ls`) |
| `w` | 내용 쓰기 | **파일 생성·삭제·이름변경** |
| `x` | 실행 | **그 안으로 들어가기·통과하기** (`cd`) |

<Note type="danger" title="디렉터리 w 권한의 무서운 점">
파일을 지우는 데 필요한 것은 **그 파일의 권한이 아니라 그 파일이 든 디렉터리의 `w` 권한**입니다.

읽기 전용(`r--r--r--`)으로 만들어둔 파일이라도, 담긴 디렉터리에 쓰기 권한이 있으면 **누구든 지울 수 있습니다.** 파일 자체를 잠그는 것으로는 삭제를 막을 수 없다는 뜻입니다.

`/tmp`처럼 누구나 파일을 만들어야 하는 공용 디렉터리가 위험한 이유가 이것이고, 그래서 스티키 비트라는 장치가 따로 생겼습니다(4.6절).
</Note>

<Note type="tip" title="x 없이 r 만 있는 디렉터리">
디렉터리에 `r`만 있고 `x`가 없으면 **이름 목록은 보이지만 그 안의 파일 정보는 못 읽습니다.** `ls`는 되는데 `ls -l`은 전부 물음표로 나오죠. 반대로 `x`만 있고 `r`이 없으면 목록은 못 보지만 **정확한 파일 이름을 알면 접근할 수 있습니다.**

후자는 실제로 쓰입니다. 웹 서버의 상위 디렉터리를 `--x`로 두면 목록 탐색은 막으면서 통과는 허용할 수 있습니다.
</Note>

## 4.5 8진수 표기 — `755` 가 무슨 뜻인가

권한 세 글자는 켜짐/꺼짐 세 개, 즉 3비트입니다. 3비트는 0~7의 숫자 하나로 표현됩니다.

| 권한 | 값 |
|---|---|
| `r` 읽기 | **4** |
| `w` 쓰기 | **2** |
| `x` 실행 | **1** |

각 덩어리의 값을 더하면 됩니다.

| 8진수 | 글자 | 뜻 |
|---|---|---|
| `7` | `rwx` | 4+2+1 |
| `6` | `rw-` | 4+2 |
| `5` | `r-x` | 4+1 |
| `4` | `r--` | 4 |
| `0` | `---` | 없음 |

<Hist year="1970s" title="왜 하필 8진수인가">
`755`, `644` 같은 표기가 낯선 이유는 우리가 10진수에 익숙하기 때문입니다. 그런데 권한은 **3비트씩 세 덩어리**입니다. 3비트로 표현되는 값은 0~7, 정확히 **8진수 한 자리**입니다.

초기 UNIX가 돌던 PDP-11은 워드 크기가 16비트였고, 당시 시스템 프로그래머들은 비트를 세 개씩 묶어 읽는 8진수에 익숙했습니다. 16진수가 표준이 된 것은 8비트 바이트 기반 기계가 보편화된 뒤의 일입니다.

그래서 권한 표기가 8진수로 굳었습니다. 오늘날 16진수를 쓰는 세상에서 **권한만 8진수인 것**은, 1970년대 하드웨어의 흔적이 남은 것입니다.

익숙해지는 요령은 10진수로 계산하지 말고 **비트로 읽는 것**입니다. `7`은 `111`(rwx), `5`는 `101`(r-x), `6`은 `110`(rw-). 몇 번 하면 눈에 들어옵니다.
</Hist>

<Term code={`
# 자주 쓰는 조합
$ chmod 644 report.txt      # rw-r--r--  일반 문서
$ chmod 755 script.sh       # rwxr-xr-x  실행 가능한 스크립트, 디렉터리
$ chmod 600 ~/.ssh/id_ed25519   # rw-------  개인키. 남이 읽으면 안 된다
$ chmod 700 ~/private       # rwx------  나만 들어가는 디렉터리

# 기호로 지정할 수도 있다 — 일부만 바꿀 때 편하다
$ chmod u+x script.sh       # 소유자에게 실행 권한 추가
$ chmod go-w shared/        # 그룹과 나머지의 쓰기 권한 제거
$ chmod -R 755 /var/www     # -R 은 하위 전체 (신중하게)

# 소유자와 그룹 변경
$ sudo chown minsu:devteam report.txt
$ sudo chgrp devteam report.txt
`} />

<Note type="danger" title="chmod 777 은 답이 아닙니다">
인터넷에서 "권한 문제는 777로 해결"이라는 조언을 자주 봅니다. **777은 누구나 읽고 쓰고 실행할 수 있다는 뜻**이고, 웹 서버 디렉터리에 이걸 주면 침입자가 악성 스크립트를 심어 실행할 수 있게 됩니다. 실제 침해사고의 흔한 경로입니다.

권한 오류가 났다면 777로 덮지 말고 **누가 무엇을 해야 하는지** 따지세요. 대개는 소유자나 그룹을 올바르게 바꾸는 것이 정답입니다. 10주차 하드닝에서 `777` 파일을 전수 조사하는 방법을 다룹니다.
</Note>

<Mini title="권한 읽고 쓰기">
1. `~/perm` 디렉터리를 만들고 그 안에 `secret.txt`를 만드세요. 기본 권한이 무엇인지 `ls -l`로 확인합니다.
2. `secret.txt`를 **나만 읽고 쓸 수 있게** 바꾸세요. 8진수로 몇 번일까요?
3. `~/perm` 디렉터리를 **나만 들어갈 수 있게** 바꾸세요.

<Answer>
<Term code={`

`640`은 **소유자는 읽고 쓰기(6), 그룹은 읽기만(4), 나머지는 없음(0)**입니다. 2주차에서 본 `/var/log/auth.log`가 정확히 이 권한이었죠. 로그를 남기는 프로세스는 쓰고, `adm` 그룹 관리자는 읽고, 나머지는 못 보게 한 것입니다.

그리고 새 파일의 기본 권한이 `666`이 아니라 `664`인 것에 주목하세요. 이유는 바로 다음 절입니다.
</Answer>

## 4.6 umask — 기본 권한은 누가 정하나

새로 만든 파일이 왜 `rw-rw-r--`일까요? 아무도 지정하지 않았는데 말입니다.

시스템은 파일에 `666`, 디렉터리에 `777`을 주려고 시작합니다. 그리고 **umask에 켜진 비트를 빼버립니다.**

<Term code={`
$ umask
0002

$ umask -S
u=rwx,g=rwx,o=rx
`} />

| | 시작값 | umask `002` | 결과 |
|---|---|---|---|
| 파일 | `666` | `-002` | **`664`** = `rw-rw-r--` |
| 디렉터리 | `777` | `-002` | **`775`** = `rwxrwxr-x` |

디렉터리는 `x`가 있어야 들어갈 수 있으니 `777`에서, 파일은 만들자마자 실행 가능하면 위험하니 `666`에서 시작합니다.

<Note type="tip" title="서버에서는 umask 를 조입니다">
개인 데스크톱은 `002`가 기본이라 같은 그룹원이 내 파일을 고칠 수 있습니다. **서버에서는 보통 `027`이나 `077`로 조입니다.**

- `027` → 파일 `640`, 디렉터리 `750`. 그룹은 읽기만, 나머지는 접근 불가
- `077` → 파일 `600`, 디렉터리 `700`. 나만 접근

`~/.bashrc`나 `/etc/profile`에 `umask 027`을 넣어두면 그때부터 만드는 파일에 적용됩니다. **이미 만들어진 파일은 바뀌지 않습니다.** 10주차 하드닝 체크리스트에 들어가는 항목입니다.
</Note>

<Mini title="umask 를 바꿔 기본 권한 관찰하기">
1. `umask`로 현재 값을 확인하고, 파일 하나를 만들어 권한을 보세요.
2. `umask 077`로 바꾼 뒤 **새 파일**을 만들어 권한을 비교하세요.
3. 1번에서 만든 **기존 파일**의 권한도 바뀌었는지 확인하세요.
4. `umask 022`로 되돌리세요. (셸을 닫으면 원래대로 돌아옵니다)

<Answer>
<Term code={`
$ umask
0002
$ touch before.txt && ls -l before.txt
-rw-rw-r-- 1 student student 0 Sep  3 12:10 before.txt

$ umask 077
$ touch after.txt && ls -l after.txt
-rw------- 1 student student 0 Sep  3 12:10 after.txt

$ ls -l before.txt
-rw-rw-r-- 1 student student 0 Sep  3 12:10 before.txt
`} />

핵심은 3번입니다. **`umask`는 앞으로 만들 파일에만 적용되고 기존 파일은 건드리지 않습니다.** 서버 하드닝에서 `umask`를 조인 뒤 "이미 있던 파일도 안전해졌다"고 착각하면 안 되는 이유입니다. 기존 파일은 `chmod`로 따로 정리해야 합니다.
</Answer>
</Mini>

## 4.7 특수 권한 세 가지

일반 권한 아홉 글자 앞에 숨은 세 비트가 더 있습니다. 실무에서 만나면 반드시 이해해야 하는 것들입니다.

### SetUID (`4000`) — 실행하는 동안 소유자가 된다

<Term code={`
$ ls -l /usr/bin/passwd
-rwsr-xr-x 1 root root 68208 Mar 23 2024 /usr/bin/passwd
`} />

소유자 자리의 `x`가 **`s`로 바뀌어** 있습니다. 이 파일을 실행하면 **실행한 사람이 아니라 파일 소유자(root)의 권한으로 동작**합니다.

왜 필요할까요? 일반 사용자가 자기 패스워드를 바꾸려면 `/etc/shadow`를 고쳐야 하는데, 그 파일은 root만 쓸 수 있습니다. 사용자에게 root 권한을 줄 수는 없으니, **`passwd` 프로그램에만 잠깐 root 권한을 빌려주는** 것입니다.

<Note type="danger" title="SetUID 는 가장 많이 악용되는 통로입니다">
SetUID가 붙은 프로그램에 취약점이 있으면, 공격자는 **일반 사용자에서 root로 곧바로 올라섭니다.** 이것을 권한 상승(privilege escalation)이라 하고, 침해사고 분석에서 가장 먼저 확인하는 항목 중 하나입니다.

특히 위험한 것은 **공격자가 심어둔 SetUID 파일**입니다. 침입에 성공한 뒤 `/tmp` 같은 곳에 root 소유의 SetUID 셸을 만들어두면, 나중에 일반 계정으로만 들어와도 언제든 root가 될 수 있는 뒷문이 됩니다.

그래서 시스템 전체의 SetUID 파일 목록을 주기적으로 확인하고, **기준 목록과 달라진 것이 있는지** 봐야 합니다.

```
$ sudo find / -perm -4000 -type f 2>/dev/null
```

10주차에서 이 목록을 기준선으로 저장하고, 11주차에서 변화를 탐지하는 방법을 다룹니다.
</Note>

### SetGID (`2000`) — 디렉터리에 걸면 그룹이 상속된다

파일에 걸면 SetUID의 그룹 버전이지만, **진짜 유용한 것은 디렉터리에 걸 때**입니다.

디렉터리에 SetGID가 있으면, 그 안에 만들어지는 파일이 **만든 사람의 그룹이 아니라 디렉터리의 그룹을 물려받습니다.** 팀 공유 폴더의 핵심 장치입니다.

<Term code={`
$ sudo chmod 2775 /srv/team
$ ls -ld /srv/team
drwxrwsr-x 2 root devteam 4096 Sep  3 11:20 /srv/team
`} />

그룹 자리의 `x`가 `s`로 바뀌었습니다. 이제 누가 여기에 파일을 만들든 그룹은 `devteam`이 되고, 팀원 모두가 접근할 수 있습니다. **이게 없으면** 각자 자기 개인 그룹으로 파일이 생겨서 서로 못 읽는 상황이 벌어집니다.

### 스티키 비트 (`1000`) — 내 것만 지울 수 있다

<Term code={`
$ ls -ld /tmp
drwxrwxrwt 10 root root 4096 Sep  3 11:25 /tmp
`} />

맨 끝이 `x`가 아니라 **`t`**입니다. 4.4절에서 "디렉터리에 `w`가 있으면 남의 파일도 지울 수 있다"고 했죠. `/tmp`는 누구나 써야 하니 `w`를 줘야 하는데, 그러면 서로의 임시 파일을 지울 수 있게 됩니다.

스티키 비트는 이 예외를 만듭니다 — **쓰기는 모두 가능하되, 삭제는 파일 소유자와 root만.**

| 특수 권한 | 8진수 | 표시 위치 | 용도 |
|---|---|---|---|
| SetUID | `4000` | 소유자 `x` → `s` | 실행 시 소유자 권한 획득 |
| SetGID | `2000` | 그룹 `x` → `s` | 디렉터리: 그룹 상속 |
| 스티키 | `1000` | 나머지 `x` → `t` | 삭제는 소유자만 |

<Note type="tip" title="대문자 S 나 T 가 보인다면">
`s`나 `t`는 원래 `x`가 있던 자리에 표시됩니다. 만약 **대문자 `S`나 `T`**로 보인다면 그 자리에 `x`가 없다는 뜻입니다.

`chmod 4644 파일`처럼 SetUID를 걸었는데 실행 권한을 안 준 경우인데, 대부분 실수입니다. 실행할 수 없는 프로그램에 SetUID는 의미가 없으니까요. 감사 중에 대문자가 보이면 설정이 잘못된 것으로 보고 확인해야 합니다.
</Note>

<Mini title="특수 권한 관찰하기">

`tee`를 쓴 것에 주목하세요 — 3주차에서 배운 "화면에 보면서 파일에도 저장"입니다.

## 4.8 sudo — 필요한 만큼만, 기록을 남기며

1주차에서 sudo가 만들어진 배경을 봤습니다. 이제 직접 설정합니다.

<Term code={`
# sudo 권한 주기 — 우분투는 sudo 그룹에 넣으면 된다
$ sudo usermod -aG sudo minsu

# 설정 파일은 반드시 visudo 로 연다
$ sudo visudo
`} />

<Note type="danger" title="/etc/sudoers 를 vi 로 직접 열지 마세요">
`visudo`는 저장할 때 **문법을 검사**합니다. 오류가 있으면 저장을 거부하고 다시 고칠 기회를 줍니다.

일반 편집기로 열어 문법을 틀리면 **sudo 자체가 동작하지 않게 됩니다.** root로 직접 로그인할 수 없게 막아둔 서버라면 아무도 관리 작업을 할 수 없고, 복구 모드로 부팅하는 수밖에 없습니다. 클라우드 서버라면 이건 꽤 큰 사고입니다.

같은 이유로 `/etc/sudoers.d/` 아래 파일을 만들 때도 `sudo visudo -f /etc/sudoers.d/파일명`을 씁니다.
</Note>

### 최소 권한으로 주기

`sudo` 그룹에 넣으면 그 사람은 **root가 할 수 있는 모든 일**을 할 수 있습니다. 운영 서버에서는 대개 과합니다.

<Term code={`
$ sudo visudo -f /etc/sudoers.d/webops

# 이 파일에 작성 — webops 그룹은 nginx 서비스만 다룰 수 있다
%webops ALL=(ALL) /usr/bin/systemctl restart nginx, /usr/bin/systemctl status nginx

# 패스워드 없이 특정 명령만 허용해야 할 때 (자동화 스크립트용)
deploy ALL=(ALL) NOPASSWD: /usr/local/bin/deploy.sh
`} />

<Note type="warn" title="NOPASSWD 를 줄 때의 함정">
자동화를 위해 `NOPASSWD`를 주는 일은 흔합니다. 다만 **허용한 명령이 다른 명령을 실행할 수 있으면 그 제한은 무의미해집니다.**

예를 들어 `vi`나 `less`에 NOPASSWD를 주면, 그 안에서 `:!sh`로 셸을 띄워 root가 될 수 있습니다. `find`의 `-exec`도 마찬가지입니다. **허용할 명령은 다른 프로그램을 실행할 수 없는 것으로 좁혀야 합니다.**

그리고 위 예시처럼 경로를 절대경로로 적고, 인자까지 명시하는 것이 안전합니다. `systemctl`만 허용하면 `systemctl` 하나로 다른 서비스도 전부 다룰 수 있으니까요.
</Note>

### 누가 무엇을 했는지 남는다

<Term code={`
$ sudo grep sudo /var/log/auth.log | tail -3
Sep  3 11:40:02 ubuntu-lab sudo: student : TTY=pts/0 ; PWD=/home/student ;
  USER=root ; COMMAND=/usr/bin/find / -perm -4000 -type f
`} />

**누가, 언제, 어디서, 어떤 명령을** 실행했는지 전부 기록됩니다. 1980년에 sudo가 해결하려던 문제가 바로 이 추적성이었습니다. 11주차 감사 시간에 이 로그를 본격적으로 다룹니다.

<Mini title="다른 사용자인 척 실행해 권한 확인하기">
권한 설계는 **설정보다 검증이 중요합니다.** `sudo -u`로 그 사람인 척 실행해 봅니다.

1. `testuser` 계정을 만드세요.
2. 홈에 `~/private` 디렉터리를 만들고 `700`으로 설정하세요.
3. `sudo -u testuser ls ~/private` 를 실행해 보세요. 어떻게 되나요?
4. `chmod 755 ~/private` 로 바꾼 뒤 다시 3번을 실행해 비교하세요.
5. `sudo grep sudo /var/log/auth.log | tail -3` 으로 방금 실행이 기록됐는지 확인하세요.

<Answer>
<Term code={`
$ chmod 700 ~/private
$ sudo -u testuser ls /home/student/private
ls: cannot open directory '/home/student/private': Permission denied

$ chmod 755 ~/private
$ sudo -u testuser ls /home/student/private
(비어 있음 — 접근 성공)
`} />

3번에서 **막히는 것이 정상**입니다. 이렇게 "안 되어야 하는 것이 실제로 안 되는지"를 확인하는 것이 권한 검증의 핵심입니다. 설정만 하고 넘어가면 실무에서 사고가 납니다.

5번에서 `sudo -u` 실행까지 전부 로그에 남은 것도 확인하세요. **권한을 빌려 쓴 모든 흔적이 기록됩니다.**
</Answer>
</Mini>

<Hist year="1980s" title="세 계층뿐인 것은 게으름이 아니라 선택이었다">
"소유자·그룹·나머지" 세 계층은 지금 보면 지나치게 단순해 보입니다. 윈도우의 NTFS는 사용자별로 세밀한 권한을 줄 수 있는데 말이죠.

이 단순함은 **의도된 것**이었습니다. 권한 정보를 파일마다 **9비트**에 담을 수 있다는 뜻이고, 1970년대에 이건 대단히 중요한 절약이었습니다. 파일 하나의 메타데이터가 작을수록 디스크와 메모리를 아꼈으니까요.

그런데 절약보다 큰 이득이 따라왔습니다. **사람이 한눈에 읽고 판단할 수 있다**는 것입니다. `ls -l` 한 번으로 수백 개 파일의 권한을 훑을 수 있고, 잘못된 것이 눈에 띕니다. 세밀한 ACL 목록이 파일마다 붙어 있다면 이런 감사는 불가능합니다.

**표현력을 포기하고 가독성을 얻은 것**이고, 50년이 지나 보면 좋은 거래였습니다. ACL이 나중에 추가됐지만 어디까지나 예외 처리용으로 남은 이유이기도 합니다.
</Hist>

## 4.9 ACL — 세 계층으로 부족할 때

소유자·그룹·나머지 세 계층은 단순해서 좋지만, "이 파일을 특정 한 사람에게만 추가로 읽게 하고 싶다"는 요구는 표현할 수 없습니다. 그럴 때 ACL을 씁니다.

<Term code={`
$ setfacl -m u:minsu:r-- report.txt
$ getfacl report.txt
# owner: student
# group: devteam
user::rw-
user:minsu:r--
group::r--
mask::r--
other::---

$ ls -l report.txt
-rw-r-----+ 1 student devteam 1024 Sep  3 12:00 report.txt
`} />

권한 끝에 **`+`**가 붙었습니다. ACL이 걸려 있다는 표시입니다. `ls -l`만 보면 놓치기 쉬우니, 권한을 감사할 때는 `+` 표시를 눈여겨봐야 합니다.

<Note type="tip" title="ACL 은 최후의 수단으로">
ACL은 강력하지만 **눈에 잘 안 보입니다.** `ls -l`에 작은 `+` 하나로만 표시되니, 몇 달 뒤 다른 관리자가 왜 이 사람만 접근되는지 몰라 헤매게 됩니다.

가능하면 **그룹으로 해결**하세요. 그룹을 하나 더 만드는 편이 대개 더 명확합니다. ACL은 그룹으로 표현이 안 되는 예외 상황에만 쓰고, 쓸 때는 반드시 문서에 남기세요.
</Note>

## 🔒 보안 포인트 · 최소 권한 원칙

이번 주 내용을 하나로 꿰는 원칙입니다. **각 주체에게 자기 일을 하는 데 필요한 최소한의 권한만 준다.**

| 실무 적용 | 이유 |
|---|---|
| root로 직접 로그인 금지, `sudo`만 사용 | 누가 무엇을 했는지 기록이 남는다 |
| 서비스마다 전용 계정, 셸은 `nologin` | 웹 서버가 뚫려도 그 계정 권한 밖으로 못 나간다 |
| `chmod 777` 대신 소유자·그룹 조정 | 777은 누구나 쓰기 가능 = 악성코드 심을 자리 |
| 서버 `umask`를 `027`로 | 새로 만드는 파일이 처음부터 조여진 상태 |
| SetUID 목록을 기준선으로 관리 | 새로 생긴 SetUID = 뒷문 신호 |
| `sudo`는 그룹 통째보다 명령 단위로 | 사고 범위를 좁힌다 |
| 개인키는 `600` | 다른 사람이 읽으면 SSH가 아예 거부한다 (7주차) |

<Note type="warn" title="지금 당장 확인해 볼 것">
누구나 쓸 수 있는 파일이 시스템에 있는지 확인하세요. 대개는 실수로 생긴 것입니다.

```
$ sudo find /home /srv /var/www -perm -002 -type f 2>/dev/null
```

결과가 나온다면 그 파일은 **아무나 내용을 바꿀 수 있습니다.** 웹 서버 디렉터리에 이런 파일이 있으면 침해 경로가 됩니다.
</Note>

## 실습 과제 W4

<Lab id="W4" title="부서별 공유 디렉터리 설계" time="120분">
요구사항을 만족하는 공유 공간을 직접 설계합니다. 명령어를 외우는 것이 아니라 **요구사항을 권한으로 번역하는 연습**입니다.

**요구사항**

- `dev` 팀과 `design` 팀이 있고, 각 팀에 두 명씩 있다
- `/srv/dev`는 dev 팀원만 읽고 쓸 수 있다. design 팀은 목록조차 볼 수 없다
- `/srv/design`은 design 팀 전용으로 같은 조건이다
- `/srv/shared`는 **양 팀 모두 읽고 쓸 수 있되, 자기가 만든 파일만 지울 수 있다**
- `/srv/shared`에 만들어지는 파일은 **자동으로 공용 그룹 소속**이 되어야 한다
- 팀장 `minsu`는 nginx 서비스만 재시작할 수 있어야 하고, 다른 sudo 권한은 없다

**과제**

1. 계정 네 개와 그룹 세 개(`dev`, `design`, `shared`)를 만들고 소속을 지정하세요.
2. 세 디렉터리를 만들고 소유자·그룹·권한을 요구사항대로 설정하세요.
3. **각 설정에 대해 왜 그 값인지 한 줄씩 적으세요.** (예: `/srv/shared`가 `3775`인 이유)
4. **검증하세요.** `sudo -u 계정명 명령` 형태로 다른 사용자인 척 실행해, 요구사항이 실제로 지켜지는지 확인합니다. 되어야 하는 것과 되면 안 되는 것을 **각각 최소 두 개씩** 시험하고 결과를 기록하세요.
5. `minsu`의 sudo 권한을 `/etc/sudoers.d/`에 설정하고, 허용된 명령과 허용되지 않은 명령을 각각 실행해 확인하세요.
6. 작업 후 `/srv` 전체의 권한을 `ls -lR`로 출력해 제출하세요.
7. **정리** — 실습이 끝나면 만든 계정과 그룹을 삭제하세요. (스냅샷 복원도 가능합니다)

**힌트** — 4번의 검증이 이 과제의 핵심입니다. 설정만 하고 확인하지 않으면 실무에서 사고가 납니다.
</Lab>

<Note type="tip" title="채점 기준">
3번과 4번을 봅니다. `/srv/shared`에 `3775`를 준 사람이 **"2000(SetGID)으로 그룹을 상속시키고 1000(스티키)으로 남의 파일 삭제를 막았다"**고 설명하면 만점입니다. 숫자만 맞고 설명이 없으면 절반입니다.

4번에서 **"되면 안 되는 것이 실제로 안 되는지"**까지 시험했는지가 갈림길입니다. 권한 설계는 허용을 확인하는 것보다 차단을 확인하는 것이 중요합니다.
</Note>

## 부록 C · 이번 주 용어의 유래

| 이름 | 유래 |
|---|---|
| **UID 0** | 숫자 0이 root의 실체다. 이름이 root가 아니어도 UID가 0이면 root 권한을 갖는다 |
