## 9.1 파일 공유 — 윈도우에서 리눅스 폴더 열기

<Compare>
  <Win>탐색기 주소창에 `\\서버\공유이름`을 칩니다. 프로토콜은 **SMB**입니다.</Win>
  <Lin>리눅스가 SMB로 말할 수 있게 해주는 것이 **Samba**입니다. 리눅스끼리는 더 가벼운 **NFS**를 씁니다.</Lin>
</Compare>

<Term code={`
$ sudo apt install samba
$ sudo mkdir -p /srv/share
$ sudo chown -R nobody:nogroup /srv/share
$ sudo chmod 2770 /srv/share      # Chapter 4의 SetGID

$ sudo vi /etc/samba/smb.conf
`} />

```ini
[share]
   path = /srv/share
   browseable = yes
   read only = no
   guest ok = no                 # 게스트 접근 금지
   valid users = @sambashare     # 이 그룹만
   create mask = 0660
   directory mask = 2770
```

<Term code={`
$ sudo groupadd sambashare
$ sudo usermod -aG sambashare student
$ sudo smbpasswd -a student       # Samba 전용 비밀번호 (리눅스 계정과 별개)

$ testparm                        # 문법 검사 — nginx -t 와 같은 역할
$ sudo systemctl restart smbd
$ sudo ss -tulpn | grep smbd
`} />

<Note type="danger" title="🔒 guest ok = yes 를 쓰지 마세요">
`guest ok = yes`는 **인증 없이 누구나 접근**할 수 있게 합니다. 사내망이니 괜찮다고 생각하기 쉽지만, 사내망에 들어온 악성코드나 감염된 노트북 하나가 그 공유를 전부 읽고 씁니다.

랜섬웨어가 조직 전체로 번지는 가장 흔한 경로가 **인증 없는 파일 공유**입니다. 한 대가 감염되면 열려 있는 모든 공유의 파일을 암호화합니다.

그리고 SMB는 인터넷에 **절대 노출하면 안 되는** 프로토콜입니다(445 포트). 과거 대규모 랜섬웨어 사태가 정확히 이 경로로 번졌습니다. Chapter 10 방화벽에서 이 포트를 확실히 막습니다.
</Note>

<Note type="warn" title="Samba 비밀번호는 리눅스 계정과 별개입니다">
`smbpasswd -a`로 설정하는 비밀번호는 `/etc/shadow`가 아니라 Samba 자체 데이터베이스에 저장됩니다. **리눅스 로그인 비밀번호를 바꿔도 Samba 쪽은 그대로**입니다.

계정을 삭제할 때도 두 곳을 모두 정리해야 합니다. `userdel`만 하고 `smbpasswd -x`를 잊으면 유령 계정이 남습니다. Chapter 10 계정 감사에서 확인할 항목입니다.
</Note>

### 리눅스끼리는 NFS

<Term code={`
$ sudo apt install nfs-kernel-server
$ sudo vi /etc/exports
# /srv/nfs  192.168.56.0/24(rw,sync,no_subtree_check,root_squash)

$ sudo exportfs -ra
$ sudo exportfs -v
`} />

<Note type="tip" title="root_squash 는 반드시 유지하세요">
`root_squash`는 **클라이언트의 root를 서버에서는 `nobody`로 강등**시킵니다. 기본값이고, 절대 끄면 안 됩니다.

이걸 `no_root_squash`로 바꾸면, 그 공유를 마운트할 수 있는 누구든 **자기 컴퓨터에서 root가 되는 것만으로 서버 파일을 마음대로 다룰 수 있습니다.** NFS는 클라이언트를 신뢰하는 프로토콜이라, 접근 범위를 IP 대역으로 좁히는 것이 특히 중요합니다.
</Note>

<Mini title="파일 공유 설정하고 확인하기">
1. Samba를 설치하고 `/srv/share`를 공유로 등록하세요. **`guest ok = no`**로 설정합니다.
2. `testparm`으로 설정 문법을 검사하세요.
3. `sudo ss -tulpn | grep smbd`로 열린 포트를 확인하세요. 몇 번인가요?
4. 같은 서버에서 `smbclient -L localhost -U student`로 공유 목록을 조회하세요.
5. 윈도우 탐색기에서 `\\서버IP\share`로 접속해 보세요. (호스트 전용 어댑터 IP)

<Answer>
<Term code={`
$ sudo ss -tulpn | grep smbd
tcp LISTEN 0.0.0.0:445    users:(("smbd",pid=2841))
tcp LISTEN 0.0.0.0:139    users:(("smbd",pid=2841))

$ smbclient -L localhost -U student
        Sharename       Type      Comment
        ---------       ----      -------
        share           Disk
`} />

**445와 139가 `0.0.0.0`으로 열렸습니다.** Chapter 7에서 배운 대로, 이건 모든 인터페이스에 열려 있다는 뜻입니다.

사내망 안이라면 필요하지만, **이 서버가 인터넷에 노출된다면 즉시 위험해집니다.** Chapter 10에서 방화벽으로 이 포트를 사설 대역으로만 제한하게 됩니다. 지금은 "열려 있다는 사실을 인지하는 것"이 중요합니다.
</Answer>
</Mini>

## 9.2 컨테이너 — 가상머신과 무엇이 다른가

<Compare>
  <Win>가상머신은 **게스트 OS 전체**를 돌립니다. 커널도, 시스템 서비스도 따로입니다. 무겁지만 격리는 완전합니다.</Win>
  <Lin>컨테이너는 **호스트의 커널을 공유**하고 프로세스만 격리합니다. 시작이 몇 초가 아니라 몇 밀리초입니다.</Lin>
</Compare>

| | 가상머신 | 컨테이너 |
|---|---|---|
| 커널 | 게스트마다 별도 | **호스트와 공유** |
| 시작 시간 | 수십 초 | 밀리초 |
| 크기 | GB 단위 | MB 단위 |
| 격리 수준 | 강함 | 상대적으로 약함 |
| 다른 OS | 가능 (리눅스 위에 윈도우) | 불가 (커널을 공유하므로) |

<Hist year="2013" title="도커는 새 기술이 아니라 새 포장이었다">
컨테이너를 이루는 커널 기능들은 도커보다 훨씬 오래됐습니다. 프로세스가 보는 세계를 격리하는 **네임스페이스**와 자원 사용량을 제한하는 **cgroups**는 2000년대 후반부터 리눅스 커널에 있었습니다. FreeBSD의 jail은 2000년, 솔라리스의 zone은 2004년입니다.

문제는 **쓰기가 너무 어려웠다**는 것입니다. 이 기능들을 조합해 격리 환경을 만들려면 깊은 지식이 필요했고, 실제로 쓰는 사람은 소수였습니다.

도커가 한 일은 새 기술을 발명한 것이 아니라 **포장을 만든 것**입니다. `Dockerfile`이라는 표준 레시피, 이미지를 주고받는 레지스트리, 그리고 `docker run` 한 줄로 끝나는 사용법. 어려운 것을 쉽게 만들자 폭발적으로 퍼졌습니다.

**좋은 기술보다 좋은 인터페이스가 세상을 바꾼 사례입니다.** Chapter 3의 파이프도 그랬죠 — 아이디어는 1964년에 있었지만, 셸에 `|` 한 글자로 들어간 1973년에야 세상이 바뀌었습니다.
</Hist>

<Hist year="1979" title="컨테이너의 조상은 chroot 였다">
1979년 UNIX v7에 `chroot`라는 시스템 콜이 추가됐습니다. **프로세스가 보는 루트 디렉터리를 바꾸는** 단순한 기능이었습니다. `/srv/jail`을 루트로 지정하면, 그 프로세스에게는 `/srv/jail/etc`가 `/etc`로 보입니다.

원래 목적은 보안이 아니라 **소프트웨어 빌드 테스트**였습니다. 깨끗한 환경에서 설치가 제대로 되는지 확인하는 용도였죠. 그런데 사람들이 이걸 격리에 쓰기 시작했습니다.

문제는 `chroot`가 **파일시스템만** 격리한다는 것이었습니다. 프로세스 목록도, 네트워크도, 사용자도 전부 공유했고, root 권한이 있으면 빠져나오는 방법도 알려져 있었습니다.

그래서 격리를 더 촘촘하게 만드는 시도가 이어집니다. FreeBSD의 jail(2000), 솔라리스 zone(2004), 그리고 리눅스의 네임스페이스와 cgroups. **도커는 이 40년짜리 계보의 마지막 포장지**입니다. `chroot`가 던진 질문 — "프로세스가 보는 세계를 어디까지 바꿀 수 있나" — 에 대한 누적된 답인 셈입니다.
</Hist>

### 설치와 기본 명령

<Term code={`
$ sudo apt install docker.io
$ sudo systemctl enable --now docker

# 매번 sudo 를 치지 않으려면 (보안 주의 — 아래 참고)
$ sudo usermod -aG docker $USER
$ newgrp docker

$ docker run hello-world
$ docker ps                    # 실행 중인 컨테이너
$ docker ps -a                 # 멈춘 것까지
$ docker images                # 받아둔 이미지
$ docker logs 컨테이너          # 로그
$ docker exec -it 컨테이너 bash # 안으로 들어가기
$ docker stop / rm / rmi
`} />

<Note type="danger" title="🔒 docker 그룹은 root 와 사실상 같습니다">
`docker` 그룹에 넣으면 `sudo` 없이 도커를 쓸 수 있어 편합니다. 하지만 **그 사람은 사실상 root 권한을 갖게 됩니다.**

이유는 간단합니다. 도커 데몬은 root로 돌고, 컨테이너에 호스트의 아무 디렉터리나 마운트할 수 있습니다.

```
$ docker run -v /:/host -it ubuntu chroot /host
```

이 한 줄이면 호스트 파일시스템 전체에 root로 접근합니다. **`docker` 그룹 = root 권한**이라고 생각해야 합니다.

그래서 운영 서버에서는 아무나 이 그룹에 넣지 않습니다. Chapter 4의 최소 권한 원칙에서 보면, `docker` 그룹 부여는 `sudo` 전체 권한을 주는 것과 같은 무게의 결정입니다. 실습 VM에서는 편의상 쓰되, **이 사실을 알고 쓰세요.**
</Note>

<Mini title="컨테이너가 정말 격리되는지 확인하기">
1. `docker run -it --rm ubuntu:24.04 bash` 로 컨테이너 안에 들어가세요.
2. 안에서 `ps aux`를 실행하세요. **호스트의 프로세스가 보이나요?**
3. 안에서 `cat /etc/os-release`와 `uname -r`을 실행하세요. 둘 중 무엇이 호스트와 같나요?
4. `exit`로 나온 뒤 호스트에서 `uname -r`과 비교하세요.

<Answer>
<Term code={`
# 컨테이너 안에서
root@a1b2c3:/# ps aux
USER  PID %CPU %MEM COMMAND
root    1  0.0  0.0 bash        ← 자기 자신이 PID 1
root   10  0.0  0.0 ps aux

root@a1b2c3:/# uname -r
6.8.0-31-generic              ← 호스트와 동일

root@a1b2c3:/# cat /etc/os-release | head -1
PRETTY_NAME="Ubuntu 24.04.1 LTS"
`} />

두 가지가 드러납니다.

**① 프로세스는 격리됩니다.** 컨테이너 안에서 자기 `bash`가 PID 1입니다. Chapter 5에서 배운 대로 호스트에서 PID 1은 `systemd`인데, 컨테이너는 **자기만의 PID 공간**을 갖습니다. 호스트 프로세스는 보이지 않습니다.

**② 커널은 공유합니다.** `uname -r`이 호스트와 완전히 같습니다. 이것이 컨테이너가 가벼운 이유이자, **격리가 가상머신보다 약한 이유**이기도 합니다. 커널에 취약점이 있으면 컨테이너 밖으로 나올 수 있습니다.
</Answer>
</Mini>

## 9.3 볼륨 — 데이터를 살려두기

컨테이너를 지우면 그 안의 데이터도 사라집니다. 데이터베이스라면 치명적이죠.

<Term code={`
# 이름 있는 볼륨 — 도커가 관리
$ docker volume create dbdata
$ docker run -d --name db -v dbdata:/var/lib/mysql mariadb:11

# 호스트 경로 바인드 — 내가 관리
$ docker run -d -v /srv/www:/usr/share/nginx/html:ro nginx:alpine

$ docker volume ls
$ docker volume inspect dbdata
`} />

| 방식 | 언제 |
|---|---|
| 이름 있는 볼륨 | **데이터베이스 등 상태 저장.** 도커가 위치를 관리 |
| 바인드 마운트 | 설정 파일, 개발 중 소스 코드. 경로를 내가 지정 |
| `:ro` | **읽기 전용.** 컨테이너가 고칠 필요 없는 것에는 반드시 |

<Note type="tip" title=":ro 를 습관으로">
설정 파일이나 정적 웹 문서를 마운트할 때는 **읽기 전용(`:ro`)**으로 거세요. 컨테이너가 침해당해도 호스트의 그 파일을 고칠 수 없습니다.

Chapter 4의 최소 권한 원칙이 컨테이너에서는 이렇게 나타납니다. **"쓸 필요가 없으면 쓰기 권한을 주지 않는다."**
</Note>

## 9.4 compose — 스택 전체를 파일 하나로

Chapter 8에서 손으로 세운 웹+DB를 재현해 봅니다.

<Term code={`
$ sudo apt install docker-compose-v2
$ mkdir -p ~/stack && cd ~/stack
$ vi compose.yaml
`} />

```yaml
services:
  db:
    image: mariadb:11
    restart: unless-stopped
    environment:
      MARIADB_DATABASE: myapp
      MARIADB_USER: myapp
      MARIADB_PASSWORD_FILE: /run/secrets/db_password
      MARIADB_ROOT_PASSWORD_FILE: /run/secrets/db_root_password
    volumes:
      - dbdata:/var/lib/mysql
    networks:
      - backend
    secrets:
      - db_password
      - db_root_password
    # 포트를 밖으로 열지 않는다 — Chapter 8의 그 원칙

  web:
    image: nginx:alpine
    restart: unless-stopped
    ports:
      - "127.0.0.1:8080:80"      # 호스트의 로컬에만 노출
    volumes:
      - ./html:/usr/share/nginx/html:ro
      - ./nginx.conf:/etc/nginx/conf.d/default.conf:ro
    depends_on:
      - db
    networks:
      - backend
      - frontend

volumes:
  dbdata:

networks:
  frontend:
  backend:
    internal: true               # 외부와 통신 불가

secrets:
  db_password:
    file: ./secrets/db_password.txt
  db_root_password:
    file: ./secrets/db_root_password.txt
```

<Term code={`
$ mkdir -p secrets html
$ openssl rand -base64 32 > secrets/db_password.txt
$ openssl rand -base64 32 > secrets/db_root_password.txt
$ chmod 600 secrets/*.txt

$ docker compose up -d
$ docker compose ps
$ docker compose logs -f web
$ docker compose down          # 중지 + 삭제 (볼륨은 남음)
$ docker compose down -v       # 볼륨까지 삭제 (데이터 소멸)
`} />

<Note type="tip" title="이 파일에 Chapter 8 원칙이 전부 들어 있습니다">
| 설정 | 대응하는 원칙 |
|---|---|
| `db`에 `ports` 없음 | **DB를 외부에 열지 않는다** (Chapter 8) |
| `127.0.0.1:8080:80` | 호스트의 로컬에만 바인드 (Chapter 7) |
| `backend: internal: true` | DB 네트워크는 인터넷과 단절 |
| `:ro` 마운트 | 최소 권한 (Chapter 4) |
| `secrets` 파일 | 비밀번호를 환경변수로 노출하지 않음 (Chapter 5) |
| `restart: unless-stopped` | 죽으면 자동 재시작 (Chapter 5 systemd의 `Restart=`) |

**같은 원칙이 도구만 바뀌어 반복됩니다.** 이것이 원리를 배우는 이유입니다.
</Note>

<Note type="warn" title="environment 로 비밀번호를 넘기지 마세요">
많은 예제가 이렇게 씁니다.

```yaml
environment:
  MARIADB_PASSWORD: mypassword123     ← 위험
```

환경변수는 **`docker inspect`로 누구나 볼 수 있고**, compose 파일이 Git에 커밋되면 비밀번호가 저장소에 영구히 남습니다. Chapter 5에서 "명령줄 인자에 비밀을 넣지 말라"고 한 것과 같은 문제입니다.

`_FILE` 접미사를 지원하는 이미지에서는 **파일로 넘기고, 그 파일을 `.gitignore`에 넣으세요.**
</Note>

## 9.5 🔒 컨테이너 보안

| 원칙 | 방법 |
|---|---|
| **root로 돌리지 않기** | `user: "1000:1000"` 또는 Dockerfile의 `USER` |
| **베이스 이미지 태그 고정** | `nginx:1.27-alpine` — `latest` 금지 |
| **공식 이미지 우선** | 출처를 알 수 없는 이미지는 무엇이 들었는지 모른다 |
| **최소 이미지** | `alpine`, `distroless` — 들어 있는 게 적으면 취약점도 적다 |
| **읽기 전용 루트** | `read_only: true` |
| **권한 상승 차단** | `security_opt: ["no-new-privileges:true"]` |
| **취약점 스캔** | `docker scout cves 이미지` 또는 `trivy` |

```yaml
  web:
    image: nginx:1.27-alpine
    user: "101:101"
    read_only: true
    tmpfs:
      - /var/cache/nginx
      - /var/run
    security_opt:
      - no-new-privileges:true
    cap_drop:
      - ALL
```

<Note type="danger" title="latest 태그를 쓰지 마세요">
`image: nginx:latest`는 편해 보이지만 두 가지 문제가 있습니다.

**① 재현이 안 됩니다.** 오늘 뜬 것과 다음 달에 뜬 것이 다른 버전일 수 있고, 그러면 "내 환경에서는 되는데"가 시작됩니다.

**② 언제 바뀌는지 모릅니다.** 재시작할 때마다 조용히 다른 버전으로 갈아탈 수 있습니다. 문제가 생겨도 무엇이 바뀌었는지 추적이 안 됩니다.

버전을 고정하고, **업데이트는 의도적으로** 하세요. Chapter 6에서 패키지 버전을 관리하던 것과 같은 원칙입니다.
</Note>

<Note type="warn" title="컨테이너 안의 root 는 진짜 root 에 가깝습니다">
컨테이너 안의 `root`(UID 0)는 호스트의 UID 0과 **같은 숫자**입니다. 네임스페이스로 격리돼 있지만, 커널 취약점이나 잘못된 설정(특권 모드, 호스트 경로 마운트)이 있으면 그 격리를 넘어설 수 있습니다.

Chapter 4에서 배운 것을 떠올리세요 — **권한은 이름이 아니라 UID 숫자로 판단됩니다.** 컨테이너를 UID 1000으로 돌리면, 설령 탈출하더라도 호스트에서 일반 사용자일 뿐입니다.
</Note>

## 9.6 셸 스크립트 — 반복을 없애기

<Term code={`
$ vi ~/bin/backup.sh
`} />

```bash
#!/usr/bin/env bash
set -euo pipefail        # ← 이 한 줄이 사고를 막는다
IFS=$'\n\t'

SRC="${1:-/etc}"
DEST="/data/backup"
KEEP_DAYS=7
STAMP=$(date +%F_%H%M)
LOG="/var/log/backup.log"

log() { echo "[$(date +'%F %T')] $*" | tee -a "$LOG"; }

cleanup() {
  local code=$?
  [ $code -ne 0 ] && log "실패 (종료 코드 $code)"
  rm -f "${TMPFILE:-}"
}
trap cleanup EXIT

# 사전 점검
[ -d "$SRC" ]  || { log "원본 없음: $SRC"; exit 1; }
mkdir -p "$DEST"

TMPFILE=$(mktemp)
ARCHIVE="$DEST/backup-${STAMP}.tar.gz"

log "백업 시작: $SRC → $ARCHIVE"
tar -czf "$ARCHIVE" "$SRC" 2>"$TMPFILE" || { log "tar 실패: $(cat "$TMPFILE")"; exit 1; }

SIZE=$(du -h "$ARCHIVE" | cut -f1)
log "완료: $ARCHIVE ($SIZE)"

# 오래된 백업 정리
DELETED=$(find "$DEST" -name 'backup-*.tar.gz' -mtime +$KEEP_DAYS -print -delete | wc -l)
log "오래된 백업 $DELETED개 삭제"
```

<Note type="tip" title="set -euo pipefail — 스크립트의 안전벨트">
| 옵션 | 하는 일 | 없으면 |
|---|---|---|
| `-e` | 명령이 실패하면 즉시 중단 | 실패해도 다음 줄이 실행돼 **엉뚱한 상태에서 계속 진행** |
| `-u` | 정의 안 된 변수를 쓰면 오류 | `rm -rf "$DIR/"` 에서 `$DIR`가 비면 **`rm -rf /`** 가 된다 |
| `-o pipefail` | 파이프 중간이 실패해도 실패로 처리 | 마지막 명령만 성공하면 전체가 성공으로 보인다 |

Chapter 2에서 `rm -rf $DIR/*` 사고를 언급했죠. **`set -u` 한 글자가 그 사고를 막습니다.** 스크립트를 쓸 때 첫 줄에 조건반사로 넣으세요.
</Note>

<Note type="warn" title="변수는 항상 큰따옴표로">
```bash
rm $FILE          # 파일 이름에 공백이 있으면 여러 개로 쪼개진다
rm "$FILE"        # 올바름
```

`My Document.txt`라는 파일에 `rm $FILE`을 쓰면 `My`와 `Document.txt` **두 개를 지우려 합니다.** Chapter 3에서 배운 셸의 단어 분리 때문입니다.

큰따옴표를 씌우면 하나의 값으로 유지됩니다. 예외 없이 씌우는 습관을 들이세요.
</Note>

<Note type="tip" title="shellcheck 로 검사하기">
```
$ sudo apt install shellcheck
$ shellcheck ~/bin/backup.sh
```

따옴표 누락, 정의 안 된 변수, 잘못된 조건문 같은 것을 자동으로 잡아줍니다. **Chapter 8의 `nginx -t`, Chapter 4의 `visudo`와 같은 역할**입니다. 실행하기 전에 검사하는 도구가 있으면 반드시 쓰세요.
</Note>

<Mini title="안전한 스크립트 만들어보기">
1. `set -euo pipefail` **없이** 다음 스크립트를 만들어 실행해 보세요.
   ```bash
   #!/bin/bash
   cd /없는디렉터리
   echo "여기까지 실행됨"
   ```
2. 첫 줄 다음에 `set -e`를 넣고 다시 실행해 차이를 보세요.
3. `set -u` 실험 — `DIR=""` 상태에서 `echo "rm -rf $DIR/tmp"` 를 출력해 보세요. 무엇이 보이나요?
4. `shellcheck`를 설치해 위 스크립트들을 검사하세요.

<Answer>
<Term code={`
# set -e 없이
$ ./test.sh
./test.sh: line 2: cd: /없는디렉터리: No such file or directory
여기까지 실행됨            ← 실패했는데 계속 진행됐다

# set -e 있으면
$ ./test.sh
./test.sh: line 3: cd: /없는디렉터리: No such file or directory
(즉시 중단)

# set -u 실험
$ DIR=""
$ echo "rm -rf $DIR/tmp"
rm -rf /tmp                ← 의도와 전혀 다른 명령이 됐다
`} />

3번이 무섭습니다. 변수가 비어 있으면 `rm -rf $DIR/tmp`가 **`rm -rf /tmp`**가 됩니다. 만약 `$DIR/`만 있었다면 `rm -rf /`가 되죠.

이런 이유로 실제 서비스가 삭제된 사고가 여러 번 있었습니다. **`set -u`는 그 변수가 정의되지 않았을 때 스크립트를 멈춥니다.** 한 줄로 막을 수 있는 사고입니다.
</Answer>
</Mini>

<Hist year="2015" title="변수 하나가 비어 있어서 벌어진 일">
2015년, 한 대형 게임 플랫폼의 리눅스 클라이언트에서 사용자 홈 디렉터리가 통째로 삭제되는 버그가 보고됐습니다. 원인은 설치 스크립트의 한 줄이었습니다.

```bash
rm -rf "$STEAMROOT/"*
```

따옴표까지 잘 씌운 코드입니다. 그런데 어떤 조건에서 `$STEAMROOT`가 **빈 문자열**이 되면 이 명령은 `rm -rf /*`가 됩니다. 외장 디스크를 마운트해 뒀다면 그것까지 지워졌습니다.

비슷한 사고가 그 전후로 여러 건 있었습니다. 한 클라우드 업체는 정리 스크립트의 경로 변수가 비어 고객 데이터를 삭제했고, 개인 개발자들의 사례는 셀 수 없습니다.

**막는 방법은 한 줄입니다.**

```bash
set -u        # 정의되지 않은 변수를 쓰면 즉시 중단
```

이 옵션이 있었다면 스크립트는 `rm`을 실행하기 전에 멈췄을 겁니다. 9.6절에서 `set -euo pipefail`을 조건반사로 넣으라고 한 이유가 이것입니다. **한 글자가 회사를 구합니다.**
</Hist>

## 9.7 (개요) Ansible — 서버 여러 대를 같게 만들기

서버가 한 대면 SSH로 들어가 손으로 해도 됩니다. 열 대라면요?

```yaml
- hosts: webservers
  become: yes
  tasks:
    - name: Nginx 설치
      apt: name=nginx state=present update_cache=yes

    - name: 설정 배포
      template:
        src: nginx.conf.j2
        dest: /etc/nginx/sites-available/mysite
        mode: '0644'
      notify: reload nginx

  handlers:
    - name: reload nginx
      systemd: name=nginx state=reloaded
```

<Note type="tip" title="멱등성 — 몇 번 실행해도 결과가 같다">
Ansible의 핵심 개념입니다. 위 작업을 열 번 실행해도 **결과는 한 번 실행한 것과 같습니다.** 이미 설치돼 있으면 건너뛰고, 설정이 이미 같으면 아무것도 하지 않습니다.

"이 명령들을 실행하라"가 아니라 **"이런 상태여야 한다"**를 선언하는 방식입니다. 그래서 안심하고 반복 실행할 수 있고, 서버 100대에 같은 상태를 보장할 수 있습니다.

Chapter 1에서 "설정이 텍스트 파일이라 서버 100대에 스크립트로 뿌릴 수 있다"고 했던 것이 이것입니다. 이 과정의 범위를 넘지만, **다음에 배울 것으로 기억해 두세요.**
</Note>

<Lab id="Ch9" title="스택 컨테이너화와 자동화" time="180분">
**스냅샷 먼저.**

1. **Samba 공유** — `/srv/share`를 인증이 필요한 공유로 설정하세요. `guest ok = no`, 전용 그룹만 허용. `testparm`으로 검사하고, `ss -tulpn`으로 열린 포트를 확인해 **왜 인터넷에 노출하면 안 되는지** 적으세요.
2. **컨테이너 격리 확인** — `ubuntu:24.04` 컨테이너 안에서 `ps aux`와 `uname -r`을 실행하고, 호스트와 비교해 **무엇이 격리되고 무엇이 공유되는지** 설명하세요.
3. **compose 스택** — 본문의 compose 파일을 참고해 웹+DB 스택을 띄우세요. 다음 조건을 모두 만족해야 합니다.
   - DB는 호스트에 포트를 노출하지 않는다
   - 웹은 `127.0.0.1:8080`에만 바인드한다
   - 비밀번호는 `secrets` 파일로 넘긴다
   - 이미지 태그를 고정한다 (`latest` 금지)
4. **검증** — 호스트에서 `ss -tulpn`으로 **3306이 안 보이는 것**과 8080이 로컬에만 열린 것을 확인하세요. 그리고 웹 컨테이너에서 DB로 통신이 되는지 확인합니다.
5. **컨테이너 보안 강화** — 웹 컨테이너에 `user`, `read_only`, `no-new-privileges`, `cap_drop`을 적용하세요. **적용 전후로 컨테이너 안에서 `whoami`와 `touch /test`를 실행해 차이를 확인**합니다.
6. **취약점 스캔** — `docker scout cves nginx:1.27-alpine` 또는 `trivy image`로 이미지를 스캔하고 결과를 요약하세요.
7. **백업 스크립트** — 본문의 스크립트를 참고해 다음을 만족하는 스크립트를 작성하세요.
   - `set -euo pipefail` 포함
   - 모든 변수를 큰따옴표로
   - `trap`으로 정리 로직
   - 로그를 파일과 화면에 동시 기록 (`tee`)
   - 7일 지난 백업 자동 삭제
8. **shellcheck** — 7번 스크립트를 검사하고, 지적된 항목을 고친 뒤 재검사 결과를 제출하세요.
9. **자동화** — 7번을 Chapter 5에서 배운 systemd 타이머로 매일 실행되게 등록하세요.
10. **데이터 보존 확인** — `docker compose down` 후 다시 `up -d` 했을 때 **DB 데이터가 남아 있는지** 확인하세요. 그리고 `down -v` 후에는 어떻게 되는지도 확인합니다.

**제출물** — 각 문항의 명령과 출력, 2·5·10번의 비교 결과, compose 파일과 스크립트 전문, 8번의 검사 전후.
</Lab>

<Note type="tip" title="채점 기준">
4번과 5번이 핵심입니다. **"DB 포트가 안 보인다"를 눈으로 확인한 것**과 설정만 써둔 것은 다릅니다. 5번에서 `read_only: true`를 적용한 뒤 `touch /test`가 실패하는 것을 보면, 그 옵션이 무엇을 하는지 확실히 알게 됩니다.

10번은 볼륨의 의미를 묻습니다. `down`과 `down -v`의 차이를 모르고 후자를 실행해 운영 데이터를 날리는 사고가 실제로 있습니다.

8번은 도구를 쓰는 습관을 봅니다. `nginx -t`, `visudo`, `sshd -t`, `testparm`, `shellcheck` — **실행 전에 검사하는 도구가 있으면 반드시 쓴다**는 것이 이 과정에서 반복해 온 원칙입니다.
</Note>

| `docker stop` / `rm` / `rmi` | 중지 / 컨테이너 삭제 / 이미지 삭제 |
| `docker volume ls` / `inspect` | 볼륨 목록 / 상세 |
| `docker system df` / `prune` | 용량 확인 / 미사용 정리 |
| `docker scout cves 이미지` | 취약점 스캔 |

## 부록 C · 이번 주 용어의 유래

| 이름 | 유래 |
|---|---|
| **Samba** | SMB 프로토콜의 자모를 살려 사전에서 찾은 단어. 리눅스가 윈도우 파일 공유에 참여하게 해준다 |
| **네임스페이스** | 프로세스가 보는 세계(프로세스 목록·네트워크·파일시스템)를 격리하는 커널 기능 |
| **cgroups** | control groups. CPU·메모리 사용량을 제한한다 |
| **컨테이너** | 화물 컨테이너에서 온 비유. 안에 무엇이 들었든 규격이 같아 어디서든 옮길 수 있다 |
| **이미지 / 컨테이너** | 이미지는 디스크의 프로그램, 컨테이너는 그것이 실행 중인 상태. **Chapter 5의 프로그램/프로세스 관계와 같다** |
| **볼륨** | 컨테이너를 지워도 남는 저장 공간 |
| **alpine** | 5MB 남짓의 초경량 리눅스 배포판. 들어 있는 게 적어 취약점도 적다 |
| **멱등성** | 몇 번 실행해도 결과가 같은 성질. 구성 관리 도구의 핵심 개념 |
| **`set -e`** | 실패하면 즉시 멈춘다. 이 옵션이 없어 사고가 커진 사례가 많아 관행으로 굳었다 |
| **shellcheck** | 셸 스크립트 정적 분석기. `nginx -t`·`visudo`와 같은 계열의 "실행 전 검사" 도구 |
