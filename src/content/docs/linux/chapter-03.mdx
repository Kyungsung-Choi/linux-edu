Chapter 1에서 "작게, 하나만 잘하게"라는 UNIX의 원칙을 봤습니다. 그런데 작은 도구만 있으면 작은 일밖에 못 하는 것 아닐까요?

이번 주가 그 답입니다. **작은 도구를 이어 붙이는 방법**을 배우고 나면, 도구 열 개로 수백 가지 일을 하게 됩니다. 리눅스가 서버에서 강력한 진짜 이유가 여기 있습니다.

<Note type="why" title="이 챕터를 마치면">
- 모든 프로그램이 입력 하나와 출력 두 개를 가진다는 것을 설명할 수 있다
- `>`, `>>`, `2>`로 출력을 파일로 보내고 오류만 따로 걸러낼 수 있다
- 파이프로 명령을 이어 붙여 원하는 정보를 뽑아낼 수 있다
- `grep`·`sort`·`uniq`·`wc`로 로그에서 통계를 만들 수 있다
- `~/.bashrc`를 고쳐 내 작업 환경을 만들 수 있다
- 오래 걸리는 작업을 백그라운드로 돌리고, 접속을 끊어도 살려둘 수 있다
</Note>

## 3.1 셸은 그냥 프로그램이다 — 다시

Chapter 1에서 `/bin/bash`가 1.4MB짜리 파일 하나임을 확인했습니다. 셸이 하는 일은 생각보다 단순합니다.

1. 사람이 친 줄을 읽는다
2. **와일드카드를 실제 파일 이름으로 바꾸고, 변수를 값으로 바꾸고, 따옴표를 처리한다**
3. 그 결과를 명령어와 인자로 쪼갠다
4. 커널에게 "이 프로그램을 실행해 달라"고 부탁한다(시스템 콜)
5. 끝날 때까지 기다렸다가 다음 줄을 읽는다

2번이 중요합니다. `rm *.log`를 실행할 때 **`rm`은 `*`를 본 적이 없습니다.** 셸이 미리 파일 목록으로 바꿔서 넘겨주기 때문입니다.

<Hist year="1989" title="bash 는 말장난이다">
초기 UNIX의 표준 셸은 스티븐 본이 만든 **Bourne shell(`sh`)**이었습니다. GNU 프로젝트가 자유로운 대체품을 만들면서 이름을 **Bourne Again SHell**, 줄여서 `bash`라고 붙였습니다. "다시 태어난(born again) 본 셸"이라는 말장난입니다.

리눅스 도구 이름에는 이런 농담이 유난히 많습니다. `less`가 `more`의 개선판인 것도, `GNU`가 "GNU is Not Unix"인 것도 같은 문화입니다. **자유 소프트웨어 진영의 유머가 그대로 시스템에 화석처럼 남아 있습니다.**
</Hist>

## 3.2 입력 하나, 출력 둘

리눅스의 모든 프로그램은 태어날 때부터 **세 개의 통로**를 가집니다. 예외가 없습니다.

| 번호 | 이름 | 뜻 | 기본 연결 |
|---|---|---|---|
| `0` | stdin | 표준 입력 | 키보드 |
| `1` | stdout | 표준 출력 | 화면 |
| `2` | stderr | 표준 **오류** | 화면 |

출력이 왜 두 개일까요? 화면에 나올 땐 똑같아 보이는데 말이죠.

<Hist year="1970s" title="조판 사고가 stderr 를 만들었다">
처음에는 출력 통로가 하나뿐이었습니다. 그런데 벨 연구소에서 문서 조판 프로그램을 돌리다 문제가 생겼습니다. 출력을 파일로 보내 인쇄를 걸었는데, **프로그램이 뱉은 오류 메시지가 결과물 한복판에 그대로 인쇄된** 것입니다.

당시 조판은 사진 식자기를 거치는 비싼 작업이었고, 이런 사고는 실제 손실이었습니다. 그래서 **결과물과 오류 메시지를 다른 통로로 분리**하기로 합니다. 이것이 stderr입니다.

덕분에 오늘날 우리는 이런 일이 가능합니다 — **결과만 파일로 저장하면서 오류는 화면으로 보기.** 서버 자동화에서 "성공한 결과는 저장하고 실패만 알림으로 받는" 구조가 전부 이 분리 위에 서 있습니다.
</Hist>

## 3.3 리다이렉션 — 통로 갈아끼우기

| 기호 | 하는 일 |
|---|---|
| `>` | stdout을 파일로 (**기존 내용 덮어씀**) |
| `>>` | stdout을 파일 끝에 이어붙임 |
| `2>` | stderr만 파일로 |
| `2>&1` | stderr를 stdout과 같은 곳으로 |
| `&>` | stdout과 stderr 둘 다 |
| `<` | 파일을 stdin으로 |

<Term code={`
$ echo "첫 줄" > note.txt      # 새로 만들거나 덮어씀
$ echo "둘째 줄" >> note.txt   # 이어붙임
$ cat note.txt
첫 줄
둘째 줄

# 오류만 따로 빼기 — 있는 파일과 없는 파일을 같이 요청
$ ls note.txt nofile.txt > ok.txt 2> err.txt
$ cat ok.txt
note.txt
$ cat err.txt
ls: cannot access 'nofile.txt': No such file or directory
`} />

성공한 결과는 `ok.txt`로, 오류는 `err.txt`로 갈라졌습니다. **한 번의 실행에서 두 통로가 다른 목적지로 간 것입니다.**

<Note type="danger" title="&gt; 는 되돌릴 수 없습니다">
`>`는 **기존 파일 내용을 통째로 날리고** 새로 씁니다. 확인 질문은 없습니다. Chapter 2의 `rm`과 같은 이유입니다.

```
$ 명령 > 중요설정.conf     ← 설정 파일이 명령 출력으로 덮어써짐
```

특히 `>>`로 쓸 자리에 `>`를 치는 실수가 흔합니다. **로그에 이어붙이려다 로그를 다 날리는** 사고죠. 중요한 파일에 리다이렉션할 때는 한 번 더 보세요.
</Note>

<Note type="tip" title="이제 2&gt;/dev/null 이 읽힙니다">
Chapter 2에서 `find / ... 2>/dev/null`을 "오류를 숨기는 관용구"로 넘어갔습니다. 이제 정확히 읽을 수 있습니다.

**stderr(2번 통로)를 `/dev/null`로 보내라.** `/dev/null`은 무엇을 써도 사라지는 장치 파일이니, 결국 오류 메시지만 버리고 정상 결과는 화면에 남기라는 뜻입니다.
</Note>

<Mini title="통로 갈라보기">
1. `ls /etc /없는폴더 > out.txt 2> err.txt` 를 실행하고 두 파일을 각각 `cat`으로 확인하세요.
2. 같은 명령을 `&> all.txt`로 실행해 둘이 합쳐지는 것을 보세요.
3. `date >> log.txt` 를 세 번 실행하고 `cat log.txt`로 세 줄이 쌓였는지 확인하세요.
4. 3번을 `>` 로 바꿔 세 번 실행한 뒤 다시 확인하세요. 몇 줄이 남았나요?

<Answer>
<Term code={`
$ date > log.txt
$ date > log.txt
$ date > log.txt
$ wc -l log.txt
1 log.txt
`} />

`>`는 매번 덮어써서 **한 줄만 남습니다.** `>>`였다면 세 줄이 쌓였겠죠. 로그를 남기는 스크립트에서 이 한 글자를 잘못 쓰면 기록이 계속 사라지는데, 사고가 나고 로그를 열어봤을 때야 발견하게 됩니다.
</Answer>
</Mini>

## 3.4 파이프 — 이 과정에서 가장 중요한 한 글자

리다이렉션이 출력을 **파일로** 보내는 것이라면, 파이프(`|`)는 출력을 **다음 프로그램의 입력으로** 보냅니다.

<Term code={`
# 앞 명령의 stdout 이 뒤 명령의 stdin 이 된다
$ ls /usr/bin | wc -l
1847
`} />

`ls`는 파일 목록을 뱉고, `wc -l`은 줄 수를 셉니다. 둘을 이으니 **"프로그램이 몇 개 설치돼 있나"**라는 새로운 도구가 됐습니다. 아무도 그런 프로그램을 만들지 않았는데도요.

<Hist year="1973" title="하룻밤에 구현된 아이디어, 그리고 다음 날 아침">
파이프의 아이디어는 더그 매클로이가 **1964년 메모**에 적어둔 것이었습니다. "프로그램을 정원 호스처럼 이어붙일 수 있어야 한다. 다른 데이터가 필요할 때 다른 호스를 끼우듯이."

그는 몇 년 동안 이 아이디어를 밀어붙였고, 1973년 켄 톰슨이 **하룻밤 만에** 셸에 구현했습니다. 그리고 다음 날 아침, 연구실 사람들이 명령을 이어붙이기 시작했습니다. 매클로이는 그날을 이렇게 회고했습니다 — **모두가 흥분해서 이것저것 이어붙여 보느라 하루가 갔다고.**

이 하룻밤이 UNIX를 완성했습니다. 그때까지 "작은 도구를 만들자"는 원칙은 그저 검소한 태도였지만, 파이프가 생기자 **작은 도구가 조합 가능한 부품**이 되었습니다. 도구 20개로 조합할 수 있는 경우의 수를 생각해 보세요. 리눅스에서 "명령어를 안다"는 것은 개별 명령을 외운다는 뜻이 아니라 **어떻게 이어붙일지 안다**는 뜻입니다.
</Hist>

<Compare>
  <Win>작업마다 그 작업을 위한 프로그램이 있습니다. 로그를 분석하려면 로그 분석 프로그램을 구하거나 만들어야 하고, 그 프로그램이 못 하는 일은 못 합니다.</Win>
  <Lin>작은 도구를 이어붙여 **필요한 도구를 그 자리에서 만듭니다.** 로그 분석 프로그램이 없어도 `grep`·`sort`·`uniq`를 이으면 됩니다.</Lin>
</Compare>

<Note type="tip" title="파이프라인을 만드는 요령">
한 번에 다 쓰지 마세요. **한 단계씩 붙이면서 그때그때 결과를 확인**하는 것이 정석입니다.

```
$ cat access.log | head -3                    ← 원본이 어떻게 생겼나
$ cat access.log | grep " 404 " | head -3     ← 잘 걸러졌나
$ cat access.log | grep " 404 " | awk '{print $7}' | head -3   ← 열이 맞나
```

중간에 `head`를 붙여 조금만 보면서 진행하면, 어느 단계에서 틀어졌는지 바로 압니다.
</Note>

## 3.5 이어붙일 부품들

| 명령 | 하는 일 | 자주 쓰는 옵션 |
|---|---|---|
| `grep` | 패턴이 든 줄만 통과 | `-i` 대소문자 무시 · `-v` 반대 · `-c` 개수 · `-r` 하위까지 · `-n` 줄번호 |
| `sort` | 정렬 | `-n` 숫자 · `-r` 역순 · `-k2` 2번째 열 기준 · `-u` 중복 제거 |
| `uniq` | 연속 중복 처리 | `-c` 개수 세기 · `-d` 중복만 |
| `wc` | 세기 | `-l` 줄 · `-w` 단어 · `-c` 바이트 |
| `head` / `tail` | 앞/뒤 일부 | `-n 20` · `tail -f` 실시간 추적 |
| `cut` | 열 잘라내기 | `-d: -f1` 구분자와 필드 |
| `tr` | 글자 치환/삭제 | `tr 'a-z' 'A-Z'` · `-d` 삭제 |
| `tee` | 화면에 보여주면서 파일에도 저장 | `command \| tee out.txt` |

<Term code={`
# 사용자 계정 이름만 뽑기 — /etc/passwd 는 콜론으로 구분된다
$ cut -d: -f1 /etc/passwd | head -5
root
daemon
bin
sys
sync

# 로그인 셸이 bash 인 계정만 세기
$ grep "/bin/bash" /etc/passwd | wc -l
2

# 실시간 로그 감시 — 서버 운영의 기본기
$ sudo tail -f /var/log/syslog
`} />

<Hist year="1974" title="grep 의 이름은 명령어 자체다">
Chapter 2에서 vi 이전의 편집기 `ed`를 잠깐 언급했습니다. `ed`에서 "파일 전체(**g**lobal)에서 어떤 패턴(**re**gular expression)에 맞는 줄을 출력(**p**rint)하라"는 명령이 `g/re/p` 였습니다.

더그 매클로이가 켄 톰슨에게 이 기능을 독립 프로그램으로 만들어달라고 부탁했고, 톰슨은 **하룻밤 만에** 만들어 다음 날 건넸습니다. 이름은 명령어 문법을 그대로 가져다 `grep`이라 붙였습니다.

`tee`의 이름도 같은 방식입니다. 물이 흐르다 두 갈래로 갈라지는 **T자 배관**에서 왔습니다. 화면과 파일로 동시에 보내니까요.
</Hist>

### sed 와 awk — 한 걸음 더

<Term code={`
# sed : 스트림 편집기. 치환이 주 용도
$ echo "hello world" | sed 's/world/linux/'
hello linux

# 파일 안에서 직접 치환 (-i 는 in-place, 되돌릴 수 없다)
$ sed -i 's/8080/9090/' config.txt

# awk : 열 단위 처리에 강하다
$ awk -F: '{print $1, $3}' /etc/passwd | head -3
root 0
daemon 1
bin 2

</Note>

### PATH — 명령어를 찾는 순서

`ls`를 치면 셸은 `PATH`에 적힌 디렉터리를 **앞에서부터 차례로** 뒤져 `ls`라는 실행 파일을 찾습니다. 먼저 찾은 것을 실행하고 멈춥니다.

<Term code={`
$ which ls
/usr/bin/ls

$ type cd
cd is a shell builtin      # cd 는 파일이 아니라 셸에 내장된 기능이다
`} />

<Note type="danger" title="현재 디렉터리가 PATH 에 없는 이유 — 보안">
윈도우는 **현재 폴더를 먼저 찾습니다.** 리눅스는 `PATH`에 `.`(현재 디렉터리)이 들어 있지 않고, 이건 실수가 아니라 **의도적인 보안 설계**입니다.

만약 `.`이 `PATH` 맨 앞에 있다면 이런 공격이 가능합니다. 공격자가 공용 디렉터리에 `ls`라는 이름의 악성 스크립트를 심어둡니다. 관리자가 그 디렉터리에서 무심코 `ls`를 치면, 진짜 `/usr/bin/ls` 대신 **그 스크립트가 root 권한으로 실행됩니다.**

그래서 리눅스에서는 현재 디렉터리의 프로그램을 실행할 때 반드시 `./script.sh`처럼 **경로를 명시**해야 합니다. 귀찮아 보이는 이 규칙이 방어막입니다. `PATH`에 `.`을 추가하라는 인터넷 조언을 보면 무시하세요. Chapter 10 하드닝에서 이 원칙을 다시 만납니다.
</Note>

### ~/.bashrc — 내 환경 만들기

셸을 새로 열 때마다 자동으로 실행되는 설정 파일입니다. 여기에 별칭과 변수를 넣어두면 매번 타이핑할 필요가 없습니다.

| 파일 | 언제 읽히나 |
|---|---|
| `~/.bashrc` | 대화형 셸을 열 때마다 (**대부분 여기 넣으면 됨**) |
| `~/.bash_profile` | 로그인할 때 한 번 |
| `/etc/profile`, `/etc/bash.bashrc` | 전체 사용자 공통 |

<Term code={`
$ vi ~/.bashrc

# 파일 끝에 추가
alias ll='ls -alhF'
alias rm='rm -i'            # Chapter 2의 안전장치
alias ..='cd ..'
alias logs='cd /var/log'
export EDITOR=vim

# 저장 후 — 새 셸을 열거나 지금 셸에 즉시 반영
$ source ~/.bashrc
$ ll
`} />

<Note type="tip" title="source 를 왜 쓰나">
`~/.bashrc`는 **셸이 시작할 때** 읽힙니다. 방금 고친 내용은 이미 열려 있는 셸에는 반영되지 않습니다. `source ~/.bashrc`(또는 `. ~/.bashrc`)는 **지금 이 셸에서 그 파일을 다시 읽으라**는 뜻입니다.

셸을 새로 열어도 되지만, 설정을 고치고 바로 확인하는 습관을 들이면 오타를 즉시 발견할 수 있습니다. `.bashrc`에 문법 오류가 있으면 다음 로그인부터 셸이 이상해지는데, 원인을 찾기가 은근히 까다롭습니다.
</Note>

## 3.7 작업 제어 — 오래 걸리는 일 다루기

| 조작 | 하는 일 |
|---|---|
| `명령 &` | 처음부터 백그라운드로 실행 |
| <kbd>Ctrl</kbd>+<kbd>Z</kbd> | 실행 중인 작업 일시 정지 |
| `jobs` | 이 셸의 작업 목록 |
| `bg` | 정지된 작업을 백그라운드로 재개 |
| `fg` | 백그라운드 작업을 앞으로 |
| <kbd>Ctrl</kbd>+<kbd>C</kbd> | 실행 중인 작업 종료 |
| `nohup 명령 &` | 로그아웃해도 계속 실행 |

<Term code={`

$ bg
[1]+ sleep 300 &

$ jobs
[1]+  Running                 sleep 300 &

$ fg
sleep 300
^C
`} />

<Note type="warn" title="접속이 끊기면 작업도 죽습니다">
SSH로 서버에 접속해 오래 걸리는 작업을 돌리다 **네트워크가 끊기면 그 작업도 함께 죽습니다.** 셸이 종료될 때 자식 프로세스에게 종료 신호를 보내기 때문입니다.

당장 쓸 수 있는 해법은 `nohup`입니다.

```
$ nohup ./backup.sh > backup.log 2>&1 &
```

다만 실무에서는 `tmux`나 `screen` 같은 **터미널 다중화 도구**를 씁니다. 접속이 끊겨도 세션이 서버에 남아 있어서, 다시 접속해 하던 화면 그대로 이어받을 수 있습니다. Chapter 7 원격 접속 시간에 다룹니다.
</Note>
